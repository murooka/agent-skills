# adr-writing

ADR（アーキテクチャ決定記録）を書くとき、ADR の置き場を用意するときは、この手順に従う。

## 中心原理

**ADR は、後から変えにくい決定について、見直す人が「今も守るべきか、変えてよいか」を判断できるようにする記録である。**

ADR が読まれるのは、決定が揺らいだときである。

1. 不満や不具合が出た、新しい技術が出た、規模が変わったなどの理由で、変えたくなったとき
2. 「B のほうがよくない?」と、同じ議論が繰り返されそうなとき
3. 背景を知らない人や AI が、既存の作りに手を入れるとき

どの場面でも読み手が知りたいのは、当時の前提、知っていて落とした案、そして**検討していないこと**である。理由が「特に理由はない」なら調査なしで変えてよいと分かる。「シャーディングした MySQL」の ADR に NoSQL が載っていなければ、知らなかったと分かる。載っていて「使ったことがない」とあれば、落とした事情が分かる。

したがって ADR の失敗は 2 つある。

- **決定でないものを ADR にする。** 要求、制約、当たり前の原則も「〜する」と書けるので、文としては成り立ってしまう。
- **人が判断していないことを、判断したように書く。** 本人が言っていない理由は、未来の読み手に存在しない前提を守らせる。

## ADR にするもの

次の 2 つを満たすなら ADR にする。

1. **ほかの選択もできた。**
2. **後から変えるコストが高い、または「なぜこうなっているのか」と迷いそうである。**

実際に比べたかどうか、理由があるかどうかは問わない。

| 種類 | 例 |
|---|---|
| 言語・基盤 | バックエンドを Go にする、クラウドは GCP にする |
| データストア | Spanner にする、シャーディングした MySQL にする |
| フレームワーク、依存の広いライブラリ | Next.js にする、ORM を使わず SQL を直接書く |
| ツール | テストフレームワーク、linter、formatter、CI サービス、IaC の選定 |
| 全体の構造、通信 | モノリスにする、モノレポにする、サービス間を gRPC にする |
| 外部サービスとの分担 | 認証を自前で作らず Auth0 を使う |
| 変えにくいデータ設計 | ID を UUIDv7 にする、複雑なデータモデルの RDB での表現、マルチテナントの分離方式 |
| 定石から外れた選択 | 定番があるのに自前で作る、外部キーを張らない |
| 過去の決定を覆すもの、試験的な導入 | MySQL から Spanner へ移行する |

Design Doc の中で下した決定も、変えにくければ ADR にする。埋もれると、見直す人が見つけられない。昔の決定を今から記録するのもよい。

### ADR にしないもの

捨てずに行き先を示す。

| 対象 | 例 | 行き先 |
|---|---|---|
| 要求（何を満たすべきか） | 操作の記録を改ざんできない形で残す | PRD |
| 外部の制約。**規格・法令・ガイドライン・顧客の指定を名指ししているもの** | PCI DSS に準拠する、変えられない社の規定 | PRD |
| 製品の判断 | 無料プランの上限を 3 プロジェクトにする | Product Spec |
| 当たり前の原則 | 最小権限にする、秘密情報をコミットしない | どこにも書かない |
| 実現方法の細部 | テーブル定義、エンドポイント、リトライ回数 | Design Doc |
| 運用上の値 | レプリカ数、タイムアウト値 | 設定やコード |
| 他の ADR から決まること | Spanner を選んだので公式クライアントを使う | その ADR の「結果」 |
| 局所的ですぐ戻せること | ディレクトリ配置、命名、一部の機能でしか使わない小さなライブラリ | どこにも書かない |
| 手段が未定のもの | 改ざんできない記録をどの技術で作るかは未定 | 決めるときに ADR にする |
| 選択の余地がない更新、不具合の修正 | サポート終了に伴うメジャーバージョン更新、N+1 の解消 | PR やコミット |

**どこから課されたかを名指ししていない記述は、決定として扱う。** 「〜する」とだけ書かれ、主体も根拠も無いものがこれにあたる。出どころを確かめたいことを報告に挙げ、制約だと分かれば差し戻す（マージ前なら番号を詰める）。

**1 文に原則と決定が同居しているときは、選ぶ余地のある部分だけを決定にする。** 「専用 DB ではなく本番 DB から、サーバー経由で読む」なら、決定は「専用 DB ではなく本番 DB から読む」で、「サーバー経由で」は背景の前提に落とす。

**元の文書には手を入れない。** 行き先は「新しくどこへ書くか」であって、「元の文書から消せ」ではない。ADR へ移した要求も元の文書に残す。ADR は要求に応えて選んだ決定の記録で、要求の置き場ではない。上流へのリンク追加、書き換え、削除が必要だと思ったら、報告に挙げて判断を仰ぐ。

## 材料の状態

中身が欠けていることは、ADR を書かない理由にならない。**聞いて「無い」と分かったことと、まだ聞けていないことを分けて書く。**

| 項目 | 取れている | 無いと分かった | まだ聞けていない |
|---|---|---|---|
| 理由 | そのまま書く | 「特に理由はない」 | 「未確認（誰に何を聞くか）」 |
| 代替案 | 案と不採用の理由を書く | 「比べていない」 | 案を示す。返事が無ければ案は本文に載せず報告に残し、節には「未確認（誰に何を聞くか）」と書く |
| 不採用の理由 | そのまま書く | 「特に理由はない」 | 案ごとに「未確認（誰に何を聞くか）」 |

「無い」は、決定者が言ったときだけ書く。書き手が推し量って「特に理由はない」「比べていない」と書くのも捏造である。「よく覚えていない」のように、どちらにも当たらない回答は言葉のまま書く。回答なので「未確認」にはしない。

- ADR を書くよう頼まれた → [書く](#書く)

## 書く

ユーザーがすでに述べた材料は聞き直さない。依頼の時点で決定や理由が出ていれば、足りないものだけを聞く。**聞くことは 1 回にまとめる。** 同意済みのことを聞き直して問答を増やさない。

複数の ADR を頼まれたら、判定はまとめて行い、書くのは 1 本ずつにする。元の文書に並んでいるからといって決定とは限らないので、1 件ずつ判定する。

### 1. 判定する

[ADR にするもの](#adr-にするもの)に照らす。ADR にしないものは、理由と行き先を示す。

### 2. 背景と課題を押さえる

- 今の実装の事実を**コードで確かめる**。新規開発でコードが無いなら、確かめた範囲を報告に書く。
- 上流に PRD や Product Spec があれば読む。
- 課題を一文で書く（書き方は [references/norms.md](references/norms.md) の「課題」）。ユーザーが述べていなければ、次の手順の質問と一緒に見せて合意を取る。ほかに聞くことが無ければ、課題のためだけに質問せず、報告で示す。

実現方法の細部には、決定が固まるまで踏み込まない。細部は決定が曖昧でも先へ進められるので、決めるべきことが決まったように見えてしまう。

### 3. 選択肢を示し、判断をもらう

**決定者に候補を見せることが、ADR の質を最も上げる。** AI が挙げた案でも、見せれば人は頭の中で判断する。即却下でも記録になる。

- 実際に候補になる案を「内容」「利点」「欠点」の 3 列の表で示す。論点が複数なら表を分ける。
- ユーザーがすでに決めていて案を挙げていなくても、**有力な案を示して採否と理由を聞く。** 「使ったことがない」「知らなかった」で十分である。書き直させない。
- 今の作りを続ける案も、要求や課題を満たせるなら入れる。比べる基準になる。
- 示す段階で、課題に効かない案は省く。示して却下された案は、即却下でも本文に残す。
- ユーザーが「ほかは見ていないし、今も見なくていい」と言えば、代替案は「比べていない」と書く。

### 4. 理由を聞き、評価する

理由はユーザーの判断である。推測や上流の文書で埋めない。ただし、**書き手の提案に同意したことは、ユーザーの判断である。** 同意済みのことは聞き直さず、提案に同意したと分かる形で書く。

出どころごとの書き方と、受け取った理由を評価する 5 点: [references/reasons.md](references/reasons.md) — **理由を扱うときに読む。** 評価は飛ばさない。

### 5. 書く

書式と規範: [references/norms.md](references/norms.md) — **書く前に読む。**

- ファイル名、番号、Status は[置き場と連番](#置き場と連番)に従う。
- テンプレートは `docs/adr/README.md` に従う。既存の ADR と食い違うときは README を優先し、食い違いを報告する。無ければ[置き場を用意する](#置き場を用意する)。
- 書いたら README の一覧に行を足す。

### 6. 見直す人の目で確かめる

書いた経緯をいったん忘れて、決定を変えたくなった人としてこの ADR だけを読む。

- [ ] 当時の前提が今も成り立つかを、この ADR だけで確かめられるか
- [ ] 検討した案と、検討していないことを見分けられるか
- [ ] 代替案の節があるか。各案に不採用の理由、「特に理由はない」、「未確認」のいずれかが付いているか
- [ ] 決定者が見ていない案を載せていないか
- [ ] 決定者が言っていない理由を書いていないか。提案への同意は同意と分かる形か
- [ ] 課題が決定の言い換えや、要求の写しになっていないか
- [ ] 必須の 5 節（背景・課題・決定・理由・検討した代替案）が規範の順に並んでいるか。見出しに英語を併記していないか
- [ ] 提案書を根拠にしていないか。コードへのリンクは実在するか
- [ ] 「適切に」「十分な」のような語で、何を指すかをぼかしていないか
- [ ] 1 本に決定が 1 つだけか

### 7. 報告する

- 書いた ADR のパス、番号、タイトル、Status
- ADR にしなかったものと行き先
- 「未確認」の項目と、誰に何を聞くか
- 評価で返したことのうち、返事がまだのもの
- コードで確かめた事実と、確かめられなかった事実

## 置き場と連番

- 置き場は **`docs/adr/`**。リポジトリ全体やアプリをまたぐ決定は `docs/adr/` に、1 つのアプリ内で完結する決定はそのアプリの中に置く。
- ファイル名は `NNNN-slug.md`（`0004-session-store.md`）。番号は 4 桁の連番、slug は内容を表す英小文字とハイフン。
- **マージ前に ADR を消したら、番号を詰める。**
- Status は次の 3 つだけを使う。

  | Status | 条件 |
  |---|---|
  | `承認済み` | 決定に合意があり、本文に「未確認」が無い |
  | `提案中` | 合意がまだか、本文に「未確認」がある |
  | `置換済み(→ NNNN)` | 新しい ADR に覆された |

  - **ユーザーが自分から述べた決定は、合意があるものとして扱う。** 「〜しようと思う」でも合意である。
  - **「特に理由はない」「比べていない」は回答なので、`承認済み` にできる。**
  - こちらが返した評価への返事待ちは、Status に影響させない。評価は提案であって、決定を保留させるものではない。
  - `提案中` の ADR も README の一覧に載せる。
- **マージ後の ADR は修正しない。** 決定を覆すときは新しい ADR を書き、古い ADR の Status を `置換済み(→ NNNN)` に変える。
- **ADR はフロー情報である。** 今のアーキテクチャの正としては参照しない。今どうなっているかはコードを見る。

## 置き場を用意する

1. 置き場を決める（[置き場と連番](#置き場と連番)）。
2. `docs/adr/README.md` を [assets/adr-readme.md](assets/adr-readme.md) から作る。
3. 既存の ADR があるなら、その書式に合わせる。ただし**理由と代替案をそれぞれ独立した節にすることは譲らない。** 見直す人が読むのはこの 2 つである。既存の書式を変えることになるなら、ユーザーに断ってから変える。
