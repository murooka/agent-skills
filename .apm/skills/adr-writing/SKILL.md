# adr-writing

ADR（アーキテクチャ決定記録）を書くとき、ADR の置き場を用意するときは、この手順に従う。

## 中心原理

**ADR は意思決定の記録である。アーキテクチャに課題があり、その解決に複数の選択肢があり、なぜその選択肢を選んだかという理由があって、初めて書く必要が生まれる。**

AI に ADR を書かせたときに起きるのは、捏造よりも先に**課題のない ADR が増えること**である。要求、制約、当たり前の原則は、どれも「〜する」という決定の形に書き換えられる。書き換えたものは文として成り立ち、セクションも埋まるので、読み手が「これは何を決めているのか」と問うまで誰も気づけない。そして課題が曖昧なまま実現方法だけが進むと、前提が崩れた時点で積み上げた設計をまとめて捨てることになる。

そこで、書く前に次の条件を確かめる。

## 書く条件

次の 3 つを書けるなら ADR にする。書けないなら ADR にしない。ただし「書けない」には 2 通りあるので、次節「満たさないのか、まだ確かめられないのか」で分ける。

| 条件 | 書けていることの確かめ方 |
|---|---|
| **課題** | 「課題は、〜である。」と一文で言える。今の作りの何が問題かを言えている |
| **採用しなかった選択肢** | 少なくとも 1 つ挙がり、採用しなかった理由が付いている |
| **理由** | なぜその選択肢を選んだかを、ユーザーの言葉で言える |

「結果」は任意である。

### 満たさないのか、まだ確かめられないのか

**条件を「満たす / 満たさない」の 2 値で判定しない。** 3 つめの状態がある。

| 状態 | 見分け方 | どうするか |
|---|---|---|
| 満たす | 3 つとも書ける | ADR を書く。Status は[置き場と連番](#置き場と連番)の規則で決める |
| **満たさない** | 課題が一文で言えない、代替案を挙げられない、または聞いたうえで理由が無いと分かった。**「条件を満たさないものの行き先」の表に当てはまるものは、聞かずにここへ入れる** | ADR にしない。「条件を満たさないものの行き先」（次節）を示す |
| **まだ確かめられない** | 確かめる先はあるが、いま答えが得られない | Status `提案中` で書く。取れていない項目は、空欄にも推測にもせず「未確認」と本文に書き、**何をすれば確かめられるかを添える**（人に聞く／実物で検証する／文書を探す）。報告の確認事項に送る。`承認済み` にしない |

「満たさない」と「まだ確かめられない」を混ぜると、聞けば答えのあることを捨てるか、答えの無いことを推測で埋めるかの、どちらかの誤りになる。

**合意が取れていないだけなら、「まだ確かめられない」ではない。** 3 つの材料が揃っているなら条件は満たしているので、書いてよい。合意の有無は Status で表す（揃っていて合意がまだなら `提案中`）。

**「まだ確かめられない」にできるのは、理由と、代替案を採用しなかった理由だけである。** 課題はコードと上流の文書から自分で一文にするものなので、書けないなら「満たさない」である。代替案も、選択肢を並べるのは自分の仕事なので、挙げられないなら「満たさない」である（**自分で並べた案を本文に載せるかは別の判断である。** `references/norms.md` の「検討した代替案」）。この 2 つを返事待ちにすると、中身の無い ADR がいくらでも書けてしまう。

### 条件を満たさないものの行き先

ADR にしないと判定したら、**捨てずに行き先を示す。** 条件を満たさないものは、たいてい別の文書に属している。

| 対象 | 例 | 行き先 |
|---|---|---|
| 要求（何を満たすべきか） | 操作の記録を、書き換え・削除できない形で保存する | PRD |
| 制約（比べて選んだのではなく、外部から課される）。**外部の規格・法令・ガイドラインを名指ししているものは、出どころが書かれているものとして制約に入れる** | 業界のガイドラインに準拠する | PRD |
| 当たり前の原則 | 最小権限、要るものだけを返す API | どこにも書かない。Design Doc の設計で守る |
| 実現方法が未定の事柄 | 書き換えできない記録を、どの技術で作るか | 方法を決めるときに、改めて ADR にする |
| 選択肢のない決定 | ほかの ADR の決定から自動的に決まること | その ADR の「結果」に書く |

**どこから課されたかを名指ししていない記述は、決定として扱う。**「〜する」とだけ書かれ、主体も根拠も無いものがこれにあたる。制約として差し戻すと、比べて選んだ決定の記録が失われる。決定として扱い、**出どころを確かめたいことを報告に挙げる。** 制約だと分かれば、そのとき差し戻せばよい（マージ前なら番号を詰める）。

**行き先は「新しくどこへ書くか」であって、「元の文書から消せ」ではない。** すでに元の文書に書かれているものは、移さず触らず、扱いを報告で問う。行き先が「どこにも書かない」の当たり前の原則も同じで、勝手に消さない。

**要求を ADR へ移すときに、元の文書から消さない。** すでに消えている状態で ADR をやめるなら、要求を PRD へ戻してから消す。要求がどこにも残らない状態を作らない。PRD の書き方は `dev-doc-writing` スキルに従う。

**上流の文書に手を入れるのは、ユーザーに断ってからにする。** ADR を書いたあとに上流の項目から ADR へリンクを張ること、要求を書き換えること、消すことはどれも、この作業の範囲外である。必要だと思ったら、報告に挙げて判断を仰ぐ。ADR を書く依頼は、上流の文書を直す許可ではない。

## 実現方法は、課題と選択肢が決まるまで進めない

課題が一文で言えていないうちに、鍵の管理、トークンの受け渡し、検証の手順といった実現方法の設計を進めない。実現方法は課題が曖昧でも先へ進められてしまうため、進んだこと自体が「決めるべきことは決まった」という錯覚を生む。前提が崩れると、積み上げた分がまとめて無駄になる。

実現方法を決めることが目的なら、それは Design Doc の仕事である（`dev-doc-writing` スキル）。ADR は「どの選択肢を選んだか」までを書き、「どう作るか」は書かない。

## 作業の判定

- ADR を書くよう頼まれた → [書く](#書く)
- ADR の置き場や README を新しく作るよう頼まれた、または書こうとして置き場がなかった → [置き場を用意する](#置き場を用意する)

複数の ADR を頼まれたら、**条件の判定だけはまとめて行い、書くのは 1 本ずつにする。** 何が課題で何が要求かは、並べて比べたほうが見分けやすい。一方、まとめて下書きしてから見直すと、課題の重なりと本数の分け方を同時に考えることになり、どちらも詰め切れない。

## 書く

手順 1〜3 は、材料が何も無い状態から対話で集める並びになっている。**ユーザーが先に決定や理由を述べているときは、その手順を確認だけで通過してよい。** 依頼の時点で「A と B で迷ったが A にする。理由は〜」まで出ていることはよくある。その場合、手順 2 で選択肢を一から作り直す必要はなく、述べられた案を表にして、抜けている案と理由だけを足す。

ただし**通過させてよいのは、材料が実際に揃っている手順だけである。** 課題の一文は、ユーザーが述べていなければ自分で書いて合意を取る（手順 1 は飛ばせない）。

### 1. 課題を一文にして、ユーザーと合意する

- 今の実装の事実を**コードで確かめる**。上流の文書の記述や、提案書の記述で済ませない（[references/norms.md](references/norms.md) の「背景の事実は 2 つで示す」）。
- 上流に PRD や Product Spec があれば読み、ADR が必要になった背景を押さえる。
- 「課題は、〜である。」の形で一文を書き、ユーザーに見せて合意を取る。
- 一文が書けない、または「今の作りの何が問題か」に答えられないなら、**「条件を満たさないものの行き先」の表を示して、ADR にしないことを提案する。** 書けないまま書き始めない。
- 1 本に 1 つの課題。2 つ以上が混ざったら、本数を分ける。

**既存の記述（PRD の技術的要求など）を ADR へ移すよう頼まれたときも、1 件ずつ条件に照らす。** 元の文書に並んでいるからといって、それが決定だとは限らない。要求が要求として並んでいただけのことが多い。

- 条件を満たさないものは移さず、元の文書に残す。
- 条件を満たすものでも、**元の文書の要求を消さない。** ADR は要求に応えて選んだ決定の記録であって、要求の置き場ではない。消すと、ADR をやめたときに要求がどこにも残らなくなる。

### 2. 選択肢を表にして示す

- 「内容」「利点」「欠点」の 3 列の表にする。
- 論点が複数あるなら、論点ごとに表を分ける。1 つの表に混ぜると、ユーザーはどの論点に答えているのかわからなくなる。
- 今の作りを続ける案（何も変えない案）も、**上流の文書の要求を満たせるなら**選択肢に入れる。ほかの案を比べるときの基準になる。満たせないなら入れず、入れなかったことを報告に書く。
  - 上流の文書が無いときは、**手順 1 で合意した課題**に照らす。課題を解消しないなら入れない。
  - 今の作りが採用案と同じなら、別案として立たないので入れない。満たせないから外したのではないので、その旨を報告に書く。

### 3. ユーザーが選び、理由を述べる。その理由を評価する

理由はユーザーに聞く。上流の文書や推測で埋めない。**受け取った理由を、評価せずに通さない。**

禁じているのは評価を飛ばすことであって、文面を必ず書き直すことではない。評価して気づいたことはユーザーに返し、**返事が来るまでは受け取った言葉のまま書く。** 書き直した理由を勝手に本文に入れると、ユーザーが述べていない判断がユーザーの判断として残る。

聞き方、評価で見る 5 点、評価したことを ADR に書く順序: [references/reasons.md](references/reasons.md) — **理由を扱うときに読む。聞く前と、受け取ったあとの両方で読む。** 返事をもらえなかった回にも読む（そのときの扱いが書いてある)。

### 4. 書く

書式と書き方の規範: [references/norms.md](references/norms.md) — **書く前に読む。**

- ファイル名と番号は、[置き場と連番](#置き場と連番)に従う。
- テンプレートは、リポジトリの `docs/adr/README.md` にあるものに従う。**既存の ADR の書式と食い違うときは README を優先し、食い違いを報告に挙げる。**無ければ [assets/adr-readme.md](assets/adr-readme.md) のテンプレートを使い、[置き場を用意する](#置き場を用意する)に進んで README も置く。
- 書いたら、README の一覧に行を足す。

### 5. チェックリストで確かめる

書き終えたら、自分で次を確かめる。上の 4 つが見落としやすい。いずれも**書いた本人には読める**ために通ってしまう項目なので、書いた経緯をいったん忘れて、この ADR だけを初めて開いた人の立場で読む。

- [ ] 「課題」セクションの冒頭が「課題は、〜である。」の一文になっているか。それが ADR を初めて読む人に課題を伝えているか。課題が決定の言い換えになっていないか
- [ ] 課題と理由が、それぞれ独立したセクションにあるか（「背景」や「決定」の中に埋めていないか）
- [ ] 検討した代替案に、採用しなかった**理由**が書いてあるか（案の中身だけで終わっていないか）
- [ ] ユーザーの答えに無い理由を書き足していないか。推奨したときの理由を、ユーザーが選んだ理由として流用していないか
- [ ] 提案書を引用していないか。ADR の中だけで情報が完結しているか、PRD・Product Spec を参照しているか
- [ ] コードへのリンクが実在するか（パスを開き、指している関数・設定を目で見て確かめる）
- [ ] 「範囲」「適切に」「十分な」のような抽象的な語で、何を指すかをぼかしていないか
- [ ] 1 本に課題が 1 つだけか
- [ ] 必須の 5 セクション（背景・課題・決定・理由・検討した代替案）が規範の順に並んでいるか。見出しに英語を併記していないか

### 6. 報告する

ユーザーに次を報告する。

- 書いた ADR のパス、番号、タイトル
- 条件を満たさず ADR にしなかったものと、その行き先。PRD へ戻す必要があるものは、戻したか・まだかを明示する
- 理由の評価で足したもの（残るリスク、前提、突き詰めて出た選択肢）のうち、ユーザーの確認がまだのもの
- コードで確かめた事実と、確かめられなかった事実
- ユーザーの返事をもらえなかったときは、示すはずだった課題の一文と選択肢の表も載せる

## 置き場と連番

- 置き場は **`docs/adr/`**。`docs/architecture/adr/` にしない（ADR の A が architecture なので重複する）。リポジトリ全体やアプリをまたぐ決定は `docs/adr/` に、1 つのアプリ内で完結する決定はそのアプリの中に置く。
- ファイル名は `NNNN-slug.md`（`0004-session-store.md`）。番号は 4 桁の連番、slug は内容を表す英小文字とハイフン。
- **マージ前に ADR を消したら、番号を詰める。** 欠番にしない。まだ誰も参照していないので、詰めたほうが読みやすい。
- Status は次の規則で決める。判定に使うのはこの 3 つだけで、ほかは使わない。

  | Status | 条件 |
  |---|---|
  | `承認済み` | 書く条件の 3 項目（課題・理由・代替案を採用しなかった理由）がすべて取れていて、決定と理由にユーザーの合意がある |
  | `提案中` | 3 項目のどれかが取れていない、または合意がまだ |
  | `置換済み(→ NNNN)` | 新しい ADR に覆された |

  - **ユーザーが自分から述べた決定と理由は、合意があるものとして扱う。**「〜しようと思う」でも合意である。
  - **こちらが返した評価への返事待ちは、Status に影響させない。** 評価は提案であって、決定を保留させるものではない。
  - **出どころを明記して書いた背景や結果の事実も、Status に影響させない**（`references/norms.md` の「背景の事実は 2 つで示す」）。判定に使うのは書く条件の 3 項目だけである。どう書いたか（「未確認」「未検証」などの語）ではなく、何が取れていないかで決める。
  - 課題の一文への合意は手順 1 の関門なので、Status の条件には入れない。`提案中` の ADR も README の一覧に載せる。
- **マージ後の ADR は修正しない。** 決定を覆すときは新しい ADR を書き、古い ADR の Status を `置換済み(→ NNNN)` に変える。
- **ADR はフロー情報である。** 決めた時点の記録なので、今のアーキテクチャの正としては参照しない。今どうなっているかはコードを見る。

## 置き場を用意する

1. 置き場を決める（[置き場と連番](#置き場と連番)）。
2. `docs/adr/README.md` を [assets/adr-readme.md](assets/adr-readme.md) から作る。一覧、書く条件、運用ルール、テンプレートが入っている。テンプレートでは、課題・理由・代替案を必須、結果を任意と明記する。
3. 既存の ADR があるなら、その書式に合わせる。ただし**課題と理由をそれぞれ独立したセクションにすることと、代替案を必須にすることは譲らない**。この 3 つは ADR が記録として成り立つかどうかを決める。既存の書式を変えることになるなら、ユーザーに断ってから変える。
