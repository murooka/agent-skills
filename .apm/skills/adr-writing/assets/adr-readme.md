# アーキテクチャ決定記録（ADR）

アーキテクチャの決定と、それを選んだ理由を残す。

## 一覧

| ADR | タイトル | Status | 日付 |
|---|---|---|---|

ADR を書いたら、`| [NNNN](NNNN-slug.md) | <決定を一文で> | 承認済み | YYYY-MM-DD |` の形で行を足す。

## ADR を書く条件

ADR は、アーキテクチャに課題があり、その解決に複数の選択肢があったときに、なぜその選択肢を選んだかという理由を
残すものである。次の 3 つを書けないなら、ADR にしない。

1. **課題** — 「課題は、〜である。」と一文で言えること
2. **採用しなかった選択肢** — 少なくとも 1 つと、採用しなかった理由
3. **理由** — なぜその選択肢を選んだか

「結果」は任意。

### ADR にしないもの

| 対象 | 例 | どこに書くか |
|---|---|---|
| 要求（何を満たすべきか） | 操作の記録を、書き換え・削除できない形で保存する | PRD |
| 制約（外部から課されるもの） | 業界のガイドラインに準拠する | PRD |
| 当たり前の原則 | 最小権限、要るものだけを返す API | 書かない。Design Doc の設計で守る |
| 実現方法が未定の事柄 | 書き換えできない記録を、どの技術で作るか | 方法を決めるときに ADR にする |
| 選択肢のない決定 | ほかの ADR の決定から自動的に決まること | その ADR の「結果」に書く |

## 運用

- 1 本に 1 つの課題。複数の課題が混ざったら分ける。
- ファイル名は `NNNN-slug.md`（4 桁の連番）。書いたら、この README の一覧に行を足す。
- **マージ前に ADR を消したら、番号を詰める。** 欠番にしない。
- **マージ後の ADR は修正しない。** 決定を覆すときは新しい ADR を書き、古い ADR の Status を
  `置換済み(→ NNNN)` に変える。
- **ADR はフロー情報である。** 決めた時点の記録なので、今のアーキテクチャの正としては参照しない。
  今どうなっているかはコードを見る。
- 背景の事実は、PRD・Product Spec へのリンクと、今の実装を示すコードへのリンクで示す。
  提案書は引用しない。
- 見出しに英語（Context、Decision など）を併記しない。

## テンプレート

```markdown
# NNNN. タイトル（決定を一文で）

- Status: 承認済み | 提案中 | 置換済み(→ NNNN)
- 日付: YYYY-MM-DD

## 背景と課題

アーキテクチャにどんな課題があるか。今の実装の事実はコードへのリンクで、ADR が必要になった背景は
PRD・Product Spec へのリンクで示す。最後に「課題は、〜である。」と一文で書く。（必須）

## 決定

どの選択肢を採用したか。実現方法は書かない。（必須）

## 理由

なぜその選択肢を選んだか。（必須）

## 検討した代替案

採用しなかった選択肢と、採用しなかった理由。（必須）

## 結果

この決定によって生じる利点、欠点、やるべきこと。この決定から自動的に決まること。（任意）
```
