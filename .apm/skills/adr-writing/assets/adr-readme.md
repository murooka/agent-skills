# アーキテクチャ決定記録（ADR）

後から変えにくい決定について、見直す人が「今も守るべきか、変えてよいか」を判断できるように残す。

## 一覧

| ADR | タイトル | Status | 日付 |
|---|---|---|---|

ADR を書いたら、`| [NNNN](NNNN-slug.md) | <決定を一文で> | <Status> | YYYY-MM-DD |` の形で行を足す。
`提案中` の ADR も一覧に載せる。

## ADR を書くとき

次の 2 つを満たすなら書く。実際に比べたかどうか、理由があるかどうかは問わない。

1. ほかの選択もできた
2. 後から変えるコストが高い、または「なぜこうなっているのか」と迷いそうである

言語、フレームワーク、依存の広いライブラリ、ツール、データストア、全体の構造、変えにくいデータ設計などが対象である。

**理由が無ければ「特に理由はない」、比べていなければ「比べていない」と書く。** これも見直す人に要る情報である。
まだ聞けていないことは、空欄にも推測にもせず、「未確認（誰に何を聞くか）」と書く。

**検討した代替案には、決定者が見て判断した案を載せる。** 誰が挙げた案でもよく、即却下でも理由を付けて残す。
理由は「使ったことがない」で構わない。載っていない案は、知らなかった案として読まれる。

| Status | いつ |
|---|---|
| `提案中` | 合意がまだか、本文に「未確認」がある |
| `承認済み` | 決定に合意があり、本文に「未確認」が無い |
| `置換済み(→ NNNN)` | 新しい ADR に覆された |

### ADR にしないもの

| 対象 | 例 | どこに書くか |
|---|---|---|
| 要求 | 操作の記録を改ざんできない形で残す | PRD |
| 外部の制約 | PCI DSS に準拠する | PRD |
| 製品の判断 | 無料プランの上限 | Product Spec |
| 当たり前の原則 | 最小権限 | 書かない |
| 実現方法の細部、運用上の値 | テーブル定義、タイムアウト値 | Design Doc、設定やコード |
| ほかの ADR から決まること | 選んだ DB の公式クライアントを使う | その ADR の「結果」 |
| 局所的ですぐ戻せること | ディレクトリ配置、一部の機能でしか使わない小さなライブラリ | 書かない |
| 手段が未定のもの | どの技術で作るかは未定 | 決めるときに書く |
| 選択の余地がない更新、不具合の修正 | サポート終了に伴う更新 | PR やコミット |

## 運用

- 1 本に 1 つの決定。複数の決定が混ざったら分ける。
- ファイル名は `NNNN-slug.md`（4 桁の連番）。書いたら、この README の一覧に行を足す。
- **マージ前に ADR を消したら、番号を詰める。** 欠番にしない。
- **マージ後の ADR は修正しない。** 決定を覆すときは新しい ADR を書き、古い ADR の Status を
  `置換済み(→ NNNN)` に変える。
- **ADR はフロー情報である。** 決めた時点の記録なので、今のアーキテクチャの正としては参照しない。
  今どうなっているかはコードを見る。
- 背景の事実は、PRD・Product Spec へのリンクと、今の実装を示すコードへのリンクで示す。
  提案書は引用しない。
- 見出しに英語（Context、Decision など）を併記しない。

## テンプレート

```markdown
# NNNN. タイトル（決定を一文で）

- Status: 承認済み | 提案中 | 置換済み(→ NNNN)
- 日付: YYYY-MM-DD

## 背景

今の作りと、この決定が必要になった経緯。決定が依存する前提もここに書く。（必須）

## 課題

既存の作りを改めるなら「課題は、〜である。」、新しく作るなら「〜を決める必要がある。」の一文。（必須）

## 決定

どの選択肢を採用したか。手順やパラメータは書かない。（必須）

## 理由

なぜその選択肢を選んだか。無ければ「特に理由はない」。（必須）

## 検討した代替案

決定者が見て採用しなかった案と、その理由。無ければ「比べていない」。（必須）

## 結果

この決定によって生じる利点、欠点、残るリスク、やるべきこと。この決定から自動的に決まること。（任意）
```
