# ADR の書式と書き方

ADR を書く前に読む。

## セクション

次の 6 つのセクションを、この順に置く。結果を除く 5 つが必須である。

| セクション | 書くこと | 必須 |
|---|---|---|
| 背景 | 今の作りと、この決定が必要になった経緯。決定が依存する前提もここ | 必須 |
| 課題 | 冒頭に「課題は、〜である。」の一文。続けて、なぜそれが問題かを数行 | 必須 |
| 決定 | どの選択肢を採用したか | 必須 |
| 理由 | なぜその選択肢を選んだか | 必須 |
| 検討した代替案 | 採用しなかった選択肢と、採用しなかった理由 | 必須 |
| 結果 | この決定によって生じる利点、欠点、やるべきこと | 任意 |

**書く条件の 3 つ（課題・理由・代替案）に、それぞれ専用のセクションを与えている。** 条件に挙げたものが
ほかのセクションに同居すると、埋もれて読み飛ばされ、書けていないことにも気づけない。

- **理由を「決定」の中に書かない。** 何を決めたかはコードを読めばわかる。なぜそれを選んだかは、この文書に
  しか残らない。同居させると、決定の説明文に埋もれ、あとから覆してよいかを判断する人が根拠を拾えない。
- **課題を「背景」の中に書かない。** 背景は事実の列挙で長くなるので、同居させると課題が本文のどこかに
  埋まる。課題を独立させると、書けていない ADR が見ただけで分かる。

**見出しに英語を併記しない。** `## 背景 (Context)` のように添えると、「検討した代替案」のように
対応する英語が一通りに決まらないセクションが必ず出て、併記のあるセクションとないセクションが混ざる。

タイトルは `# NNNN. <決定を一文で>` にする。課題ではなく、決定を書く。

frontmatter は置かない。Status と日付は、タイトルの直下に箇条書きで書く（テンプレートを参照）。

## 背景

- 今の作りと、この決定が必要になった経緯を書く。事実の示し方は次節に従う。
- **決定が依存する前提もここに書く。** 依存する設定、効いている制約、この決定が及ばない範囲が
  これにあたる（`reasons.md` の「評価の結果を ADR に書くとき」）。
- **課題はここに書かない。** 課題は次のセクションに独立して置く。

## 課題

- **冒頭に「課題は、〜である。」の一文を置く。** 続けて、なぜそれが問題かを数行書いてよい（症状、
  困っている場面）。一文を先頭に置くのは、読み手が最初の 1 行で課題を受け取れるようにするためである。
- **課題を決定の言い換えにしない。** 「X を採用する」という決定に対して「X を採用していないことが課題」と
  書くと、課題の形をした決定ができる。問うのは「今の作りの何が問題か」である。それに答えられないなら、
  ADR にしない（`SKILL.md` の「書く条件」）。
- **要求を課題として書かない。** 「操作の記録を残す必要がある」は要求で、PRD にある。課題は、その要求を
  今の作りでは満たせない理由、または満たし方が一通りに決まらない理由である。

## 背景の事実は 2 つで示す

背景に事実を書くときは、次の 2 つだけを使う。

1. **ADR が必要になった背景としての、PRD・Product Spec へのリンク。** 何を作るかを決めた文書である。
2. **今の実装の事実を示すコードへのリンク。** パスと、指している関数・設定の名前まで書く。

**リンクを張る前に、コードで事実を確かめる。** 「たぶんこうなっている」で張ったリンクは、読み手が開いた
時点で ADR 全体の信用を落とす。背景が怪しければ、課題も理由も疑われる。

**この 2 つで示せない事実が要るときは、落とすか、出どころを明記して書く。** 黙って混ぜない。ユーザーの口頭の
申告、まだ導入していないツールの挙動、Design Doc や議事録にしかない記述がこれにあたる。出どころを明記して
書いたものは、報告の確認事項に送る。コードで確かめられる事実を、この抜け道で代えない。

### 提案書を引用しない

提案書、見積り、営業資料を決定の根拠にしない。提案書のどこに書いてあるかを示すだけで済ませない。

提案書は「何を作るか」を決めた文書ではない。骨子が通っても細部は変わるので、決定の根拠にならない。
引用だけが書かれた ADR は、読み手に何も伝えない。**この ADR の中だけで情報を完結させるか、
PRD・Product Spec を参照するか、どちらかにする。**

## 1 本に 1 つの課題

課題が 2 つ混ざったら、ADR を 2 本に分ける。判定は、**選択肢の構造で決める。**

- **主たる判定**: 挙げた選択肢が、一方の課題にだけ効く案と、他方にだけ効く案に分かれるか。分かれるなら 2 課題。
  どの案も両方に効くなら、症状が 2 つ見えていても原因は 1 つなので 1 課題である。
- 補助: 「課題は、〜である。」の一文に「かつ」「また」「および」が入る。ただし**これだけで分けない。**
  一文を書き直せば消えてしまうので、文面を直して回避したことにならないか、主たる判定で確かめる。

混ざったままだと、どの代替案がどの課題への答えなのかが読めなくなり、片方の決定だけを覆すこともできない。

## 決定

- 採用した選択肢を書く。実現方法（鍵の管理、呼び出しの手順、検証の流れ）は書かない。それは Design Doc の仕事である。
- **移す対象の 1 文に原則が同居しているときは、選択肢が立つ部分だけを決定文にし、原則の部分は背景の前提に落とす。**
  （「専用 DB ではなく本番 DB から、サーバー経由で読む」なら、決定は「専用 DB ではなく本番 DB から読む」。
  「サーバー経由で」は選択肢が立たないので背景へ）
- **当たり前の原則を決定に混ぜない。** 「最小権限で絞る」「要るものだけを返す」は選んだ結果ではないので、
  決定から外す（`SKILL.md` の「条件を満たさないものの行き先」）。混ざっていると、ADR が何を決めたのかがぼやける。

## 理由

- なぜその選択肢を選んだかを書く。集め方と評価の仕方は `reasons.md` にある。
- **理由が取れていないときは、空欄にも推測にもしない。**「未確認」と書き、何をすれば確かめられるかを添える。
  **相手は役割で書く**（「運用コンソールの依頼者」「情報システム」）。ADR の読み手は依頼者とは限らないので、
  「ユーザー」と書かない
  （`SKILL.md` の「満たさないのか、まだ確かめられないのか」）。必須の項目で材料が取れないことは起きるので、
  そのときの書き方を決めておく。空欄だと書き忘れと区別できず、推測だとユーザーの判断として読まれる。

## 検討した代替案

- 採用しなかった選択肢ごとに、**案の中身と、採用しなかった理由**を書く。中身だけで終わらせない。
  理由のない代替案の列挙は、検討したという体裁を作るだけで、読み手に判断材料を与えない。
- **理由の出どころを 3 段に分ける。** 2 段目があることを忘れると、書けるものを「未確認」にしてしまう。

  | 出どころ | 書き方 |
  |---|---|
  | ユーザーが述べた | そのまま書く |
  | ユーザーの発話から一意に導ける | 書く。導いたことと導出元を添える（「採用理由（運用の対象を増やさない）の裏返しとして」） |
  | 書き手の推測 | 書かない。「未確認（誰に何を聞くか）」とする |

- 推奨したときに自分が挙げた短所を、ユーザーが採用しなかった理由として流用しない（`reasons.md`）。
  これは 3 段目の推測であって、2 段目の導出ではない。
- **本文に載せるのは、ユーザーが挙げた案と、ユーザーに示して採否をもらった案だけである。** **上流の文書が
  名指しで挙げている案（「X ではなく Y にする」の X）も、ユーザーが挙げた案として扱う。** 理由を上流の文書で
  埋めてはいけないのとは別で、案がそこに挙がっているという事実は、文書から読み取れる。 書き手が思い
  ついた案は、まずユーザーに示す。返事が無いうちは本文に載せず、報告に残す。ユーザーが検討していない案を
  「検討した代替案」に並べると、検討の記録が実際より多く見える。
- **採用しなかった理由が取れていない案は、「未確認」と書いて残す。** 案ごとに書くので、1 案だけ取れて
  いないこともある。取れた案の理由で埋めない。並べた利点と欠点は選んでもらうための材料であって、
  ユーザーが述べた理由ではないので、その区別が読み手に分かるように書く。
- 比較にならないほど明らかに劣る案を並べて水増ししない。

## 結果

任意のセクション。置くなら、次を書く。

- この決定によって生じる利点、欠点
- この決定から派生してやるべきこと
- **この決定から自動的に決まること**（選択肢がないので、それ自体を別の ADR にしない）

## 言葉

- **抽象的な一般用語で、何を指すかをぼかさない。**「範囲」「適切に」「十分な」「など」は、読み手が
  別のものを思い浮かべる。何を指すかを書く。

  | ぼかした書き方 | 具体的な書き方 |
  |---|---|
  | 社員が見られる範囲を絞る | 社員が見られるデータの種類（文字起こし・要約文）と期間（作成から 1 週間以内）を絞る |
  | 適切に記録する | 誰がどのデータを開いたかを、書き換えできない形で記録する |

- **動詞を正確に選ぶ。** 入力から答えを導くのは「判断する」、方針を定めるのが「決める」である
  （「どの社員の操作かを判断する」。「決める」ではない）。ADR の中で「決める」は決定そのものを指す語なので、
  処理の説明に使うと、どこまでが決定なのかが分からなくなる。
- 新しく語を作らない。リポジトリに `GLOSSARY.md` があれば、そこの語に合わせる（`dev-doc-writing` スキル）。
- **ユーザーの言葉のまま置いている理由は、この節の対象外とする。** 具体化した案はユーザーに返し、返事を
  もらってから書き換える（`reasons.md`）。書き手が勝手に具体化すると、ユーザーが述べていない判断が
  ユーザーの判断として残る。
