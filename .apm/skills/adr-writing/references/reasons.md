# 理由の集め方と評価

理由を扱うときに読む。聞く前と、受け取ったあとの両方で読む。返事をもらえなかったときも読む。

## 理由はユーザーに聞く

ADR の理由は、ユーザーの判断である。上流の文書、提案書、AI の推測で埋めない。

- **聞いたうえで理由が無いと分かったなら、ADR を書かずに保留する。**「理由はまだ記録していない」とだけ
  書いた ADR は、`SKILL.md` の「書く条件」を満たしていない。理由の無い決定を記録に残しても、あとから
  読む人は覆してよいかを判断できず、記録として役に立たない。
- **まだ聞けていないだけなら、違う。** Status を `提案中` にして書き、理由は「未確認」として、誰に何を
  聞くのかを添える（`SKILL.md` の「満たさないのか、まだ確かめられないのか」）。聞けば答えのあることを、
  聞かずに捨ててはいけない。
- AI が背景の事実から導いて足した理由は、決定の理由として書く前にユーザーの確認を求める。導いた理由は、
  ユーザーが実際に重視したものと違っていることがある。

## 受け取った理由は、写さずに評価する

ユーザーが述べた理由をそのままセクションに写すと、ADR の質は、ユーザーがその場で書いた一言の質にとどまる。
ユーザーは理由を短く言うことが多く、前提は頭の中にある。ADR の読み手にはその前提がわからない。

次の 5 点を見て、気づいたことをユーザーに返す。返すのは評価であって、書き換えの指示ではない。
決めるのはユーザーである。

### 1. 前提は正しいか。読み手に誤読されないか

理由に含まれる前提を取り出し、**その言葉のまま読んだ人が何を受け取るか**を確かめる。

**例**: 「クライアント証明書は、サービス側が業界ガイドラインに準拠するために入れた」という理由は、
そのままでは「社内コンソールにはガイドラインが関係ない」と受け取られてしまう。ガイドラインが求めるのは
認証・アクセス制御・記録であって、証明書そのものではない。そう書き直すと、理由が成り立つ。

### 2. 比べる相手は適切か

「十分」「問題ない」「過剰」は、比べる相手を決めないと意味を持たない。相手が決まっていなければ、
何と比べたのかを聞く。

**例**: 「一般のアプリと比べて十分」ではなく、「医療情報を扱うコンソールとして十分」と比べる。

### 3. 決定によって残るリスクは何か。それをどう小さくするか

選んだ選択肢でも消えないリスクを書く。書かないと、あとから読む人は「検討されていない」と受け取り、
同じ議論をやり直すことになる。

**例**: 端末を絞らないと、盗まれたセッションが別の端末から使える。その被害は、権限を絞ることと
操作の記録で小さくする。

### 4. 理由を突き詰めると、もっとよい選択肢がないか

ユーザーの理由を前提として突き詰めると、選択肢の表に無かった案が出ることがある。出たら示す。

**例**: 「1 つのミスが致命傷になる」という理由を突き詰めると、アプリの中でログインを実装するより、
認証を前段のプロキシに任せるほうがよい。アプリの実装ミスが認証に影響しなくなる。

この問いは、選択肢の表を作り直すことを意味する。手順 2 に戻ってよい。理由から出てきた案のほうが、
最初に並べた案より筋が通っていることはよくある。

### 5. ADR に前提として書くべきことは何か

決定が依存している設定、検証の手順の要点、決定の及ばない範囲を挙げる。決定そのものではないが、
これが無いと、あとから読む人が決定を正しく実装できない。

**例**: ドメインの制限はサーバー側で署名と一緒に確かめる、安全性は 2 段階認証の設定に依存する、
停止前からあるセッションは停止後も残る。

## 評価の結果を ADR に書くとき

**先にユーザーへ返し、返事を待たずに書いてよい範囲だけ書く。** 評価は提案なので、採るかどうかを決めるのは
ユーザーである。一方、返事を待って何も書かないと、評価したこと自体が残らない。そこで中身で分ける。

| 中身 | 確認前に書いてよいか |
|---|---|
| 事実、残るリスク、決定が依存する前提 | 書く（**事実と前提は「背景」、残るリスクは「結果」**）。確認がまだであることを報告に挙げる。**理由そのものが未確認の回でも書く**（事実はユーザーの判断に依存しない）。ただし**リスクを小さくする手立ては書かない** — 手立ては選択であって事実ではないので、返事をもらってから書く |
| 書き直した前提、比べる相手を正した理由 | **書かない。** 理由はユーザーの判断なので、返事をもらってから書く。それまでは受け取った言葉のまま置く。**評価を返したことの注記も本文に書かない** — 残すのは報告だけにする |
| 突き詰めて出た新しい選択肢 | 書かない。選択肢の表に足して、ユーザーに示す（`norms.md` の「検討した代替案」） |

**派生作業と手立ては別である。** 決定を実施すれば必ずやることは、選択の余地がないので「結果」に書いてよい
（「`Taskfile.yml` の 2 つのタスクを書き換える」）。やるかやらないかに選択の余地があるものは手立てなので、
返事をもらってから書く（「レプリカを立てて読み取りを逃がす」）。

返事が来たら、次の対応で書く。

| 評価で出たもの | 書くセクション |
|---|---|
| 書き直した前提、比べる相手を正した理由 | 理由 |
| 残るリスクを小さくする手立て | 結果（リスク自体は確認前に書いてある） |
| 決定が依存する設定、検証の要点、及ばない範囲 | 背景（前提として）。この決定から生じるものなら結果 |
| 突き詰めて出た選択肢を、ユーザーが採用しなかったとき | 検討した代替案 |
| 突き詰めて出た選択肢を、ユーザーが採用したとき | 決定（最初の案は検討した代替案へ移す） |
