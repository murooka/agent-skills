# adr-writing

AI エージェントに ADR（アーキテクチャ決定記録）を書かせるスキル。

## 解決する課題

ADR が読まれるのは、決定を変えたくなったとき、同じ議論が繰り返されそうなとき、背景を知らない人や AI が既存の作りに
手を入れるときである。読み手は「今も守るべきか、変えてよいか」を判断したい。

AI に書かせると、この役に立たない ADR が 2 種類できる。

- **決定でないものの ADR。** 要求、制約、当たり前の原則も「〜する」と書けるので、文もセクションも成り立ってしまう。
- **人が判断していないことを書いた ADR。** 本人が言っていない理由は、未来の読み手に存在しない前提を守らせる。
  検討していない案が載ると、「知らなかった」が「知っていて落とした」に変わる。

一方で、形式を厳しくしすぎると、残すべき決定が落ちる。比べずに決めた技術選定も、「特に理由はない」と分かれば
後から気にせず変えられる。

## アプローチ

- **対象は、比べたかどうかではなく、ほかの選択もできたか、後から変えにくいかで決める。**
  選ぶ余地がないものや、すぐ戻せるものは、捨てずに行き先を示す。
- **「無い」と「聞けていない」を分けて書く。** 理由は「特に理由はない」、代替案は「比べていない」と書ける。
  まだ聞けていないことは「未確認」とする。どちらも推測で埋めない。
- **候補を決定者に見せてから記録する。** AI が挙げた案でも、見せれば人は判断する。
  その案は「使ったことがない」という理由でも代替案として残す。案を見せずに本文へ載せることはしない。
- **提案への同意は、決定者の判断として記録する。** 同意済みのことは聞き直さず、提案に同意したと分かる形で書く。
- **受け取った採用理由を、写さずに評価する。** 前提、比べる相手、残るリスク、もっとよい案、崩れたら見直す前提の
  5 点を返し、決めるのは決定者に委ねる。
- **課題は場面で書き分ける。** 既存の作りを改めるなら今の作りの問題を、新しく作るなら何を決める必要があるかを書く。
- **理由、代替案、課題をそれぞれ独立したセクションにする。**
- **背景の事実は、PRD・Product Spec へのリンクと、コードへのリンクで示す。** 提案書は根拠にしない。

## 使い方

```
「セッションの持ち方を Redis に変える決定を ADR に残して」
「バックエンドを Go にしたので記録を残して。特に比べてはいない」
「PRD の技術的要求 TR-3 と TR-4 を ADR の形にして」
「このリポジトリに ADR の置き場を作って」
```

## 依存

なし。PRD や Design Doc も扱うなら `dev-doc-writing` を一緒に入れる。

```bash
apm install murooka/agent-skills --skill adr-writing --skill dev-doc-writing
```
