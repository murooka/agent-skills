# adr-writing

AI エージェントに ADR（アーキテクチャ決定記録）を書かせるスキル。

## 解決する課題

AI に ADR を書かせると、**課題のない ADR が増える。** 要求（何を満たすべきか）、制約（外部から課されるもの）、
当たり前の原則（最小権限など）は、どれも「〜する」という決定の形に書き換えられる。書き換えたものは文として
成り立ち、セクションも埋まるので、読み手が「これは何を決めているのか」と問うまで誰も気づけない。

課題が曖昧でも実現方法の設計は先へ進められるため、進んだこと自体が「決めるべきことは決まった」という錯覚を
生む。前提が崩れた時点で、積み上げた設計をまとめて捨てることになる。

理由の扱いもおろそかになりやすい。セクションを分けないと理由は「決定」の説明に埋もれ、上流の文書（提案書など）の引用で
済ませると、ADR の中には何も残らない。ユーザーが述べた理由をそのまま写すと、ADR の質は、ユーザーが
その場で書いた一言の質にとどまる。

## アプローチ

- **書く前に条件を確かめる。** 課題（一文で言えるか）、採用しなかった選択肢（1 つ以上と理由）、理由の 3 つが
  書けるときだけ ADR にする。満たさないものは捨てずに行き先（PRD、Design Doc、ほかの ADR の「結果」）を示す。
  PRD から移した要求は、ADR をやめるときに PRD へ戻す。
- **課題と選択肢が決まるまで、実現方法を進めない。** ADR は「どの選択肢を選んだか」まで。「どう作るか」は
  Design Doc に任せる。
- **課題と理由をそれぞれ独立したセクションにする。** 書く条件に挙げたものを、背景や決定に同居させない。
  何を決めたかはコードを読めばわかるが、なぜ選んだかはこの文書にしか残らない。課題が背景に埋もれると、
  課題のない ADR が書かれていることに誰も気づけない。
- **受け取った理由を、写さずに評価する。** 前提は正しいか、比べる相手は適切か、残るリスクは何か、
  突き詰めるともっとよい選択肢がないか、前提として書くべきことは何か——の 5 点を返し、決めるのはユーザーに委ねる。
- **背景の事実は、PRD・Product Spec へのリンクと、コードへのリンクだけで示す。** 提案書は引用しない。
  リンクを張る前にコードで事実を確かめる。

## 使い方

```
「セッションの持ち方を Redis に変える決定を ADR に残して」
「PRD の技術的要求 TR-3 と TR-4 を ADR の形にして」
「このリポジトリに ADR の置き場を作って」
```

## 依存

なし。PRD や Design Doc も扱うなら `dev-doc-writing` を一緒に入れる。

```bash
apm install murooka/agent-skills --skill adr-writing --skill dev-doc-writing
```
