# テストコードの規範: 汚染源別の禁止規則と記述規範

テストの良し悪しは「テストケースと期待値が契約(最終仕様)だけから導出されているか」で判定する。契約以外の導出元(汚染源)は 3 つあり、それぞれに禁止規則と判定質問がある。

## 目次

- 汚染源 1: 実装
- 汚染源 2: 会話・修正履歴
- 汚染源 3: 契約外の観測可能な細部
- 通常コーディング規範の上書き(DAMP)
- 記述構造

## 汚染源 1: 実装

テストケースの列挙と期待値の導出に実装を使わない。

- ケースは契約条項(仕様・doc・シグネチャ・型)から列挙する。実装の分岐・早期リターン・エラーパスを写して列挙しない。
- 期待値は実装を読まずに導出できる値であること。実装を頭の中で実行して逆算した期待値は、実装のバグをバグごと固定化する(トートロジー)。
- 期待値の計算にプロダクションコードの定数・関数・フォーマッタを再利用しない。実装が間違っていてもテストが通ってしまう。期待値は独立に手で導出したリテラルを書く。
- 内部の呼び出し回数・呼び出し順序を verify しない。相互作用の検証が許されるのは、その相互作用自体が契約であるときだけ(例: 「メールを送る」という外部から観測される副作用)。「内部でリポジトリを 2 回呼ぶ」は契約ではない。
- 同一条項・同一同値類の入力違いでテストを増やさない。検出力は増えず、変更コストだけが増える。
- 既存テストの期待値を新しいテストの期待値の根拠にしない。既存テストは契約源ではなく、それ自体が規範違反(契約外の文言の固定など)を含み得る。既存テストが契約から導出できない値を assert しているのを見つけたら、それは報告対象であり、踏襲してよい根拠ではない。

**判定質問**: 「このテストが落ちるのは、どの約束が破られたときか?」
答えが「実装がこう書かれているという事実が変わったとき」にしかならないなら、それは change-detector テストであり、書かない(既存なら削除を提案する)。

## 汚染源 2: 会話・修正履歴

テストは最終状態の契約からのみ導出する。そこに至る開発過程(レビュー指摘、修正依頼、会話)を検証しない。

- レビュー指摘に対応した後は、指摘を仕様の変更として吸収し、テストは変更後の仕様から導出し直す。指摘そのもの(新旧の遷移についての文)をテスト化しない。
- 「〜が含まれない」「〜しない」という不在の assert は、契約が明示的に不在を約束しているときだけ許可する(例: 「レスポンスにパスワードハッシュを含めない」というセキュリティ・互換性要件)。
- その概念が最終仕様に一切登場しないなら、その概念についてのテストは書かない。

**判定質問**: 「この assert が参照する概念は、最終仕様に登場するか?」
登場しないなら、それは会話履歴のテストであり、書かない。

## 汚染源 3: 契約外の観測可能な細部

観測できることと約束されていることは違う。assert してよいのは約束だけ。

- エラーの検証はエラーコード・型・構造化フィールドで行う。メッセージ全文の等価比較は禁止。メッセージの内容自体が契約である場合(「違反したフィールド名を含む」を約束している等)のみ、約束された最小限の部分一致で検証する。
- 順序を約束していないコレクションの順序を assert しない。ソートまたは集合として比較する。
- ログ出力を assert しない(ログ自体が契約である場合を除く)。
- 出力全体の等価比較(スナップショット含む)は、全体の形が契約であるときだけ許可する(例: 公開 API のレスポンススキーマ)。

## 通常コーディング規範の上書き(DAMP)

以下の通常規範はテストコードには適用しない。「良いコード」の習慣が最も混入しやすい箇所なので、明示的に上書きする。

| 通常規範 | テストコードでは |
|---|---|
| DRY(重複排除) | 適用しない。テスト間の重複は削除対象ではない。共通化の提案もしない |
| マジックナンバーの定数化 | 適用しない。期待値はリテラルで書く。複数テストで同じ値が重複してよい |
| ヘルパー関数への抽出 | 期待値に影響する入力はテスト本体に残す。影響しない boilerplate(無関係なフィールドの穴埋め等)だけ隠してよい |
| パラメタライズによる集約 | 同一契約条項の入出力表であるときだけ使う。条項ごとに検証内容が違うなら、名前を持つ別テストに分ける |

基準: **読者がテスト本体だけを読んで「なぜこの期待値になるのか」を追えること。** テストにはテストがないので、目視で正しさを検証できる形を最優先する。

## 記述構造

- AAA(Arrange / Act / Assert)の 3 段構造を保つ。因果(何をしたら何が起きるか)がテスト内で一目で追えること。
- テスト名は仕様文にする(条件と期待結果を含む)。失敗一覧がそのまま仕様書として読める状態が理想。
- 各テスト関数の先頭に、検証する契約条項を 1 行で述べるコメントを必須とする(Python では docstring)。テストとケース表の条項対応はここで示す。
- すべてのアサーションに失敗時メッセージを必須とする(言語・フレームワークがメッセージを渡せる場合)。メッセージは失敗ログだけで「どの約束が破られたか」が分かる内容にする。メッセージを渡せないフレームワークでは、アサーション行の直上コメントで代替する。
- テスト内にロジック(if・ループ・期待値の計算)を書かない。ロジックを持つテストはそれ自体がバグを持ち得る。
- 決定性を守る。時刻・乱数・外部 I/O・実行順序に依存しない。固定できないものは境界で注入して固定する。
