# japanese-proofreading

人間が読むための日本語 — コードコメント、docstring、README や設計文書、BigQuery のカラム説明 — の添削を、
Gemini (Antigravity CLI の `agy`) に委譲するスキル。

## 解決する課題

エージェントが書く日本語は、2 つの方向で読みにくくなる。

1 つは圧縮。情報を詰め込むほど助詞が落ちて名詞が数珠つなぎになり、条件と動作と例外が一文に同居し、読点がないので係り受けが読めない。

```
// 認証トークンの有効期限切れ時に再取得を試行するが、リトライ上限到達時は例外送出せず nil を返却する仕様のため呼び出し側での nil チェック必須
```

もう 1 つは語の選び方と構成。生成された文章では、その分野で定着した語が避けられ（「バージョン」が「版」、「ツール」が「道具」、
「ディレクトリ」が「置き場」）、否定や前置きから入って主旨が後ろに回る。意味は通るので、読み返しても引っかかりにくい。

厄介なのは、書いた本人（エージェント）がこれを読み返しても意味を復元できてしまうので、読みにくさを検知できないこと。
自己添削では直らない。一方で Gemini 3.8 Flash は日本語の文章力が高く、この 2 つを直すのが得意である。
どちらを重点的に見るかは、原文の出自（`--origin ai` / `human`）で切り替える。

## アプローチ

**文章を直すのは Gemini、事実を守るのは Claude** という分担にする。

Claude が対象の日本語をファイルから集めて `agy` へ渡し、返ってきた添削案を、対象のコードやスキーマに照らして
1 件ずつ検証してから反映する。語調を整える過程で条件の限定（「5xx のうち **503 のみ**」の「のみ」）が落ちたり、
固有の用語が一般語に置き換わったりするのを、コードを読める側が検知する。

**Claude が却下できるのは、原文の主張が変わる案と、依頼で渡した制約（長さ、書式、表記、文体）に反する案だけ。**
どちらの言い回しが読みやすいかは Gemini の判断に従う。ここを自分の語感で覆すと、Claude の日本語に寄せ直すことになり、
委譲した意味がなくなる。却下した案は、何がどう変わるのかを添えてユーザーへ報告する。

Gemini は、読み手の理解を助ける補足（「ログイン試行回数の上限」に「レートリミット」、「利用停止中」に `status: suspended`）を
足してよい。足したものは申告させ、Claude が根拠を確かめる。申告は漏れるので、インラインコードと数値の増減はスクリプトが
機械的に数え、Claude はそれも突き合わせる。根拠を確かめられない補足は、その部分だけ落とす。

反映するのは、渡した箇所だけ。ある箇所で採用された言い換えを、ほかの箇所へ検索置換で広げない。同じ語でも文脈で適した語は変わり、
Gemini はそれを見て使い分けている。ほかの箇所もそろえたいなら、その箇所を渡して添削させる。

直す範囲は Claude が決め、原文はテキストとして渡す。そのうえで、原文の周りの文脈（コメントが指す関数、カラムの定義）は
Gemini 自身に読ませる。`agy` は `-p` では、`--add-dir` で加えたディレクトリの中だけ読み取りを許可し、書き込みと外の読み取りを
拒否するので、読ませる範囲をディレクトリ単位で絞れる。周りを読むことで意味の取り違えが減り、原文と実装の食い違いにも気付ける。
ただし `.gitignore` の対象も読まれうるので、読ませるディレクトリは原文を含むなるべく狭い範囲にする。

同梱の `scripts/proofread.py` が呼び出しを引き受ける。複数箇所を 1 回の呼び出しにまとめ（10 件で 40 秒弱）、
構造化出力で id と添削文を対応づけ、間欠的に起きる構造化出力の欠落を再試行とフォールバックで吸収する。

## 使い方

```
「このコメントの日本語を添削して」
「README の第 2 節が硬いので読みやすくして」
「このテーブルのカラム説明をまとめて整えて」
```

明示的に依頼されたときだけ起動する。コメントの要否や過不足は別の論点で、`code-comment-style` が扱う。

## 依存

- [Antigravity CLI](https://antigravity.google) (`agy`) がインストール済みで、`gemini-3.8-flash-*` が利用可能なこと
- Python 3（標準ライブラリのみ）
