# japanese-proofreading

AI が書いた日本語 — コードコメント、docstring、README や設計文書、terraform や dbt に書くカラム説明 — の推敲を、
Gemini (Antigravity CLI の `agy`) に委譲するスキル。

## 解決する課題

AI に文章を書かせると、人間には読みにくい日本語が出てくる。癖は 4 つある。

- **その分野の技術者が使わない語を選ぶ。** 「バージョン」が「版」に、「ツール」が「道具」になる。英語でも同じ傾向があり、"claudish" と呼ばれている
- **構成が独特である。** 否定や前置きから入る、不要な比較をする、結論が後ろに回る
- **どの段落も同じ重さになる。** 人間が書くような「結論は短く強く、理由はフラットに詳しく」という書き分けがなく、どこを重点的に読めばよいか分からない
- **量が多い。** 文脈をすべて文章に残そうとする

最初はこれを規則で捕まえようとした。しかし文書の形式ごとに規則が変わるうえ、規則を足すと今度は別のところが崩れる。
**「良い文章」は規則の集合ではない**ので、この方向には際限がない。

一方、Gemini 3.8 Flash は日本語の文章力が高く、ファイルを渡して「推敲して」とだけ言うと、全体の可読性が上がる。
このスキルは、その挙動をそのまま使う。

## アプローチ

**文章を直すのは Gemini、主張と事実を守るのは Claude** という分担にする。

Gemini には、推敲してほしいファイルと範囲を渡し、**その範囲をまるごと書き換えてもらう**。指示は「推敲して」だけで、
直し方は指定しない。文章を切り出して渡すと、節をまたぐ構成や段落どうしのつながりを直せなくなるため、ファイルごと渡す。

**Gemini は、背景を知らない第三者として使う。** Claude はその文章を書くまでのやりとりを大量に持っていて、
書かれていない前提を補って読んでしまう。前提を持たない読み手に読ませることに、この委譲の意味がある。

Claude は書き換わったファイルを読み、**不変条件が守られているか**と**事実と食い違っていないか**だけを確かめ、
外れた箇所だけを直す。**変更を全面的に拒否しない。** 「原文と違う」「自分ならこう書かない」は直す理由にならず、
直すのは「<出どころ>は X と言っているが、書き換え後は Y と言っている」を出典付きで書けるときに限る。

どこまで書き換えてよいかは、依頼ごとに 1 つの目盛りで決める。語と接続詞だけ（`sentences`）、見出しを保って節の中は
自由（`headings`、既定）、結論だけ保って論の組み立ては自由（`conclusion`）、事実だけ保って内容の取捨も自由（`facts`）。
事実はどの段階でも凍結する。

## 安全のしくみ

`agy` は `--mode accept-edits` で編集を自動承認し、`--add-dir` で加えたディレクトリの中だけを読み書きできる。
外は読み取りも拒否される。そこで、対象ファイルを含むなるべく狭いディレクトリだけを渡す。

それでも同じディレクトリの別ファイルは書き換えられるので、同梱の `scripts/proofread.py` が実行の前後でディレクトリ
全体のハッシュを比べ、対象以外が変わっていれば知らせる。控えも取るので、気に入らなければ丸ごと戻せる。

あわせて、見出しの一致（`sentences` なら段落数と文数も）と、インラインコード・数値の増減を機械的に数える。
機械で決まることに読解を使わないためである。

## 使い方

```
「この設計文書を推敲して」
「README の第 2 節が硬いので読みやすくして」
「このカラム説明をまとめて整えて。見出しは変えないで」
```

明示的に依頼されたときだけ起動する。コメントの要否や過不足は別の論点で、`code-comment-style` が扱う。

## 依存

- [Antigravity CLI](https://antigravity.google) (`agy`) がインストール済みで、`gemini-3.8-flash-*` が利用可能なこと
- Python 3（標準ライブラリのみで動作）
