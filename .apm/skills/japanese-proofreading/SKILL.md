# 日本語の推敲を Gemini に委譲する

日本語の文章を読みやすく直すよう依頼されたら、この手順に従う。

## なぜ委譲するのか

AI が書いた日本語には、次の癖が出る。

- その分野の技術者が使わない語に言い換えられている（「バージョン」が「版」、「ツール」が「道具」）
- 構成が独特である。否定や前置きから入る、不要な比較をする、結論が後ろに回る
- どの段落も同じ重さで書かれていて、読み手がどこを重点的に読めばよいか分からない
- 文脈をすべて書き残そうとして、量が多い

**これらは規則にできない。** 「否定から入らない」のような規則を足しても、次は別のところが崩れる。文章の良し悪しは
規則の集合ではないので、規則を増やす方向に進むと際限がなくなる。だから**指示は「推敲して」だけにして、直し方は Gemini に任せる**。

**Gemini は、背景を知らない第三者として使う。** 自分はこの文章を書くまでのやりとりを大量に持っていて、
書かれていない前提を補って読んでしまう。だから自分では読みにくさに気付けない。前提を持たない読み手として
Gemini に読ませることに、この委譲の意味がある。自分の語感で添削文を原文へ寄せ直すと、その意味がなくなる。

## 分担

**文章を直すのは Gemini、主張と事実を守るのは自分。**

Gemini は対象のファイルを直接書き換える。自分は書き換わったファイルを読み、**不変条件（次節）が守られているか**と、
**事実と食い違っていないか**だけを確かめる。外れている箇所があれば、**そこだけ**直す。

**変更を全面的に拒否しない。** 原文に戻すのは、事実と食い違ったときの手段の 1 つでしかない。
「原文と違う」「原文に無い」「自分ならこう書かない」は、直す理由にならない。

## 不変条件 — どこまで書き換えてよいか

依頼ごとに変えるのは、この目盛りだけである。厳しい順に並び、上の段は下の段が保つものをすべて保つ。

| 段階 | 保つもの | 変えてよいもの | 使う場面 |
| --- | --- | --- | --- |
| `sentences` | 文の並びと切り方、段落、見出し、主張、事実 | 語の選び方、接続詞、助詞、読点 | 構造は動かさず、語と接続だけ直したいとき |
| `headings`（既定） | 見出しの文言と並び、各節が扱う主張、事実 | 節の中の段落構成、文の切り方と順序、語、冗長の削り | 書式の決まった文書（Design Doc など）。**指定がなければこれ** |
| `conclusion` | 最終的な主張、事実 | 見出し、節の並び、論点の順序と取捨、構成、文、語 | 提案書のように、結論は動かさず組み立てを直したいとき |
| `facts` | 事実だけ | 何を書くか、どこまで書くか、順序、構成、文、語 | コメントのように、書く内容ごと見直してよいとき |

**事実はどの段階でも凍結する。**

段階は依頼の文言から決める。明示されていなければ `headings` にする。

| 依頼の言い方 | 段階 |
| --- | --- |
| 「構造は変えずに」「言い回しだけ」「単語の選び方だけ」 | `sentences` |
| 「見出しは変えないで」「フォーマットが決まっている」、**指定なし** | `headings` |
| 「結論は変えずに、組み立ては直してよい」「論の運びを見て」 | `conclusion` |
| 「内容ごと見直してよい」「書くべきことから考え直して」 | `facts` |

どれを使ったかは、手順 4 の報告に必ず書く。ユーザーが選び直せるようにするためである。

## 手順

### 1. 対象と範囲を決める

推敲するファイルと、その中の行範囲を決める。**文章を切り出して渡すのではなく、ファイルと範囲を渡す。**
節をまたぐ構成や、段落どうしのつながりは、範囲をまるごと渡さないと直せない。

- ファイルの一部だけを直したいときは `--range 12-48` で行範囲を渡す。省略するとファイル全体になる
- 複数のファイルをまとめて渡してよい（`--file` を繰り返す）。同じ実行に載せたほうが速い
- **直す必要のない範囲は渡さない。** 結論を動かされたくないなら、その段落を範囲から外すのが、いちばん確実で安い

### 2. 投げる

```bash
python3 <この SKILL.md と同じディレクトリ>/scripts/proofread.py \
  --file /abs/path/to/docs/design.md --preserve headings \
  --context-dir /abs/path/to/docs
```

- **`--context-dir` には、agy に読み書きを許すディレクトリを渡す。** 既定は対象ファイルの共通の親。
  agy はこの中だけを読み書きでき、外は読み取りも拒否される
- **`--context-dir` はなるべく狭くする。** 中の `.env` のような `.gitignore` の対象も読まれうる。
  加えて**書き込みも許すので、同じディレクトリの別ファイルも書き換えられる**。スクリプトが実行の前後で
  ディレクトリ全体のハッシュを比べ、対象以外が変わっていれば `!! 対象以外のファイルが変わった` と出す。
  出たら控えから戻す（控えの場所は実行の最後に出る）
- `--hint` には、ファイルを読んでもわからないことを書く（既存表記、読み手、書かれていない前提）
- `--preserve` は前節の段階。既定は `headings`
- 既定モデルは `gemini-3.8-flash-medium`。**変更がほとんど無く、読み返して納得できないときは
  `--model gemini-3.8-flash-high` で投げ直す**（長文では手を抜いて原文をほぼそのまま返すことがある）
- 失敗したら 1 回だけ自動で投げ直す。それでも `!! 推敲できなかった` が出るときは、`拒否された操作` の名前を見る。
  読ませたいファイルが `--context-dir` の外にある

### 3. 書き換わったファイルを確かめる

スクリプトは、字数・行数の変化と、機械で決まる検査の結果を出す。まず `!!` の行を読む。

| 出るもの | 意味 | すること |
| --- | --- | --- |
| `不変条件に反した` | 見出しが変わった（`sentences` なら段落数・文数も） | その箇所だけ戻すか、段階を 1 つ厳しくして投げ直す |
| `原文に無い記号・数値が増えた` | インラインコードや数値が足された | 1 件ずつ出どころに当たる（下記） |
| `原文にあった記号・数値が消えた` | 事実が落ちた候補 | 原文の側を読んで確かめる |
| `対象以外のファイルが変わった` | 範囲外が書き換えられた | 控えから戻す |

そのうえで本文を読み、**事実と食い違っていないか**だけを確かめる。

**「<出どころ>の<箇所>は X と言っているが、書き換え後は Y と言っている」を、出典（ファイルと行、要求 ID、
スキーマの列、URL）付きで書けるときだけ直す。** 書けないなら、そのまま採用する。

| 直す理由にしない | なぜ |
| --- | --- |
| 原文と違う、原文に無い、原文より強い / 弱い | 推敲とはそういうものである |
| 別の意味にも読めてしまう | 曖昧さの判断は言い回しの領分。実際に別のものを指していると出典で示せるなら、それは食い違いなので直す |
| この文書の定義語ではない、実装寄りの語である | 用語の縛りは `--hint` で先に渡す。渡していない縛りを後から持ち出さない |
| 根拠を確かめられなかった | 確かめられないことと、事実と違うことは別である。数値と識別子だけは例外（次項） |
| 構成が変わった、量が減った | 読みやすさの判断であり、委譲したところである |

事実の出どころは、対象のコード、スキーマ、上流文書、周辺の文書、そして一般に知られている事実である。
**原文は事実の出どころではない。** 原文も誰かが書いた文章で、間違っていることがある。
原文のほうが事実と食い違っているなら、原文にも戻さない（手順 4 で別に報告する）。

**数値・単位・日付・識別子・型名・カラム名・URL だけは、確かめられないものを残さない。** 間違っていたときの
実害が大きく、読み手が正しさを判断できないためである。一方、**一般に知られている事実の補足**（「カード番号は
Stripe が保持する」など）は、食い違いを示せない限り残す。

直すときは、**その箇所だけ**を直す。ほかの変更は活きたままにする。

### 4. 報告する

- 使った不変条件の段階と、そう決めた理由（依頼の文言、または既定）
- 字数と行数の変化、変更が大きかった箇所
- **事実に合わせて直した箇所と、その出典**。「<出どころ>は X と言っているが、書き換え後は Y と言っていた」を書く。黙って直さない
- 控えの場所（気に入らなければ戻せることを伝える）
- 対象以外のファイルが変わっていたら、その旨と戻したこと

**原文の内容そのものが実装と食い違っている**ことに気付いたら、推敲とは別に報告する。
書き換え後を事実に合わせるのは自分の仕事だが、もともと間違っていた説明を正しい説明にするのは文書の改訂であり、
どう直すかはユーザーの指示を待つ。

## 扱わないもの

- **コメントの要否や有無** — そのコメントを書くべきか、足りないコメントは何かは別の論点（`code-comment-style` の領分）
- **英語の文章** — このスキルの指示文は日本語を前提にしている
- **ユーザーへの回答やコミットメッセージ** — 依頼されれば拒む理由はないが、想定している対象ではない
