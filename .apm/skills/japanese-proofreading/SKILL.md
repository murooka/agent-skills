# 日本語の添削を Gemini に委譲する

日本語の文章を読みやすく直すよう依頼されたら、この手順に従う。

## 役割分担

**文章を直すのは Gemini、事実を守るのは自分。** この分担が成立の条件になる。

症状は 2 つあり、原文の出自で出方が変わる。**手早く書いた文章では、情報が圧縮される** — 助詞が落ちて名詞が数珠つなぎになり、
条件と動作と例外が一文に同居する。**生成した文章では、語の選び方と構成が崩れる** — その分野で定着した語を避けた言い換え
(「バージョン」を「版」、「ツール」を「道具」、「ディレクトリ」を「置き場」)が入り、否定や前置きから入って主旨が後ろに回る。

どちらも、自分で読み返すと意味が復元できてしまうので、読みにくさに気付けない。だから文章の判断は Gemini に渡す。

Gemini には、原文の周りのファイル(コメントが指す関数、カラムの定義)を読ませられる。周りを読めば原文の意味を取り違えにくくなるが、
それでも語調を整える過程で条件が反転したり、読んでいないことを断定したりする。**その結果として文書が事実でないことを言い始めるのを
検知するのが自分の仕事**になる。コードとスキーマと上流文書を読めるのは自分だけだからである。

**内容が原文と変わること自体は、問題ではない。** 推敲は言い換えだけの作業ではなく、限定の言い直しも、言葉の足し引きも含む。
Gemini は読み手の理解を助ける補足も足してよいことになっていて、足したものは `note` の「補った:」行に申告される。

ただし、**自分が守るのは事実と、渡した制約だけ**で、言い回しの良し悪しは Gemini の領分になる。
どちらの言い方が読みやすいかを自分の語感で覆し始めると、自分の日本語に添削文を寄せることになり、このスキルを使う意味がなくなる。
原文に寄せ直すのも同じで、原文は守るべきものではない。

## 手順

### 1. 対象を集める

依頼された範囲の日本語を、自分でファイルから読み取る。**どこからどこまでを直すかは自分が決め、原文は `text` に入れて渡す。**
Gemini に読ませるのは、原文の意味を取るための周りの文脈だけで、書き換えの範囲は渡した原文に限る。

項目の切り方で結果が変わる。

**1 項目の単位は、`kind` を 1 つで書ける最大の連続範囲にする。** 形式の制約が途中で変わるなら分け、変わらないならまとめる。
連続範囲とは、原文がファイルの上で途切れずに隣り合っている範囲を指す。関数をまたぐコメントのように離れているものは、
`kind` が同じでも別の項目にする。反映先を `id` で独立に特定できることも条件になる。

分けた項目は、**それぞれ独立に添削される**。項目をまたいで内容を移させない(要約行の一部を本文へ動かす、など)。
移したいなら、それは添削ではなく自分で行う書き直しになる。同じ形式の項目が並んでも、`kind` は項目ごとに書く(共通指定はない)。
書き写す手間で制約が抜けるくらいなら、依頼の JSON をスクリプトで組み立てる。

**1 項目は 2,000 字くらいまでにする。** これを大きく超えると、同じ入力・同じ指示でも、返ってくる書き換えの量が run ごとに振れる
(10,800 字の節を 3 回投げて、書き換えた割合が 10%、15%、20%)。どこに手が入ったかも追いにくい。長い節は `###` の小見出しで割る。割ったぶんは、
`id` を `<節>/<小見出し>` のようにして反映先を特定する。

| 対象 | 切り方 |
| --- | --- |
| 文書・節(README、設計文書) | 節をまるごと 1 項目にする。段落のつながりや語の重複まで直せる。見出し行は `text` に入れない。2,000 字を大きく超える節は、`###` の小見出しで割る |
| docstring(要約行 + 本文) | 要約行と本文で制約が違う(要約行は 1 文 1 行、本文は段落)なら 2 項目に分ける |
| 表のセル、カラム説明 | セルごとに 1 項目。反映先が行ごとに違うので、表をまるごと 1 項目にしない |
| 散在する短文(コメント、カラム説明) | 1 箇所 1 項目。ただし**全項目を 1 回の実行にまとめて渡す** |

スクリプトが項目を塊に分けて並行に投げるので、1 件ずつ実行を繰り返すより速く終わる（10 件で 40 秒程度）。

直したい箇所は、**直す可能性のある範囲をすべて項目にする**。項目にしなかった箇所は、添削の結果がどうであれ手を付けない(手順 5)。
1 箇所の言い換えをほかへ広げる代わりに、その箇所も項目として渡す。

日本語としては読めるが、**内容が実装や定義と合っているかを確かめたい箇所も項目にする**。周辺と突き合わせた食い違いの指摘
(手順 4 の「食い違い:」)は、項目として渡した箇所にしか付かない。読みやすさだけを基準に外すと、その機会も一緒に消える。

### 2. 依頼の JSON を書く

作業用ディレクトリ(scratchpad など、対象リポジトリの外)に項目の配列を書く。ディレクトリ名は実行ごとに一意にする
(`jp-proofread-<日時>-<PID>` など)。使い回すと、別の実行に入力や結果を上書きされる。

```json
[
  {
    "id": "token.go:7",
    "kind": "Go の行コメント(関数直上, 1〜2 行)",
    "text": "// 認証トークンの有効期限切れ時に再取得を試行するが、リトライ上限到達時は…",
    "path": "/abs/path/to/repo/auth/token.go",
    "line": 7,
    "hint": "既存表記は『リトライ』(カタカナ)"
  }
]
```

- `id` — 反映先を自分が特定できる名前(`ファイル:行` でも、カラム名でもよい)。重複は不可
- `text` — 直す日本語だけを入れる。`//` や `#` のように原文と同じ行にある記号は、そのまま含めてよい。
  docstring の `"""` や、行頭のインデント、Markdown の表の `|` のような**囲みは `text` から外し、`kind` に外した旨を書いて、
  反映のときに自分で戻す**。囲みを渡すと、添削文の中で位置や字下げが変わり、反映のときに壊れる。
  戻すときは、**`text` に入れなかった文字を原文のまま 1 文字も変えずに戻す**(要約行が `"""` と同じ行にあったなら、同じ行に戻す)。
  ただし、読みやすさのために折ってあるだけの**物理改行(ハードラップ)は囲みではなく本文の一部**になる。`text` では 1 行につないで渡し、
  反映のときに折り直す。折る幅は原文の最長行に合わせ、**句読点の直後だけで折る**(語の途中では折らない)。
  上限の近くに句読点がないなら、上限を少し超えて 1 行のままにする(語の途中で折ったり、極端に短い行を作ったりするよりよい)。
  ほどいて**行が増えうる対象**(1 行コメントなど)では、増えた行の行頭記号を誰が付けるかを `kind` に書く
  (「2 行目以降も `//` で始める」)。書かずに渡すと、2 行目に記号が付かないまま返る
- `kind` — **守ってほしい形式を書く**。次の 4 つを、対象に当てはまるだけ書く。ここを空にすると、カラム説明が段落に育つ
  - **長さ**(「全角 60 文字以内」)。**数値を書くのは、その数値の出どころがあるときだけ**。出どころは 2 つで、
    ①ユーザーが依頼で指定した値、②リポジトリの中に実在するもの(カラム説明の桁数の仕様、表示幅の決まり、リンタの設定ファイル)。
    どちらもないなら、言語の慣習(PEP 8 の 79 桁など)でも数値にしない。自分で決めた数値を書かない。
    数値が**行の物理的な幅**を指すなら、囲みやインデントを `text` から外した分の桁を引く(4 スペース + `"""` なら 7 桁)。
    カラム説明の文字数のように、文そのものの長さを指す数値なら引かない。
    数値を書かない対象では「既存の行に合わせる」と書く。これは Gemini への目安であって、**手順 4 の却下の根拠にはならない**。
    長さを渡さなかった対象は、反映したあとに幅を測り、伸びた箇所を手順 5 で報告する(却下はしない)。
    測るのは囲みを戻した反映後の行で、比べる相手はその項目の原文の同じ行
  - **行数と改行**(「1 行」「1〜2 行」「表のセルに入るので改行と `|` を使わない」)
  - **文体**(「ですます調」「常体(だ・である調)」)。**直したあとに守ってほしい形を書く。原文の現状を書き写さない**。
    体言止めの羅列が読みにくさの原因なら、「体言止め中心」ではなく「常体(だ・である調)の文で書く」と書く。
    ここを空けると、スクリプトの既定(文体は原文に合わせる。体言止めの有無も含む)が効いて、**羅列は羅列のまま返る**
  - **その書式の規約**(「docstring の要約行は 1 文(PEP 257)」「godoc なので関数名で書き始める」「`"""` とインデントは外してある」)。
    **構造の作り替え**(箇条書きにする、節を分ける、見出しを足す)は、させたくないならここに「しない」と書く。書かないと提案されうる。
    表やカラム説明なら、文末の句点を付けるかも書く。**原文の周りに暗黙にある体裁(句点の有無、語尾、記号)は、渡す前にここへ書き出す**。
    書かなかった体裁は、手順 4 の却下の理由にできない
- `path` — 任意。原文のあるファイルの**絶対パス**。Gemini はこのファイルを読み、原文の周り
  (コメントが指す関数、同じ文書の前後の節)を確かめてから添削する。`line` で行(`42` や `"42-45"`)を添える。
  内容が実装と合っているかを確かめてほしいときも、`path` を渡せば足りる。`hint` に「実装と突き合わせて」と書く必要はない
- `refs` — 任意。原文が指すものが別のファイルにあるとき、その**絶対パス**の配列(カラム説明ならテーブル定義や、値を作る SQL)。
  Gemini がそのファイルを実際に読めたかは、結果からは判別できない。**外せない制約(既存の表記など)は `hint` にも書く**。
  `note` に参照先にしかない値(キー名、定数名)が出ていれば、読めたと見てよい
- `hint` — 任意。ファイルを読んでもわからない文脈を渡す。効果が大きいのは次の 2 つ
  - **プロジェクトの既存表記**(「既存表記は『ユーザ』(長音なし)」) — 指定しないと表記を勝手に統一される
  - **ファイルにない事実**(カラムに実際に入る値の分布、`path` を渡せない対象の前提)

`path` と `refs` は相対パスにしない。agy の読み取りツールは絶対パスしか受け付けず、Gemini は作業ディレクトリを知らない。

**守ってほしい制約は、先に `kind` か `hint` に書く。** 見出し名、定型句、既存の表記、文体、長さの上限は、
書いておけば提案されない。書かずに後から却下すると、Gemini の言い回しの判断まで自分の語感で退けることになる(手順 4)。
直す必要のない文字列は、そもそも `text` に入れない。

### 3. Gemini に投げる

```bash
python3 <この SKILL.md と同じディレクトリ>/scripts/proofread.py --input items.json --output result.json \
  --origin ai --context-dir /abs/path/to/repo/auth
```

標準出力に、項目ごとの原文・添削文・変更理由が出る。項目は 5 件ずつの塊に分けて並行に投げられる。

`--output` の JSON は、手順 4 の検証を機械的に回すときに読む。形は次のとおり。

```json
{
  "results": [{"id": "", "kind": "", "original": "", "revised": "", "note": "",
               "changed": true, "undecidable": false, "mismatch": false, "supplemented": false,
               "added_tokens": [], "removed_tokens": []}],
  "missing_ids": [], "unexpected_ids": [], "failures": [], "denied_actions": []
}
```

`undecidable` は `note` が「判断できない:」で始まる項目、`mismatch` は「食い違い:」で始まる項目、
`supplemented` は `note` に「補った:」の行がある項目に立つ(手順 4)。
`added_tokens` と `removed_tokens` は、原文と添削文でインラインコードと数値の集合を比べた差で、
スクリプトが機械的に数える。**Gemini の「補った:」の申告は漏れることがあるので、この 2 つも必ず見る。**

- **`--origin` で、原文の出自を伝える。** 出自によって出る症状が違うので、Gemini が重点的に見るところが変わる
  - `ai` — エージェントや LLM が生成した文章。語の選び方と構成を重点的に見る。**エージェントが書いた設計文書、README、コメントはこれにあたる**
  - `human` — 人が手早く書いた文章。一文の圧縮をほどくことを重点的に見る
  - `mixed` — 既定。どちらとも決まらないとき。重点を置かないぶん、`ai` より手の入り方が弱くなる
- **`--context-dir` には、Gemini に読ませてよいディレクトリを指定する**(繰り返し指定可)。`path` と `refs` は、この中に置く。
  agy はこのディレクトリの中だけ読み取りを許可し、書き込みと、外の読み取りは拒否する
- **`--context-dir` はなるべく狭くする。** 中にある `.env` のような `.gitignore` の対象も Gemini に読まれうるので、
  リポジトリのルートではなく、原文と参考のファイルを含むサブディレクトリを指定する。ホームディレクトリと `/` はスクリプトが拒む。
  秘密を含むファイルと同じディレクトリにしか置けない対象は、`path` を渡さず、周りの文脈を `hint` に書き写す
- `path` も `refs` もない項目だけなら、`--context-dir` は要らない(原文だけで添削する)
- 既定モデルは `gemini-3.8-flash-medium`。原文だけなら短文 10 件で約 40 秒。周りを読ませると、1 回の呼び出しが 20〜30 秒ほどに延びる
- **結果がほとんど「変更なし」で、読み返して納得できないときは、まず `--origin` の指定を確かめる。**
  生成された文章に `mixed` のまま投げると、語の選び方と構成にほとんど手が入らない。指定しても薄いなら
  `--model gemini-3.8-flash-high` で投げ直す(長文では手を抜いて原文をそのまま返すことがある)
- **再試行は 2 層ある。** 内側は、スクリプトが塊ごとに行う 3 試行で、自動。外側は、自分がコマンドをもう一度実行する投げ直しで、
  **内側が尽きてから**行う。下の表が言う「投げ直す」は、外側のほう
- **進む判断は、機械可読のフィールドだけで行う。** 拒否も構造化出力の欠落も間欠的に起きる。最後に `missing_ids`、
  `unexpected_ids`、`failures`、`denied_actions` がどれも空なら、拒否のなかった試行の結果が返っている。そのまま手順 4 へ進む。
  **`!!` の行は人に向けた印で、食い違いの知らせにも付く。これを進む判断に使わない**
- `--output` の JSON を読み戻すときは、`results` の id の集合が自分の入力と一致することを確かめる。
  別の実行に上書きされていても、`missing_ids` や `unexpected_ids` では気づけない
- **進んでよいことと、記録を残すことは別。** 途中で `拒否された操作:` が出ていたなら、返ってきた添削が `path` や `refs` を
  読んだうえのものとは限らない。外せない制約が `hint` にも入っているかを確かめ、拒否があったことを手順 5 で報告する。
  先へ進めることは、この報告を免除しない

**結果がそろわなかったときだけ読む表:**

| 症状 | 次の一手 |
| --- | --- |
| 一部の塊だけ `!! 添削できなかった id:` | 他の塊の結果は使える。失敗した id だけを別の入力ファイルにまとめて投げ直す |
| 全滅し、エラー文に `拒否された操作:` がある | 同じ入力で 1 回投げ直す。続くなら操作の名前で分ける。`ViewFile` は読ませたいファイルが `--context-dir` の外にあるので範囲を見直す。`ListDir` は範囲外を一覧しようとしているので、`path` と `refs` を外し、周りの文脈を `hint` に書き写す |
| 全滅し、エラー文に何も付いていない | 構造化出力の間欠的な欠落。同じ入力でもう 1 回だけ実行する |
| 投げ直しても全滅する | `agy --model gemini-3.8-flash-medium -p "1 と答えて"` で疎通を確かめ、返らなければ agy 側の問題としてユーザーに報告して止める |

- agy のエラー文は「headless では許可を聞けないので自動で拒否した」と出るが、これは拒否の**伝え方**であって原因ではない。
  原因は、読もうとした先が `--context-dir` の外にあることのほうにある
- `path` と `refs` を外して投げ直したときは、周りを読ませられていない。その旨を手順 5 の報告に書く
- 投げ直しで変えてよいのは `path`、`refs`、`hint`、`--context-dir` だけ。**`text` と `kind` は変えない**
  (添削の条件そのものが変わると、何が原因だったのか分からなくなる)。自分で日本語を書き換えて済ませることもしない
- `!!` で始まる行（返ってこなかった id、依頼していない id、agy が拒否した操作、食い違いの指摘）は必ず読む。
  対応づけが崩れたまま反映すると、別の箇所の添削文を書き込むことになる

### 4. 検証する — このスキルの本体

添削文をそのまま反映しない。ただし確かめるのは 1 つだけ。**添削文が言っていることが、事実と食い違っていないか。**

事実の出どころは、対象のコード、スキーマ、上流文書、周辺の文書、そして一般に知られている事実である。
**原文は事実の出どころではない。** 原文も誰かが書いた文章で、間違っていることがある。

**原文との違いは、直す理由にならない。** 内容が変わっていても、言葉が増えていても、限定が外れていても、
それ自体は問題ではない。問題になるのは、その結果として文書が事実でないことを言っている場合だけである。
推敲を頼んだ以上、どう言い換えるかは Gemini の判断であって、こちらが原文へ寄せ直すためのものではない。

#### 直すのは、食い違いを書けるときだけ

**「<出どころ>の<箇所>は X と言っているが、添削文は Y と言っている」を、出典(ファイルと行、要求 ID、スキーマの列、URL)
付きで書けるときだけ直す。** 書けないなら採用する。

| 直す理由にしない | なぜ |
| --- | --- |
| 原文と違う、原文に無い、原文より強い / 弱い | 推敲とはそういうものである。事実と食い違っていないなら、変わってよい |
| 別の意味にも読めてしまう | 曖昧さの判断は言い回しの領分で、Gemini のほうが上手い。実際に別のものを指していると出典で示せるなら、それは食い違いなので直す |
| この文書の定義語ではない、実装寄りの語である | 用語の縛りは `kind` か `hint` で先に渡す(手順 2)。渡していない縛りを後から持ち出さない |
| 根拠を確かめられなかった | 確かめられないことと、事実と違うことは別である。数値と識別子だけは例外(次項) |
| 構成が変わった、ほかの列と内容が重なった | 読みやすさの判断であり、Gemini に任せたところである |

#### 確かめ方

1. 変わった箇所を拾う。`changed` が立った項目と、`added_tokens` / `removed_tokens` に出た記号・数値。
2. その箇所が言っていることを、出どころに当たって確かめる。上流文書なら要求 ID を引き、実装ならコードとスキーマを読む。
   `path` や `refs` を渡した項目は、Gemini も同じものを読んでいる。
3. 食い違いを出典付きで書けたら、**事実に合わせて書き直す**。原文に戻すのは手段の 1 つでしかない。
   原文のほうが事実と食い違っているなら、原文にも戻さない(手順 5 で別に報告する)。

**数値・単位・日付・識別子・型名・カラム名・URL だけは、確かめられないものを残さない。** 間違っていたときの実害が大きく、
読み手が正しさを判断できないためである。`added_tokens` に出たものは、1 件ずつ出どころに当たる。
一方、**一般に知られている事実の補足**(「カード番号は Stripe が保持する」「値を写し取ることをスナップショットと呼ぶ」など)は、
食い違いを示せない限り残す。

| 判定 | 例 |
| --- | --- |
| 採用 | 「その卸先ユーザーが所属する取引先のデータ」→「自社の取引先データのみを扱う」(指す範囲は同じ。別のものを指していると示す出典が無い) |
| 採用 | 「カード番号は Stripe が保持し」→「カード番号などの機密情報は Stripe が保持(トークン化)し」(一般に知られている事実。確かめられないことは直す理由にならない) |
| 採用 | 「決済」→「決済レコード」(用語をそろえたいなら `hint` に既存表記として渡す。渡していないなら直さない) |
| 直す | 「セッションは 7 日で切れる」→「30 日で切れる」(`docs/specs/staff-accounts.md#FS-10` が 7 日と定めている) |
| 直す | 足された `status: active`(スキーマの列に `active` が無く、値は `enabled` である) |

#### 渡した制約に反するか

`kind` と `hint` で渡した制約(長さの上限、書式、既存の表記、定型句、見出し名、文体)に反していれば却下する。
これは好みの判断ではなく、渡した条件との照合である。

照合できるのは、**数値・列挙・定型句のように機械的に突き合わせられる制約だけ**。「既存の行に合わせる」のような目安に
反したことは、却下の理由にしない。伸びが気になるなら、次の依頼で桁数を `kind` に書く(手順 2)。

ほどけば文は 5〜20% 伸びる(これは見込みであって、許容幅ではない)。長さの制約がある対象では、伸びた分が収まっているかを実際に数える。
**「全角 N 文字」は、全角(East Asian Width が W か F)を 1、それ以外を 0.5 として数える。** 目分量で判断しない。

```bash
python3 -c 'import sys,unicodedata as u; print(sum(1 if u.east_asian_width(c) in "WF" else 0.5 for c in sys.argv[1]))' "<添削文>"
```

制約に反する案が返ってきたということは、その制約が伝わっていない。**次の依頼では `kind` か `hint` に書いて、
そもそも提案させない。** 直す必要のない文字列(見出し名、`該当なし：` のような定型句、要求 ID)は `text` から外す。

**`note` が「判断できない:」で始まる項目は、Gemini が原文の意味を読み取れなかったもの。**
これは添削の失敗ではなく、原文が読み手に意味を渡せていないという最も強い signal になる。
コードを読んで意味が特定できるなら、自分で書き直した案を出す。特定できないなら、
その項目は原文のまま残し、何が読み取れなかったかをユーザーに提示して聞く。**推測で埋めない。**

**`note` が「食い違い:」で始まる項目は、Gemini が周りを読んで、原文の内容と実装や定義の食い違いに気付いたもの。**
この項目の `note` は、1 行目が食い違いの内容、2 行目が変更理由になる。
食い違いが本当かを自分でコードを読んで確かめる。**添削文の反映は、ほかの項目と同じように進めてよい**(書き方だけが直っていて、
誤った内容はそのまま残っているため)。**誤りそのものは直さない。** 数値や条件を書き換えるのは添削ではないので、
手順 5 で添削とは別に報告し、どう直すかはユーザーの指示を待つ。

### 5. 反映して報告する

依頼が「見て」「どうか」で止まっていて修正の意図を含まないなら、**検証を済ませた案を提示するところで止める**。
勝手に書き換えない。「直して」「整えて」と言われているなら、採用した案をファイルへ反映する。

**反映するのは、項目として渡した範囲だけ。** 添削文に出てきた言い換えを、ほかの箇所へ広げない。
検索置換をしない。「渡す → 送付する」が採用された項目があっても、ほかの箇所の「渡す」はそのまま残す。
同じ語でも文脈によって適した語は変わり、Gemini はそれを見たうえで使い分けている。
1 箇所の言い換えを文書全体に適用すると、Gemini が読んでいない文脈にまで自分の判断で手を入れることになり、かえって読みにくくなる。

ほかの箇所も同じようにそろえたいなら、**その箇所を項目として渡して添削させる**。
プロジェクトで表記が決まっている語なら、`hint` に既存表記として渡す(手順 2)。どちらも、判断するのは Gemini の側になる。

どちらの場合も、報告に必ず含める。

- 反映した件数と、変更が大きかった箇所
- 項目にしていない箇所で、同じ言い換えが当てはまりそうだと気付いたもの。勝手に直さず、次の依頼に含めるかをユーザーに聞く
- **事実に合わせて直した箇所と、その出典**。「<出どころ>は X と言っているが、添削文は Y と言っていた」を出典付きで書く。
  制約に反していて直した箇所は、どの制約(`kind` や `hint` のどれ)に反するかを書く。黙って落とさない
- 直した件数が多いなら、次の依頼で `kind` か `hint` に足すべき制約(用語、定型句、書式)を添える
- 「判断できない」で返ってきた項目と、ユーザーへの質問

**原文の内容そのものが実装と食い違っている**ことに気付いたら、添削の範囲外として別に報告する。
添削文を事実に合わせるのは自分の仕事だが、もともと間違っていた説明を正しい説明に書き換えるのは、推敲ではなく文書の改訂になる。
どう直すかはユーザーの指示を待つ。

  ここで扱うのは、書くと決まった日本語の読みやすさだけ
- **英語の文章** — このスキルの指示文は日本語を前提にしている
- **ユーザーへの回答やコミットメッセージ** — 依頼されれば拒む理由はないが、想定している対象ではない
