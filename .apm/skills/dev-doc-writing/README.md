# dev-doc-writing

AI エージェントに、開発文書（PRD、Product Spec、Design Doc）を書かせる、改訂させる、レビューさせるスキル。

## 解決する課題

AI に開発文書を書かせると、材料のない箇所まで流暢に埋めてしまう。製品原則、市場規模、目標値、スケジュールがそれらしく書かれ、読み手はどこまでがユーザーの判断で、どこからが推測かを区別できない。

また、PRD の機能要求と Product Spec の Functional Specification、PRD のそのほか技術的要求と Design Doc の非機能要件のように、似た内容を扱うセクションの境界が曖昧だと、同じ内容が 2 回書かれるか、どちらかが空洞になる。

## アプローチ

- **出どころを決めてから書く。** 各セクションの中身に、意思決定、ユーザーの知る事実、環境の事実、外部の事実、導出のどれから持ってくるかを割り当てる。ユーザーにしか決められないことと、ユーザーしか知らない事実は、書く前に聞き取る。答えのないものは推測で埋めず、未決定事項として残す。
- **3 文書を緩くつなぐ。** PRD → Product Spec → Design Doc を上流から下流への関係として扱い、要求 ID（`FR-1` など）で対応を辿れるようにする。上流文書がなくても書ける。上流を改訂したら、参照を検索して下流にも反映する。
- **境界を明文化する。** 似た内容を扱うセクションの組ごとに、何で分けるか（抽象度、与えられ方、視点、画面への依存）を定める。
- **経緯を知らない読み手にチェックさせる。** 書き上げた文書は、会話の経緯を持たないサブエージェントにチェックさせる。書いた本人は前提を頭の中で補って読んでしまうので、抜けに気づけない。

## 使い方

```
「データエクスポート機能の PRD を書いて」
「docs/prd/data-export.md をもとに Product Spec を書いて」
「PRD の機能要求を変えたので、Product Spec と Design Doc にも反映して」
「この Design Doc をレビューして」
```

依頼に PRD、Product Spec、Design Doc のいずれかの名前が出たときに起動する。

## 依存

- 聞き取りに `ask-via-form` スキルを使う。一緒に入れる。動作の要件（Python 3.9 以上、ブラウザなど）は `ask-via-form` の README を参照。

  ```bash
  apm install murooka/agent-skills --skill dev-doc-writing --skill ask-via-form
  ```

- チェックにサブエージェントを使う。サブエージェントを起動できない環境では、書いたエージェントが自分でチェックし、その旨を報告する。
