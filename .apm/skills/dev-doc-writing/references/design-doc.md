# Design Doc のセクション規範

Design Doc は、作るものを技術的にどのように実現するのかを記す。主な読み手は実装エージェントなので、契約（型、シグネチャ、スキーマ、要求 ID）は、辿れる具体名で書く。人間のレビュアーも読むので、採用した方式と、検討して採らなかった案は省かない（採らなかった理由は、聞き取りの答えにあるときだけ書く）。

## セクション

次のセクションを、この順ですべて置く。

| セクション | 書くこと | 書かないこと | 出どころ |
|---|---|---|---|
| 概要 | 何をどう実現する設計か | 背景の長い説明、上流の要求 ID の一覧 | 導出 |
| Goals / Non-goals | この設計で達成すること、あえて達成しないこと | 製品のスコープの繰り返し | 意思決定、導出 |
| 既存実装 | 変更に関わる今のコード、データ、依存の構造。ファイルパスなど辿れる形で。コードがまだ無ければ、その事実と、規約が定める前提 | 変更後の姿 | 環境の事実 |
| 技術設計 | 採用する方式、コンポーネントの分担、処理の流れ。論点ごとに 要約 → 流れ → 決めごと → 出典 | 型やスキーマの細部（データモデル、API / Interface） | 導出（採否はユーザー） |
| データモデル | 追加や変更するエンティティ、スキーマ、制約、移行の要否。ER 図が既定 | 変更に関わらない既存モデルの全体 | 導出、環境の事実 |
| API / Interface | 公開する API、関数、イベントのシグネチャと契約。実装言語の型で書く | 実装の本体 | 導出 |
| エラーハンドリング | 失敗の種類ごとの検出、利用者への見え方、復旧 | Product Spec のエッジケースの繰り返し（要求 ID で参照する） | 導出 |
| 非機能要件 | そのほか技術的要求を測れる目標値に落としたもの（対応する要求 ID）と、技術側で足した要件 | 目標を満たす実現方法（技術設計） | 導出、意思決定（目標値） |
| Alternatives Considered | 検討した別案と、その中身（採らなかった理由は、答えにあるときだけ） | 比較にならない明らかに劣る案 | 導出 |
| Rollout / Migration | 段階的な公開、データ移行、切り替え時の検証、ロールバックの手順 | 日付の約束（PRD のマイルストーン） | 導出、意思決定 |
| 未決定事項 | 答えのない意思決定と事実。関わるセクションと、次に聞く先 | 決まったこと | 聞き取りで答えがなかったもの |

テスト方針のセクションは置かない。テストケースは Product Spec の受け入れ条件から導き、テストの層の分担は実装するときに決める。移行時のデータの突き合わせのような特別な検証は、Rollout / Migration に書く。

## 置き場の書き方

具体名を求めるのは契約である。型名、シグネチャ、スキーマ、要求 ID は、辿れる具体名で書く。

**これから作るものの置き場は、層と領域までにとどめる。** ファイル名やディレクトリ構成は書かない（「アプリケーション層の認証ユースケース」「インフラ層の Google OAuth クライアント」まで）。置き場の正はコードとプロジェクトの規約であって、この文書ではない（`conventions.md` の「文書と実装がずれたとき」）。書いても実装で最初に陳腐化し、本文から削られることになる。

既存実装は例外で、実在するコードを指すので具体名で書く（「既存実装」の項）。

## セクションごとの注意

### 概要

- 何をどう実現する設計かを、2〜3 文で書く。
- 上流文書の一覧や、扱う要求 ID、扱わない要求 ID を並べない。上流との対応は、Goals と非機能要件の各項目の参照で表す（`conventions.md` の「上流の項目への参照」）。
- リファクタリングや移行のように上流文書がなければ、範囲は Goals / Non-goals が担う。

### Goals / Non-goals

- Goals には `G-<番号>` を振る。上流文書があれば、対応する要求 ID を添える（`` `docs/specs/data-export.md#FS-1` ``）。上流文書がないとき、「共有の部品をこの文書で定める」のように上流に対応しない技術的な Goal のときは、`—` と書く（`conventions.md` の「上流の項目への参照」）。
- Non-goals には、あえて達成しないことと、その理由を書く（例: 「既存の検索インデックスは作り直さない。移行コストに見合う改善がないため」）。
- 製品のスコープを言い換えて繰り返さない。技術の視点で、この設計が何に責任を持つかを書く。

### 既存実装

- 変更に関わるコード、データ、依存の構造を、調べた結果だけで書く。
- ファイルパス、クラス名、関数名、テーブル名など、読み手が辿れる具体名で書く（`` `src/export/job.ts` の `ExportJob.run` ``）。実在するものを指すので、ここは具体名でよい。ただし、ディレクトリツリーを丸写ししない。
- 変更後の姿は書かない。それは技術設計以降に書く。
- **まだコードが無いアプリなら、無いという事実と、規約が定める前提（採用しているフレームワーク、層の分け方など、すでに決まっている制約）だけを、1 行ずつ書く。** これから作るものは技術設計に書く。「該当なし」にはしない（調べた結果、書ける事実がある）。

### 技術設計

- 論点ごとに `###` の小見出しを立てる（「セッションの持ち方」「Google 連携」など）。
- **小見出しの中は、要約 → 流れ → 決めごと → 出典の順に置く。**

  | 並び | 中身 | 形 |
  |---|---|---|
  | 要約 | この論点で何をどう実現するか | 2〜3 文 |
  | 流れ | 処理や状態の移り変わり | Mermaid のシーケンス図、または番号付きの手順。一本道の論点では省く |
  | 決めごと | 実装が従う決定 | 箇条書き。1 項目に 1 決定 |
  | 出典 | 外部の事実の根拠 | 箇条書き（URL と参照日） |

- **1 つの箇条書き項目に、流れと決めごとと出典を同居させない。** 同居させると 1 項目が数百字に膨らみ、実装するときに流れと決めごとだけを拾えなくなる。節が長いことは問題ではない。
- 順に評価して結果を返す判定（どの条件でどれを返すか）は、「判定」と「返す理由」の表にする（`conventions.md` の「表、箇条書き、文章を使い分ける」）。
- 方式に複数の妥当な候補があるときは、候補と推奨を示して、採否をユーザーに委ねる。採らなかった候補は Alternatives Considered に書く。
- セキュリティの実現方法（認可を確かめる箇所、暗号化の方式など）もここに書く。

### データモデル

- **Mermaid の `erDiagram` を既定にする。** エンティティ、関連、多重度（1 対 0..1、1 対多）を図で示す。表で並べない。表にすると、1 対 0..1 と 1 対多の違いが列に散り、読み取れなくなる。
- 図から読めないことだけを、図の下に箇条書きで残す。NULL 可否、一意性、既定値、テーブルを分ける理由など。
- 既存データの移行が要るかどうかを書く。移行の手順は Rollout / Migration に書く。
- 変更に関わらない既存のモデルは書かない。

### API / Interface

- 公開する API、関数、イベントについて、シグネチャと契約（入力、出力、エラー、事前条件、事後条件）を書く。
- **契約は、実装言語の型で書く。表にしない。** TypeScript なら型宣言、Go なら interface、Python なら型注釈付きのシグネチャ。表にすると、「成功」「失敗の理由」「事後条件」の列が並び、型から読めることまで日本語で書き直すことになる。
- 成功の形と、失敗の理由（`reason` など）は、型から読める形にする（リテラルの合併型など）。
- 型で表せない事後条件（副作用、冪等性、呼び出しの前後関係）だけを、シグネチャの上のコメントに置く。
- 依存を注入する型（`XxxDeps` など）は、名前だけを書く。中身は実装に依存し、設計として決めることがない。
- 具体度は、型、シグネチャ、スキーマまでにする。込み入った処理に限って、擬似コードを書いてよい。
- 実装コードの断片は書かない。実装が変わった時点で文書が古くなり、実装と文書を二重に管理することになる。

### エラーハンドリング

- 失敗の種類ごとに、どう検出するか、利用者にどう見えるか、どう復旧するかを書く。
- Product Spec で定めたエッジケースの振る舞いは繰り返さず、`` `docs/specs/data-export.md#EC-3` `` のように参照する。

### 非機能要件

- `NFR-<番号>` を振り、対応するそのほか技術的要求を添える（`` `docs/prd/data-export.md#TR-2` ``）。技術側の都合で足した要件は上流を持たないので、`—` と書く（`conventions.md` の「上流の項目への参照」）。
- 測れる目標値で書く（p99 レイテンシ、スループット、可用性、データの保持期間など）。目標値は意思決定なので、候補と推奨を示して聞き取る。
- 技術側の都合で足した要件（運用コストの上限など）も書く。
- 個人情報や認可に触れる変更では、守るべきセキュリティの水準を書く。監視する指標とアラートの閾値もここに書く。

### Alternatives Considered

- 検討した別案ごとに、案の中身（どういう方式か、採用案と何が違うか）を書く。調べた事実があれば、出典を添える。
- **採らなかった理由は、聞き取りの答えにあるときだけ書く。** 聞き取りでは案の採否だけが返り、理由が付かないことがほとんどである。推奨したときの理由を、ユーザーが採らなかった理由として流用しない（`check.md` の項目 1）。理由が要ると判断したなら、未決定事項に入れる。
- 比較にならないほど明らかに劣る案を並べて水増ししない。

### Rollout / Migration

- 段階的な公開（フラグ、対象の絞り込み）、データ移行、切り替え時の検証、監視やアラートの立ち上げ、ロールバックの手順を書く。
- 移行時のデータの突き合わせや負荷の確認など、切り替えの前後で行う特別な検証もここに書く。
- 日付は約束しない。日付は PRD のマイルストーンに任せる。

```markdown
## Rollout / Migration

```
