# Design Doc のセクション規範

Design Doc は、作るものを技術的にどのように実現するのかを記す。主な読み手は実装エージェントなので、ファイルパス、型名、シグネチャ、スキーマなど、辿れる具体名で書く。人間のレビュアーも読むので、採用した方式の理由と、採らなかった案は省かない。

## セクション

次のセクションを、この順ですべて置く。

| セクション | 書くこと | 書かないこと | 出どころ |
|---|---|---|---|
| 概要 | 何をどう実現する設計か | 背景の長い説明、上流の要求 ID の一覧 | 導出 |
| Goals / Non-goals | この設計で達成すること、あえて達成しないこと | 製品のスコープの繰り返し | 意思決定、導出 |
| 既存実装 | 変更に関わる今のコード、データ、依存の構造。ファイルパスなど辿れる形で | 変更後の姿 | 環境の事実 |
| 技術設計 | 採用する方式、コンポーネントの分担、処理の流れ | 型やスキーマの細部（データモデル、API / Interface） | 導出（採否はユーザー） |
| データモデル | 追加や変更するエンティティ、スキーマ、制約、移行の要否 | 変更に関わらない既存モデルの全体 | 導出、環境の事実 |
| API / Interface | 公開する API、関数、イベントのシグネチャと契約 | 実装の本体 | 導出 |
| エラーハンドリング | 失敗の種類ごとの検出、利用者への見え方、復旧 | Product Spec のエッジケースの繰り返し（要求 ID で参照する） | 導出 |
| 非機能要件 | そのほか技術的要求を測れる目標値に落としたもの（対応する要求 ID）と、技術側で足した要件 | 目標を満たす実現方法（技術設計） | 導出、意思決定（目標値） |
| Alternatives Considered | 検討した別案と、採らなかった理由 | 比較にならない明らかに劣る案 | 導出 |
| Rollout / Migration | 段階的な公開、データ移行、切り替え時の検証、ロールバックの手順 | 日付の約束（PRD のマイルストーン） | 導出、意思決定 |
| 未決定事項 | 答えのない意思決定と事実。関わるセクションと、誰が決めるか | 決まったこと | 聞き取りで答えがなかったもの |

テスト方針のセクションは置かない。テストケースは Product Spec の受け入れ条件から導き、テストの層の分担は実装するときに決める。移行時のデータの突き合わせのような特別な検証は、Rollout / Migration に書く。

## セクションごとの注意

### 概要

- 何をどう実現する設計かを、2〜3 文で書く。
- 上流文書の一覧や、扱う要求 ID、扱わない要求 ID を並べない。上流との対応は、Goals と非機能要件の各項目の参照で表す（`conventions.md` の「上流の項目への参照」）。
- リファクタリングや移行のように上流文書がなければ、範囲は Goals / Non-goals が担う。

### Goals / Non-goals

- Goals には `G-<番号>` を振る。上流文書があれば、対応する要求 ID を添える（`` `docs/specs/data-export.md#FS-1` ``）。
- Non-goals には、あえて達成しないことと、その理由を書く（例: 「既存の検索インデックスは作り直さない。移行コストに見合う改善がないため」）。
- 製品のスコープを言い換えて繰り返さない。技術の視点で、この設計が何に責任を持つかを書く。

### 既存実装

- 変更に関わるコード、データ、依存の構造を、調べた結果だけで書く。
- ファイルパス、クラス名、関数名、テーブル名など、読み手が辿れる具体名で書く（`` `src/export/job.ts` の `ExportJob.run` ``）。
- 変更後の姿は書かない。それは技術設計以降に書く。

### 技術設計

- 採用する方式、コンポーネントの分担、処理の流れを書く。処理の流れは、Mermaid のシーケンス図などを使ってよい。
- 方式に複数の妥当な候補があるときは、候補と推奨を示して、採否をユーザーに委ねる。採らなかった候補は Alternatives Considered に書く。
- セキュリティの実現方法（認可を確かめる箇所、暗号化の方式など）もここに書く。

### データモデル

- 追加や変更するエンティティ、スキーマ、制約（一意性、外部キー、NULL 可否）を書く。
- 既存データの移行が要るかどうかを書く。移行の手順は Rollout / Migration に書く。
- 変更に関わらない既存のモデルは書かない。

### API / Interface

- 公開する API、関数、イベントについて、シグネチャと契約（入力、出力、エラー、事前条件、事後条件）を書く。
- 具体度は、型、シグネチャ、スキーマまでにする。込み入った処理に限って、擬似コードを書いてよい。
- 実装コードの断片は書かない。実装が変わった時点で文書が古くなり、実装と文書を二重に管理することになる。

### エラーハンドリング

- 失敗の種類ごとに、どう検出するか、利用者にどう見えるか、どう復旧するかを書く。
- Product Spec で定めたエッジケースの振る舞いは繰り返さず、`` `docs/specs/data-export.md#EC-3` `` のように参照する。

### 非機能要件

- `NFR-<番号>` を振り、対応するそのほか技術的要求を添える（`` `docs/prd/data-export.md#TR-2` ``）。
- 測れる目標値で書く（p99 レイテンシ、スループット、可用性、データの保持期間など）。目標値は意思決定なので、候補と推奨を示して聞き取る。
- 技術側の都合で足した要件（運用コストの上限など）も書く。
- 個人情報や認可に触れる変更では、守るべきセキュリティの水準を書く。監視する指標とアラートの閾値もここに書く。

### Alternatives Considered

- 検討した別案ごとに、概要と、採らなかった理由を書く。
- 比較にならないほど明らかに劣る案を並べて水増ししない。

### Rollout / Migration

- 段階的な公開（フラグ、対象の絞り込み）、データ移行、切り替え時の検証、監視やアラートの立ち上げ、ロールバックの手順を書く。
- 移行時のデータの突き合わせや負荷の確認など、切り替えの前後で行う特別な検証もここに書く。
- 日付は約束しない。日付は PRD のマイルストーンに任せる。

## 骨組み

```markdown
# <設計の対象> Design Doc

## 概要

## Goals / Non-goals

## 既存実装

## 技術設計

## データモデル

## API / Interface

## エラーハンドリング

## 非機能要件

## Alternatives Considered

## Rollout / Migration

## 未決定事項
```
