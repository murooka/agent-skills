# Design Doc のセクション規範

Design Doc は、作るものを技術的にどのように実現するのかのうち、**人がレビューして決めておくべき要点だけ**を記す。読み手はまず人間のレビュアーである。実現方法の大半は、実装エージェントが実装するときに決めてよい。

長い Design Doc は、レビューされないか、レビューする人を消耗させる。データベースの構成だけが書かれた Design Doc で十分なこともある。**短いことがこの文書の価値である。**

**書くのは、次のどれかにあたる決定だけである。**

- 後から変えにくい（データの持ち方、層の分け方、トランザクションの境界、公開する契約）
- コードの外に影響する（既存データの移行、外部サービス、インフラのリソース、他のアプリの変更）
- セキュリティにかかわる（認証、認可、個人情報）
- 上流文書から読み取れず、実現方式が 1 つに絞れない

**どれにもあたらないなら、Design Doc を書かない。** その旨をユーザーに伝えて終える。実現方法は実装するときに決める。

上流が決めた「何をするか」は書かない（要求 ID で参照する）。実装を進めれば自明なことも書かない（`conventions.md` の「その文書を見ないと決められないことだけ書く」）。

文字数の目安: 5000

## セクション

次のセクションは必ず置く。

| セクション | 書くこと | 書かないこと | 出どころ |
|---|---|---|---|
| 概要 | 何をどう実現する設計か | 背景の長い説明、上流の要求 ID の一覧 | 導出 |
| 未決定事項 | 答えのない意思決定と事実。関わるセクションと、次に聞く先 | 決まったこと | 聞き取りで答えがなかったもの |

次のセクションは**任意**で、書くことがあるときだけ、この順で概要と未決定事項の間に置く（`conventions.md` の「見出し」）。**少なくとも 1 つは要る。** 1 つも置けないなら、Design Doc を書く理由がない。

| セクション | 書くこと | 書かないこと | 出どころ |
|---|---|---|---|
| Non-goals | あえて達成しないこと | 製品のスコープの繰り返し | 意思決定、導出 |
| 技術設計 | 人が決めておくべき方式と、その決定 | 実装すれば自明な手順、既存コードの説明、内部の関数やファイルの一覧 | 導出（採否はユーザー） |
| データモデル | 追加や変更するエンティティ、関連、制約、移行の要否。ER 図が既定 | 変更に関わらない既存モデルの全体、列の一覧 | 導出、環境の事実 |
| 公開する契約 | リポジトリや別のアプリから使われる API、イベントの形 | 内部の関数やモジュールのシグネチャ | 導出 |
| 非機能要件 | 測れる目標値。対応する制約 | 目標を満たす実現方法（技術設計） | 導出、意思決定（目標値） |
| 移行と切り替え | データ移行、段階的な公開、外部の準備、切り替え時の検証、ロールバック | 日付の約束（PRD のマイルストーン） | 導出、意思決定 |

テスト方針のセクションは置かない。テストケースは Product Spec の Functional Specification から導き、テストの層の分担は実装するときに決める。

## セクションごとの注意

### 概要

- 何をどう実現する設計かを、2〜3 文で書く。
- 上流文書の一覧や、扱う要求 ID、扱わない要求 ID を並べない。上流との対応は、各決定の参照で表す（`conventions.md` の「上流の項目への参照」）。

### Non-goals（置くときだけ）

あえて達成しないことと、その理由を書く（例: 「既存の検索インデックスは作り直さない。移行コストに見合う改善がないため」）。製品のスコープを言い換えて繰り返さない。

### 技術設計（置くときだけ）

- 論点ごとに `###` の小見出しを立てる（「セッションの持ち方」「Google 連携」など）。
- 小見出しの中は、2〜3 文の要約と、`D-<番号>` を振った決定の箇条書きにする。1 項目に 1 決定。応える上流の項目を添える（`` `docs/specs/data-export.md#FS-1` ``）。上流を持たない決定は `—` と書く。
- **流れの図を置くのは、分岐があるか、複数の構成要素をまたぐときだけ。** 一本道なら要約だけで足りる。図では、読み書きする外部を参加者として分ける。
- 外部の事実を根拠にするなら、出典（URL と参照日）を添える。
- ライブラリの使い方、上流の振る舞いから一意に決まる手順、id や添字の形式、NOT NULL のような細部は書かない。**上流の決定を言い直したものも書かない。**
- 方式に複数の妥当な候補があるときは、候補と推奨を示して、採否をユーザーに委ねる。
- **採らなかった案は、決定の下に 1 行で書く。** 理由は、聞き取りの答えにあるときだけ書く。推奨したときの理由を、ユーザーが採らなかった理由として流用しない（`check.md` の「答えとの対応」）。長く残すべき選定は ADR にする。

### データモデル（置くときだけ）

- **Mermaid の `erDiagram` を既定にする。** エンティティ、関連、多重度（1 対 0..1、1 対多）を図で示す。表で並べない。表にすると、1 対 0..1 と 1 対多の違いが列に散り、読み取れなくなる。
- 図から読めないことのうち、後から変えにくいものだけを、図の下に箇条書きで残す。一意性、テーブルを分ける理由など。
- 既存データの移行が要るかどうかを書く。移行の手順は移行と切り替えに書く。

### 公開する契約（置くときだけ）

- 外から呼ばれるものだけを書く。内部の関数やモジュールの型はコードに任せる。
- **契約は、実装言語の型で書く。表にしない。** 成功の形と失敗の理由が型から読める形にする。
- 型で表せない事後条件（副作用、冪等性、呼び出しの前後関係）だけを、シグネチャの上のコメントに置く。
- 実装コードの断片は書かない。

### 非機能要件（置くときだけ）

- `NFR-<番号>` を振り、対応する制約を添える（`` `docs/prd/data-export.md#TR-2` ``）。技術側の都合で足した要件は `—` と書く。
- 測れる目標値で書く（p99 レイテンシ、可用性、データの保持期間など）。目標値は意思決定なので、候補と推奨を示して聞き取る。
- 個人情報や認可に触れる変更では、守るべきセキュリティの水準を書く。

### 移行と切り替え（置くときだけ）

- データ移行、段階的な公開（フラグ、対象の絞り込み）、マージ以外に要る作業（環境変数、インフラ、外部サービスの設定）、切り替え時の検証、ロールバックの手順を書く。
- 日付は約束しない。

## 置き場の書き方

具体名を求めるのは契約である。型名、シグネチャ、スキーマ、要求 ID は、辿れる具体名で書く。

**これから作るものの置き場は、層と領域までにとどめる。** ファイル名やディレクトリ構成は書かない（「アプリケーション層の認証ユースケース」「インフラ層の Google OAuth クライアント」まで）。置き場の正はコードとプロジェクトの規約であって、この文書ではない（`conventions.md` の「文書と実装がずれたとき」）。

## 骨組み

データベースの構成だけを決める場合:

```markdown
# <設計の対象> Design Doc

## 概要

## データモデル

## 未決定事項
```
