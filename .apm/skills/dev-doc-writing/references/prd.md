# PRD のセクション規範

PRD は、何を、なぜ作るのかを記す。主な読み手は「作るべきか」を判断する人間なので、要点を先に置き、論旨が通るように書く。AI も読むので、判定できる書き方（`conventions.md`）は守る。

## セクション

次のセクションを、この順ですべて置く。

| セクション | 書くこと | 書かないこと | 出どころ |
|---|---|---|---|
| 概要 | 何を作るかの要約（3〜5 文）。読み手が最初に読む | 背景の詳細、機能の列挙 | 導出（ほかのセクションの要約） |
| 背景 | 解決したい課題、今の状況、なぜ今やるのか | 解決策の中身、成功指標 | 意思決定、ユーザーの知る事実 |
| 製品原則 | この製品が何を達成しようとしているのか。方向性の指針になる形で | どの製品にも当てはまる言葉（「使いやすく」） | 意思決定 |
| スコープ | 今回扱う課題、ユーザー、機能と、扱わないもの | 技術的な達成目標（Design Doc の Goals / Non-goals） | 意思決定 |
| 対象ユーザ | 誰のための製品か。属性と、置かれている状況 | 市場の規模 | 意思決定 |
| ユースケース | 誰がどんな状況で何を達成したいか | 画面や操作（Product Spec のユーザーフロー） | 意思決定、導出（候補を AI が出す） |
| 機能要求 | ユーザーが何をできるようになるべきか。対応するユースケース | 振る舞いの詳細（Product Spec の Functional Specification） | 意思決定、導出（ユースケースから候補を出す） |
| そのほか技術的要求 | 製品や事業の側から課される制約 | 技術側で決める測れる目標値（Design Doc の非機能要件） | 意思決定、ユーザーの知る事実、環境の事実 |
| リリーススケジュールおよびマイルストーン | 節目ごとの日付と、その時点で満たすべき状態 | 実装タスクの分解 | 意思決定 |
| マーケティング計画 | 誰にどう届けるか。告知の時期と経路 | 市場や競合の分析 | 意思決定 |
| 未決定事項 | 答えのない意思決定と事実。関わるセクションと、次に聞く先 | 決まったこと | 聞き取りで答えがなかったもの |

**この段で決めないもの**：振る舞いの細部、画面と操作、エッジケース、異常系、境界値、技術側で決める目標値、技術の選択。
どれも下流の文書で決まるので、**聞き取りの設問にもしない**（`sources-and-questions.md` の「この段で決めることだけを聞く」）。

次の 2 つは**任意のセクション**で、既定では置かない。関係しそうなときに、置くかどうかをユーザーに提案する
（`conventions.md` の「見出し」）。

| セクション | 書くこと | 書かないこと | 出どころ |
|---|---|---|---|
| 市場分析 | 市場の規模、動向、機会。出典付き | 個別の競合製品（競合分析） | 外部の事実 |
| 競合分析 | 競合製品と代替手段、その強みと弱み、差別化の軸。出典付き | 自社の機能要求 | 外部の事実 |

社外に売る製品で、作るかどうかの判断に市場や競合が効くときだけ提案する。社内ツール、個人開発、技術的な改修では提案しない。

## セクションごとの注意

### 概要

ほかのセクションを書き終えてから、要約として書く。概要にしか書かれていない情報を作らない。

### 背景

- 課題、今の状況、なぜ今やるのかを書く。「今の状況」の数値や事情はユーザーの知る事実、「なぜ今やるのか」は意思決定である。
- **課題は、ユーザーの言葉のまま写す。縮めない。** 言い換えるなら、元の語より狭くも広くもならないかを確かめる
  （「権限の仕組みが弱い」を「権限が弱い」に縮めると、「付与されている権限が小さい」とも読めてしまう）。
  短くしたいなら、縮めるのではなく文を分ける。
- **成功指標は書かない。** 指標と目標値を決めるには、作ったものが動いたあとの観測が要る。PRD の段で決めると、
  根拠のない数値を置くことになる。

### 製品原則

- **何を達成しようとしているのかを書く。** 読んだ人が、迷ったときにどちらへ進めばよいかを判断できる形にする
  （例: 「初めて使う人が、説明を読まずに 1 件目を登録できるようにする」）。
- トレードオフの形（「A より B を優先する」）で書く必要はない。何を犠牲にするかは、この段では決まっていない。
- 「使いやすく」「速く」のように、どの製品にも当てはまる言葉は書かない。この製品の向きが分かる言葉で書く。

### スコープ

「扱う」と「扱わない」を分けて列挙する。扱わないものには、なぜ今回は扱わないのかを添える。

### 対象ユーザ

属性（役割、規模、利用環境）と、置かれている状況（何に困っているか）を書く。市場の規模は書かない。

### ユースケース

- `UC-<番号>` を振る。
- 「<誰>が、<どんな状況>で、<何を達成したい>」の形で書く。
- 画面、ボタン、クリックなどの操作に触れない。画面が決まるのは Product Spec であり、PRD の時点で書くと推測の画面が入り込む。

### 市場分析、競合分析（置くときだけ）

- 出典（URL と参照日）を付ける。
- 調べる手段がなければ、ユーザーに資料や URL を求め、得られなければ置かない。AI の知識だけで書かない。

### 機能要求

- `FR-<番号>` を振り、対応するユースケースを `UC-<番号>` で添える。
- 「ユーザーは〜できる」の形で書く。
- 実現方法（画面、API、データ構造）に触れない。

### そのほか技術的要求

- `TR-<番号>` を振る。
- 対応環境、法規制、連携が必須の既存システム、体感としての速さなど、製品や事業の側から課される制約を書く。
- 外から与えられた数値（契約上の SLA、法定の保存期間など）はそのまま書いてよい。技術側で決める目標値（p99 レイテンシなど）は書かず、Design Doc の非機能要件に任せる。

### リリーススケジュールおよびマイルストーン

節目ごとに、日付と、その時点で満たすべき状態を書く。日付は意思決定なので、決まっていなければ未決定事項に入れる。

### マーケティング計画

誰に、いつ、どの経路で届けるかを書く。社内ツールや個人開発では、該当なしになりやすい。

## 骨組み

```markdown
# <製品名または機能名> PRD

## 概要

## 背景

## 製品原則

## スコープ

## 対象ユーザ

## ユースケース

## 機能要求

## そのほか技術的要求

## リリーススケジュールおよびマイルストーン

## マーケティング計画

## 未決定事項
```
