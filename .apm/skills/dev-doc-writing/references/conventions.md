# 開発文書に共通の規約

PRD、Product Spec、Design Doc の 3 文書に共通する規約。どの作業でも、始める前に読む。

## 用語

- **開発文書**：PRD、Product Spec、Design Doc の総称。
- **上流文書、下流文書**：PRD → Product Spec → Design Doc の順で、ある文書より前にあるものが上流文書、後ろにあるものが下流文書。
- **要求 ID**：開発文書の項目に振る識別子（`FR-1` など）。
- **未決定事項**：意思決定やユーザーの知る事実が必要なのに、まだ答えがない事項。
- **該当なし**：その場面では書くことがないと判断したセクションに書く記載。

文書の中では、同じものを同じ語で呼ぶ。「開発文書」を「設計文書」「仕様書」と言い換えない。

## プロジェクトの決まりとの関係

置き場所、参照の書き方、図の書式、用語など、プロジェクトに決まり（CLAUDE.md や AGENTS.md の記述、既存の開発文書の書式）があれば、この規約より優先する。

上書きした点は控えておき、チェックを頼むときに規範照合役へ渡す（`check.md` の「渡すもの」）。渡さないと、規範照合役がこの規約に照らして誤った指摘を返す。

## 形式と置き場所

- リポジトリ内の、日本語の Markdown で書く。
- 置き場所は、プロジェクトの決まり（既存の `docs/` の構成、CLAUDE.md の記述など）があればそれに従う。なければ次を既定にする。

| 文書 | 置き場所 |
|---|---|
| PRD | `docs/prd/<名前>.md` |
| Product Spec | `docs/specs/<名前>.md` |
| Design Doc | `docs/design-docs/<名前>.md` |

- `<名前>` は、内容を表す英小文字とハイフンにする（例: `data-export`）。
- 文書の先頭に frontmatter を置かない。上流文書は概要に書く。状態（下書き、承認済みなど）は文書に書かず、プルリクエストなどリポジトリの運用に任せる。上流文書を概要と frontmatter の 2 か所に書くと、片方だけ更新されてずれる。

## 見出し

- 各文書のセクション規範（`prd.md`、`product-spec.md`、`design-doc.md`）の表にあるセクションを、すべて、その順で `##` の見出しとして置く。
- 書くことがないセクションは、見出しを残して `該当なし：<理由>` と 1 行書く（例: `該当なし：社内ツールで、利用者への告知は社内チャットの 1 投稿で済むため`）。
- 「調べられなかった」「まだ決まっていない」は該当なしにしない。未決定事項に入れる。該当なしは「書くことがない」という判断であり、答えのない問いを隠す場所ではない。

## 要求 ID

### 振る対象

| 文書 | セクション | 接頭辞 |
|---|---|---|
| PRD | ユースケース | `UC` |
| PRD | 機能要求 | `FR` |
| PRD | そのほか技術的要求 | `TR` |
| Product Spec | ユーザーフロー | `UF` |
| Product Spec | Functional Specification | `FS` |
| Product Spec | エッジケース | `EC` |
| Product Spec | 受け入れ条件 | `AC` |
| Design Doc | Goals / Non-goals の Goals | `G` |
| Design Doc | 非機能要件 | `NFR` |
| 3 文書共通 | 未決定事項 | `OQ` |

### 採番

- `<接頭辞>-<番号>` の形で、番号は 1 から振る。文書の中で一意にする。
- 改訂で振り直さない。項目を消したら、その番号は欠番にして再利用しない。振り直すと、下流文書や過去のやりとりにある参照がすべて壊れる。
- 項目の先頭に ID を書く（例: `- **FR-2** ユーザーは、退会する前に自分の投稿をまとめて持ち出せる。（UC-1）`）。

## 参照の書き方

- 同じ文書の中の項目は、ID だけで書く（`FR-3`）。
- 別の文書の項目は、リポジトリのルートからのパスと ID を `#` でつなぎ、インラインコードで書く（`` `docs/prd/data-export.md#FR-3` ``）。
- Markdown のリンクやアンカーにしない。上流を改訂したとき、パスの文字列でリポジトリを検索して下流の参照を見つけるためである。アンカーは表示環境によって作られ方が違い、見出しの文言まで含むので壊れやすい。

## 上流の項目への参照

下流文書の項目は、応える上流の項目を要求 ID で参照する。上流との対応は、この項目ごとの参照だけで表す。

| 下流の項目 | 参照する上流の項目 |
|---|---|
| ユーザーフロー `UF`（Product Spec） | ユースケース `UC`（PRD） |
| Functional Specification `FS`（Product Spec） | 機能要求 `FR`（PRD） |
| Goals `G`（Design Doc） | Functional Specification `FS`（Product Spec）。Product Spec がなければ機能要求 `FR`（PRD）。技術的な Goal は上流を持たないことがある（`—`） |
| 非機能要件 `NFR`（Design Doc） | そのほか技術的要求 `TR`（PRD）。技術側の都合で足した要件は上流を持たない（`—`） |

上流に対応しない項目もある。上流文書そのものがない項目、技術側の都合で足した非機能要件、「共有の部品をこの文書で定める」のような技術的な Goal がこれにあたる。この場合は、参照欄に `—` と書く（`- **NFR-3** …（—）`）。省略すると、上流を持たないのか、参照を書き忘れたのかを読み手が区別できない。

概要などに、上流文書の一覧や、この文書が扱う要求 ID、扱わない要求 ID をまとめて書かない。1 つの PRD を複数の Product Spec に分けると、そうした一覧は「この文書では扱わない」の記載ばかりになり、読み手に情報を渡さない。

### 上流の漏れの確かめ方

上流の項目の漏れは、文書 1 つごとではなく、下流文書全体で確かめる。

1. 上の表で、書いた文書の項目が参照する種類の、上流の要求 ID を集める（Product Spec なら PRD の `UC` と `FR`）。
2. それぞれについて、`` `<上流文書のパス>#<ID>` `` の文字列でリポジトリ全体を検索する。
3. どの下流文書からも参照されていない ID を、ユーザーへの報告に挙げる。文書には書かない。

複数の下流文書に分けて書いている途中なら、残りの文書で扱う予定の ID も挙がる。その旨を添えて報告する。

## 未決定事項

- 3 文書すべての末尾に「未決定事項」セクションを置く。
- 各項目には、`OQ-<番号>`、何が決まっていないか、関わるセクションや要求 ID、次に聞く先（誰に聞けば決まるか）を書く。次に聞く先がわからなければ「不明」と書く。決まっていないことは、誰が決めるかもまだ決まっていないことが多い。「不明」のまま残してよく、埋めるために推測しない。
- 本文の該当箇所からは `OQ-<番号>` で参照する。本文に「未定」「検討中」「TBD」とだけ書いて残さない。
- 未決定事項がなければ「なし」と書く。

```markdown
## 未決定事項

- **OQ-1** エクスポートファイルの保持期間。関わる項目: FR-2、そのほか技術的要求。次に聞く先: 法務
```

## 図

Mermaid など、テキストで書ける図だけを使う。画像は使わない。開発文書は AI も読み、差分でレビューされるので、図の中身をテキストとして読めることが要る。

## 書き方

### 判定できるように書く

- 「適切に」「なるべく」「高速に」「十分な」「など」で範囲をぼかさない。量は数値と単位で書き、範囲は列挙で書く。
- 数値や範囲が決まっていなければ、ぼかして書かずに未決定事項に入れる。
- 1 つの文や項目に、条件、振る舞い、例外を詰め込まない。分けて書く。

### 用語をそろえる

- 同じものは、文書の中でも、上流文書との間でも、同じ語で呼ぶ。上流文書で使われている語があれば、それに合わせる。
- 新しく導入する語は、初出で定義する。

### 表、箇条書き、文章を使い分ける

- 同じ属性を持つ項目が並ぶなら、表にする。
- 独立した項目や、順序のある手順は、箇条書きにする。
- 理由、経緯、トレードオフは、文章で書く。
- 型やスキーマで表せるものは、表にも日本語にも開かず、型やスキーマで書く。表にすると、型から読めることまで日本語の列に書き直すことになる。
- 順に評価して、最初に当たったものを返す判定は、「判定」と「返す理由」の 2 列の表にする。箇条書きにすると「A、B、または C なら X を返す」と 1 項目に詰まり、評価の順序が読めなくなる。

### 読み手に合わせる

3 文書とも、人間と AI の両方が読む。重みが違う。

- **PRD**：人間の意思決定者寄り。要点を先に置き、論旨が通るように書く。
- **Product Spec**：人間と実装エージェントの両方。受け入れ条件はテストケースの導出元になるので、判定できることを読みやすさより優先する。
- **Design Doc**：実装エージェント寄り。契約（型、シグネチャ、スキーマ、要求 ID）は、辿れる具体名で書く。これから作るものの置き場は、層と領域までにとどめる（`design-doc.md` の「置き場の書き方」）。

## 開発文書どうしの境界

上流と下流で似た内容を扱うセクションが 4 組ある。境界を守らないと、同じ内容が 2 回書かれるか、どちらかが空洞になる。

| 上流のセクション | 下流のセクション | 分け方 | 例 |
|---|---|---|---|
| 機能要求（PRD） | Functional Specification（Product Spec） | **抽象度**。機能要求は、ユーザーが何をできるようになるべきか（実現方法に触れない）。Functional Specification は、入力や状態に応じて製品がどう振る舞うか（外から観測できる振る舞い） | 機能要求「ユーザーは退会する前に自分の投稿を持ち出せる」。Functional Specification「設定画面でエクスポートを押すと、全投稿をまとめたファイルを作り、できたらメールで知らせる」 |
| そのほか技術的要求（PRD） | 非機能要件（Design Doc） | **与えられ方**。そのほか技術的要求は、製品や事業の側から課される制約。非機能要件は、それを測れる目標値に落とし、技術側の都合で足した要件を加えたもの | そのほか技術的要求「検索結果はほとんど待たずに表示される」。非機能要件「検索 API の p99 レイテンシを 300ms 以下にする」 |
| スコープ（PRD） | Goals / Non-goals（Design Doc） | **視点**。スコープは、今回どの課題、ユーザー、機能を扱い、どれを扱わないか（製品の視点）。Goals / Non-goals は、この設計で何を達成し、何をあえて達成しないか（技術の視点） | スコープ外「法人向けプラン」。Non-goal「既存の検索インデックスは作り直さない」 |
| ユースケース（PRD） | ユーザーフロー（Product Spec） | **画面に依存するか**。ユースケースは、誰がどんな状況で何を達成したいか（画面や操作に触れない）。ユーザーフローは、そのユースケースを製品上でどんな画面と操作の順に達成するか | ユースケース「退会を考えているユーザーが、これまでの投稿を手元に残したい」。ユーザーフロー「設定画面 → データ管理 → エクスポートを押す → 完了メールのリンクを開く」 |

## 文書と実装がずれたとき

| 中身 | 正 |
|---|---|
| 振る舞い | Product Spec |
| 契約（型、シグネチャ、スキーマ） | Design Doc |
| 置き場（ファイル名、ディレクトリ構成） | コードと、プロジェクトの規約 |

振る舞いと契約がずれていたら、文書を正として実装を直す。置き場がずれていたら、文書の側を直すか、消す。

開発文書は置き場の正ではない。これから作るもののファイル名やディレクトリツリーを書くと、実装で最初に陳腐化する記述になる（`design-doc.md` の「置き場の書き方」）。
