# チェック

書き上げた開発文書（作成、改訂）と、レビューを頼まれた開発文書のチェックの手順。

## 担い手

会話の経緯を持たないサブエージェントに任せる。

書いたエージェントは、聞き取りで得た前提を知っている。そのため、文書に書かれていない前提を頭の中で補って読んでしまい、抜けに気づけない。経緯を知らないサブエージェントが読めるかどうかが、そのまま実際の読み手（人間と実装エージェント）を想定した試験になる。

## 渡すもの

依頼文に全文を転記して渡す。ファイルのパスは渡さず、ファイルやリポジトリを開かないよう伝える。リポジトリを見られると、文書に書かれていない前提をコードから補ってしまい、抜けを見逃す。

- 対象の文書の全文
- 上流文書の全文（なければ「上流文書なし」と伝える）
- 対象の文書のセクション規範（`prd.md`、`product-spec.md`、`design-doc.md` のいずれか）の全文
- 共通の規約（`conventions.md`）の全文
- このファイルの「チェック項目」と「出力形式」
- 聞き取りで確定した設問と答え（作成、改訂のとき）。`ask-via-form` の `history` で読み直し、設問ごとに、設問の文、答え、出どころの区分、使うセクションを転記する（`sources-and-questions.md` の「答えの控え」）
- 改訂のときは、今回の変更の差分

## 渡さないもの

- 会話の経緯（試行錯誤、却下した案、ユーザーとのやりとりのうち確定した答え以外のもの）
- 前回のチェックの指摘と、それへの対応の経緯（再チェックでも、直した後の文書だけを渡す）

## チェック項目

1. **聞き取りの裏付け**：出どころが意思決定、ユーザーの知る事実の記述に、聞き取りの答えという裏付けがあるか。答えにない数値、方針、日付、固有の事実が書かれていないか。
2. **出典**：外部の事実に出典（URL と参照日）があるか。
3. **上流との対応**：上流文書の要求 ID のうち、この文書で扱われておらず、扱わない旨も概要に書かれていないものはないか。
4. **判定できる受け入れ条件**：受け入れ条件が、前提、操作、期待結果に分かれ、実装を見ずに合否を判定できる書き方になっているか（Product Spec のとき）。
5. **境界**：各セクションに、セクション規範の「書かないこと」にあたる内容が入っていないか。
6. **該当なしの理由**：「該当なし」に理由があるか。「調べられなかった」「決まっていない」が該当なしにされていないか。
7. **未決定事項の漏れ**：本文の「未定」「検討中」「TBD」など、決まっていないことを示す記述が、すべて未決定事項に載り、`OQ` で参照されているか。
8. **セキュリティの水準**：個人情報や認可に触れる変更で、非機能要件にセキュリティの水準が書かれているか（Design Doc のとき）。
9. **用語の統一**：同じものが、文書の中でも上流文書との間でも、同じ語で呼ばれているか。
10. **前提を補わずに読めるか**：経緯を知らない読み手が、書かれていない前提を補わずに読めるか。読めない箇所は、何が書かれていないために読めないのかを示す。

### 改訂のとき

項目 1 は、今回の変更の差分にだけ適用する。変更していない箇所は、以前の聞き取りで確定したものとして扱う。

### レビューのとき

聞き取りの答えがないので、項目 1 を次に置き換える。

1. **根拠の示されない断定**：出どころが意思決定、ユーザーの知る事実の記述のうち、根拠が示されず、推測で埋めたように見える断定がないか（理由のない目標値、出どころの書かれない現状の数値、決めた人のわからない方針など）。

## 出力形式

サブエージェントには、次の形で返させる。

```markdown
## 指摘

- [項目 <番号>] <セクション名、または要求 ID>：<何が問題か>。直し方の案：<案>

## 扱われていない上流の要求 ID

- `<上流文書のパス>#<ID>`
```

指摘がなければ、それぞれに「なし」と書かせる。

## 依頼文の骨子

> あなたは開発文書のチェック役です。以下に転記した材料だけで判定してください。ファイルやリポジトリは開かないでください。書き手の意図や経緯は知らされていません。書かれていないことを補って読まず、書かれていないために読めない箇所は指摘してください。
>
> 対象の文書が、共通の規約とセクション規範に沿っているかを、チェック項目ごとに確かめ、出力形式に従って返してください。判定に迷う箇所は、指摘する側に倒してください。
>
> （以下、材料を転記）

## 指摘の扱い（作成、改訂のとき）

- 書いたエージェントが直す。直したら、直した後の文書で、同じ材料を渡して再チェックする。再チェックは、新しいサブエージェントでも、前回のサブエージェントの続きでもよい。
- 指摘がなくなるまで繰り返す。上限は 3 回。3 回で解消しなかった指摘は、ユーザーに報告する。
- 直すのに新しい意思決定やユーザーの知る事実が要る指摘は、推測で直さない。聞き取るか、未決定事項に入れる。
- 指摘が聞き取りの答えと食い違う（ユーザーが答えたことを「裏付けがない」と指摘されたなど）場合は、依頼文への転記漏れを疑い、転記を直して再チェックする。

## サブエージェントを使えないとき

サブエージェントを起動できない環境では、書いたエージェントが同じ材料と同じ項目で自分でチェックする。項目 2、3、6、7 は経緯を知っていても機械的に確かめられるが、項目 1、9、10 は見逃しうる。報告に、自分でチェックしたことと、前提の抜けを見逃しうることを添える。
