# チェック

書き上げた開発文書（作成、改訂）と、レビューを頼まれた開発文書のチェックの手順。

## 目的

**文書が、聞き取りの答えから外れていないかを確かめる。** 外れていれば、書いたエージェントが本文を直す。

チェックは、ユーザーに新しく聞くことを探す工程ではない。聞き取りで決まったことを掘り返したり、決まった範囲の外へ
論点を広げたりしない。聞き取りを終えたユーザーにとって、決めたことの理由や前提を問い直される設問は負担でしかない。

## 2 段で終える

1. **機械チェック** — `scripts/check.py` を 1 回走らせる。見出し、要求 ID、該当なし、未決定事項、上流への参照
2. **答えとの照合** — サブエージェント **1 体**。聞き取りの答えとの食い違いだけを見る

**規範との照合にサブエージェントを使わない。** 以前は 2 体目に `conventions.md`、セクション規範、上流文書の全文を
貼って照合させていた。材料が 30KB 近くになるうえ、出てくる指摘の多くは機械チェックで拾えるか、書くときに守れることで、
時間に見合わなかった。用語の統一、境界、形式、出典は、書き手が自分で見る（「書き手が目で見ること」）。

**再チェックはしない。** 指摘を直したら終わりにする。例外は 1 つだけで、「答えを貼り漏れていた」と分かったときに、
貼り直して同じサブエージェントにもう一度投げる場合である。

## 1. 機械チェック

```bash
python3 <この SKILL.md と同じディレクトリ>/scripts/check.py \
  --file docs/prd/data-export.md \
  --norm <同ディレクトリ>/references/prd.md \
  --upstream docs/prd/initial-launch.md
```

`!!` は直すもの、`--` は見て判断するものである。

| 見るもの | `!!` になる場合 |
| --- | --- |
| 見出し | セクション規範の表にある見出しが足りない、順序が違う |
| 要求 ID | 同じ番号を 2 回振っている |
| 該当なし | 理由が続いていない |
| 未決定事項 | 「未定」「検討中」「TBD」があるのに `OQ` の参照がない |
| 上流への参照 | `` `<path>#<ID>` `` の ID が、渡した上流文書に実在しない |

`--` に出るのは、規範に無い見出し（プロジェクト固有の節なら正しい）、要求 ID の欠番（改訂で消したなら正しい）、
参照先を渡していないので確かめられなかったもの（必要なら `--upstream` に足して再実行）である。

上流の項目の**漏れ**（どの下流文書からも参照されていない ID）は、このスクリプトでは見ない。文書 1 つでは決まらないので、
`conventions.md` の「上流の漏れの確かめ方」に従って、書き手が下流文書全体で確かめる。

## 2. 答えとの照合

会話の経緯を持たないサブエージェント 1 体に投げる。**書いた本人は、答えより強く言い切ったことや、答えにない理由を
書き足したことに気づきにくい。** 答えと文書だけを突き合わせる読み手なら、それを見つけられる。ここだけは代わりがない。

### 渡すもの

依頼文に貼って渡す。ファイルのパスは渡さず、ファイルやリポジトリを開かないよう伝える。リポジトリを見られると、
文書に書かれていないことをコードから補って判定してしまう。

- 対象の文書の全文
- 聞き取りの設問と答え。`ask-via-form` の `forms` の出力（設問の本文、選択肢とその説明、推奨）と、`history` の出力
  （回答）を、どちらもそのまま貼る。書き起こしたり要約したりしない。選択肢の説明や、選ばれなかった選択肢が落ちると、
  答えにあることを「裏付けがない」と誤って指摘される。**貼るのは、対象の文書のために出したフォームだけ。**
  同じセッションで複数の開発文書を書いたなら、ほかの文書のためのラウンドは貼らない
- 出どころの区分の見分け方（選択肢と推奨がある設問は意思決定、自由記述だけの設問はユーザーの知る事実、
  複数選択の候補は導出の採否で、選ばれなかった候補は採らないと決まったもの）
- 書き手が調べた事実（環境の事実、外部の事実）と、その出典。次の形で書く

  ```markdown
  ## 調べた事実

  - （環境の事実）`src/auth/` に認証のコードはまだない。`package.json` に `next@15.5`、`drizzle-orm@0.44`
  - （外部の事実）Google の ID トークンの `hd` クレームは、Workspace のドメインを表す。https://developers.google.com/identity/openid-connect/openid-connect （2026-09-15 参照）
  ```

- 改訂のときは、今回の変更の差分
- チェック項目と、このファイルの「出さない指摘」「出力形式」

**渡さないもの**: 会話の経緯（試行錯誤、却下した案、確定した答え以外のやりとり）。退けた指摘とその理由
（伝えると、次からその種の指摘を避けるようになり、見落としが増える）。

### チェック項目

- **答えとの対応**：出どころが意思決定、ユーザーの知る事実の記述が、聞き取りの答えと食い違っていないか。
  答えより強く言い切っていないか。答えにない数値、方針、日付、理由を書き足していないか。採られなかった選択肢の
  説明や推奨の理由を、決まったことの理由として流用していないか。
- **判定できる受け入れ条件**（Product Spec のときだけ）：受け入れ条件が、前提、操作、期待結果に分かれ、
  実装を見ずに合否を判定できる書き方になっているか。

改訂のときは、前者を**今回の変更の差分にだけ**適用する。変更していない箇所は、以前の聞き取りで確定したものとして扱う。

### 出さない指摘

- **決まったことの是非や前提を問う指摘** — 決めたのはユーザーであり、チェック役には判断する材料がない
- **事実そのものの正しさを疑う指摘** — 背景の事実、ユーザーの知る事実、調べた事実が本当に正しいかを疑うもの
- **聞いていない論点を足りないとする指摘** — 聞き取りで扱わなかったエッジケース、決めていない細部。それをこの文書の
  段で決めるべきかは、チェック役には判断できない
- **根拠を示せない指摘** — 食い違う答えを示せないもの（言い回しの好み、文の長さなど）

### 出力形式

**指摘だけを返させる。確かめた項目や、問題がなかったことは書かせない。**

```markdown
## 指摘

- <セクション名、または要求 ID>：<何が問題か>。根拠：<食い違う答え（フォーム id と設問）>。直し方の案：<案>
```

指摘がなければ「なし」の 1 行だけを返させる。

### 依頼文の骨子

> あなたは開発文書のチェック役です。以下に貼った材料だけで判定してください。ファイルやリポジトリは開かないでください。
>
> 対象の文書が、聞き取りの答えから外れていないかを、チェック項目ごとに確かめてください。聞き取りの答えは、
> ユーザーが決めたことです。その是非や前提を問うのは、あなたの役割ではありません。
>
> 指摘には、食い違う答えを根拠として必ず示してください。根拠を示せないものは指摘しないでください。
> 「出さない指摘」にあたるものは、気づいても書かないでください。直し方の案は、本文をどう直すかで書き、
> ユーザーに聞く案は書かないでください。
>
> **確かめたことは書かないでください。指摘だけを、出力形式のとおりに返してください。** 指摘がなければ「なし」とだけ書いてください。
>
> （以下、材料を貼る）

## 書き手が目で見ること

サブエージェントに回さない。書くときに守れることなので、書き終えたときに自分で一度通して見る。

- **出典** — 外部の事実（自社の外にある製品、サービス、市場の事実）に、URL と参照日があるか
- **境界** — 各セクションに、セクション規範の「書かないこと」にあたる内容が入っていないか
- **用語の統一** — 同じものが、文書の中でも上流文書との間でも、同じ語で呼ばれているか
- **指定された形式** — セクション規範が形式を指定しているところ（Design Doc のデータモデルの ER 図、
  API / Interface の型、技術設計の小見出しの中の並びなど）が、その形式で書かれているか
- **セキュリティの水準**（Design Doc のとき）— 個人情報や認可に触れる変更で、非機能要件に書かれているか

## 指摘の扱い

書いたエージェントが、会話の経緯を踏まえて指摘を選別し、本文を直す。**指摘を、ユーザーへの設問にしない。**

- **退ける**：根拠が示されていない指摘、「出さない指摘」にあたる指摘、聞き取りの答えを読み違えた指摘
- **答えに合わせる**：答えより強い記述は、答えの強さに合わせて弱める。答えにない理由、補足、数値は消す。
  書き足した記述の裏付けを、ユーザーに求めない
- **決定が要るものは未決定事項へ**：直すのに新しい意思決定やユーザーの知る事実が要る指摘は、推測で直さず入れる
- **聞き直してよいのは、矛盾と上流との食い違いだけ**：聞き取りの答えどうしが矛盾していて、どちらかに決めないと
  書けないときは、`ask-via-form` で聞き直す。そのときも、矛盾している答えを並べ、どちらを採るかだけを聞く。
  答えが上流文書の記述と食い違っているときも聞き直してよい（`sources-and-questions.md` の
  「答えが上流文書と食い違ったとき」）
- **食い違って見えたら貼り漏れを疑う**：ユーザーが答えたことを「裏付けがない」と指摘されたら、まず `forms` と
  `history` の出力をそのまま貼ったかを確かめる。貼り漏れがあれば、貼り直して同じサブエージェントに投げ直す

## レビューのとき

聞き取りの答えがないので、機械チェックを走らせたうえで、答えとの照合を次に置き換える。

- **根拠の示されない断定**：出どころが意思決定、ユーザーの知る事実の記述のうち、根拠が示されず、推測で埋めたように
  見える断定がないか（理由のない目標値、出どころの書かれない現状の数値、決めた人のわからない方針など）。

## サブエージェントを使えないとき

機械チェックは変わらず走らせる。答えとの照合は、書き手が `forms` と `history` を読み直して自分で行う。
自分の書き足しや言い換えを見逃しうるので、その旨を報告に添える。
