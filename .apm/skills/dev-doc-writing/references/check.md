# チェック

書き上げた開発文書（作成、改訂）と、レビューを頼まれた開発文書のチェックの手順。

## 目的

文書が、聞き取りの答え、共通の規約、セクション規範から外れていないかを確かめる。外れていれば、書いたエージェントが本文を直す。

チェックは、ユーザーに新しく聞くことを探す工程ではない。聞き取りで決まったことを掘り返したり、決まった範囲の外へ論点を広げたりしない。聞き取りを終えたユーザーにとって、決めたことの理由や前提を問い直される設問は負担でしかなく、文書もよくならない。

## 担い手

会話の経緯を持たないサブエージェントに任せる。

書いたエージェントは、答えより強く言い切ったことや、答えにない理由を書き足したことに気づきにくい。聞き取りの答えと文書だけを突き合わせる読み手なら、それを見つけられる。

一方で、経緯を知らない読み手は、書かれていない前提が本当に要るのか、背景の事実が正しいのか、決まったことが妥当なのかを判断できない。そこで、チェック項目は答えと規約に照らして食い違いを示せるものに限り、指摘の選別は経緯を知る書き手が行う。聞いたことが漏れなく文書に書かれているかは、経緯を知る書き手にしか確かめられないので、書き終えたときに書き手が自分で確かめる（SKILL.md の作成の手順 5）。

## 渡すもの

依頼文に貼って渡す。ファイルのパスは渡さず、ファイルやリポジトリを開かないよう伝える。リポジトリを見られると、文書に書かれていないことをコードから補って判定してしまう。

- 対象の文書の全文
- 上流文書の全文（なければ「上流文書なし」と伝える）
- 対象の文書のセクション規範（`prd.md`、`product-spec.md`、`design-doc.md` のいずれか）の全文
- 共通の規約（`conventions.md`）の全文
- このファイルの「チェック項目」「出さない指摘」「出力形式」
- 聞き取りの設問と答え（作成、改訂のとき）。`ask-via-form` の `forms` の出力（設問の本文、選択肢とその説明、推奨）と、`history` の出力（回答）を、どちらもそのまま貼る。書き起こしたり要約したりしない。選択肢の説明や、選ばれなかった選択肢が落ちると、答えにあることを「裏付けがない」と誤って指摘される。あわせて、出どころの区分の見分け方（選択肢と推奨がある設問は意思決定、自由記述だけの設問はユーザーの知る事実、複数選択の候補は導出の採否で、選ばれなかった候補は採らないと決まったもの）を伝える
- 書き手が調べた事実（環境の事実、外部の事実）と、その出典
- 改訂のときは、今回の変更の差分

## 渡さないもの

- 会話の経緯（試行錯誤、却下した案、ユーザーとのやりとりのうち確定した答え以外のもの）
- 前回のチェックの指摘と、それへの対応の経緯（再チェックでも、直した後の文書だけを渡す）

## チェック項目

1. **答えとの対応**：出どころが意思決定、ユーザーの知る事実の記述が、聞き取りの答えと食い違っていないか。答えより強く言い切っていないか。答えにない数値、方針、日付、理由を書き足していないか。採られなかった選択肢の説明や推奨の理由を、決まったことの理由として流用していないか。
2. **出典**：外部の事実に出典（URL と参照日）があるか。
3. **上流との対応**：上流文書の要求 ID のうち、この文書で扱われておらず、扱わない旨も概要に書かれていないものはないか。
4. **判定できる受け入れ条件**：受け入れ条件が、前提、操作、期待結果に分かれ、実装を見ずに合否を判定できる書き方になっているか（Product Spec のとき）。
5. **境界**：各セクションに、セクション規範の「書かないこと」にあたる内容が入っていないか。
6. **該当なしの理由**：「該当なし」に理由があるか。「調べられなかった」「決まっていない」が該当なしにされていないか。
7. **未決定事項の漏れ**：本文の「未定」「検討中」「TBD」など、決まっていないことを示す記述が、すべて未決定事項に載り、`OQ` で参照されているか。
8. **セキュリティの水準**：個人情報や認可に触れる変更で、非機能要件にセキュリティの水準が書かれているか（Design Doc のとき）。
9. **用語の統一**：同じものが、文書の中でも上流文書との間でも、同じ語で呼ばれているか。

### 改訂のとき

項目 1 は、今回の変更の差分にだけ適用する。変更していない箇所は、以前の聞き取りで確定したものとして扱う。

### レビューのとき

聞き取りの答えがないので、項目 1 を次に置き換える。

1. **根拠の示されない断定**：出どころが意思決定、ユーザーの知る事実の記述のうち、根拠が示されず、推測で埋めたように見える断定がないか（理由のない目標値、出どころの書かれない現状の数値、決めた人のわからない方針など）。

## 出さない指摘

次にあたるものは、気づいても指摘しない。

- **決まったことの是非や前提を問う指摘**：聞き取りで決まったことが妥当か、その理由は何か、前提は正しいかを問うもの。決めたのはユーザーであり、チェック役には判断する材料がない。
- **事実そのものの正しさを疑う指摘**：背景の事実、ユーザーの知る事実、書き手が調べた事実が本当に正しいかを疑うもの。
- **聞いていない論点を足りないとする指摘**：聞き取りで扱わなかったエッジケース、決めていない細部、書かれていない前提を、足りないとするもの。それをこの文書の段で決めるべきかは、チェック役には判断できない。
- **根拠を示せない指摘**：食い違う答えも、規約やセクション規範の該当箇所も示せないもの（言い回しの好み、文の長さなど）。

## 出力形式

サブエージェントには、次の形で返させる。指摘には、根拠を必ず添えさせる。直し方の案は本文をどう直すかで書かせ、ユーザーに聞く案は書かせない。指摘を設問にしないためである。

```markdown
## 指摘

- [項目 <番号>] <セクション名、または要求 ID>：<何が問題か>。根拠：<食い違う答え（フォーム id と設問）、または規約やセクション規範の該当箇所>。直し方の案：<案>

## 扱われていない上流の要求 ID

- `<上流文書のパス>#<ID>`
```

指摘がなければ、それぞれに「なし」と書かせる。

## 依頼文の骨子

> あなたは開発文書のチェック役です。以下に貼った材料だけで判定してください。ファイルやリポジトリは開かないでください。
>
> 対象の文書が、聞き取りの答え、共通の規約、セクション規範から外れていないかを、チェック項目ごとに確かめ、出力形式に従って返してください。指摘には、食い違う答えか、規約やセクション規範の該当箇所を、根拠として必ず示してください。根拠を示せないものは指摘しないでください。「出さない指摘」にあたるものは、気づいても書かないでください。直し方の案は、本文をどう直すかで書き、ユーザーに聞く案は書かないでください。
>
> 聞き取りの答えは、ユーザーが決めたことです。その是非や前提を問うのは、あなたの役割ではありません。
>
> （以下、材料を貼る）

## 指摘の扱い（作成、改訂のとき）

書いたエージェントが、会話の経緯を踏まえて指摘を選別し、本文を直す。**指摘を、ユーザーへの設問にしない。**

- **退ける**：根拠が示されていない指摘、「出さない指摘」にあたる指摘、聞き取りの答えを読み違えた指摘は、直さずに退ける。
- **答えに合わせる**：答えより強い記述は、答えの強さに合わせて弱める。答えにない理由、補足、数値は、消す。書き足した記述の裏付けを、ユーザーに求めない。
- **規約に合わせる**：出典、上流との対応、境界、該当なし、未決定事項、用語の指摘は、本文を直す。
- **決定が要るものは未決定事項へ**：直すのに新しい意思決定やユーザーの知る事実が要る指摘は、推測で直さず、未決定事項に入れる。
- **聞き直してよいのは矛盾だけ**：聞き取りの答えどうしが矛盾していて、どちらかに決めないと文書を書けないときだけ、`ask-via-form` で聞き直す。そのときも、矛盾している答えを並べ、どちらを採るかだけを聞く。
- **食い違って見えたら貼り漏れを疑う**：ユーザーが答えたことを「裏付けがない」と指摘されたら、まず `forms` と `history` の出力をそのまま貼ったかを確かめる。貼り漏れがあれば、貼り直して再チェックする。

直したら、直した後の文書で、同じ材料を渡して再チェックする。再チェックは、新しいサブエージェントでも、前回のサブエージェントの続きでもよい。直すべき指摘がなくなるまで繰り返す。上限は 3 回で、3 回で解消しなかった指摘はユーザーに報告する。

## サブエージェントを使えないとき

サブエージェントを起動できない環境では、書いたエージェントが同じ材料と同じ項目で自分でチェックする。項目 2、3、6、7 は経緯を知っていても機械的に確かめられるが、項目 1 と 9 は、自分の書き足しや言い換えを見逃しうる。報告に、自分でチェックしたことと、答えとの食い違いを見逃しうることを添える。
