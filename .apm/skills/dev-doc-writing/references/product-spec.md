# Product Spec のセクション規範

Product Spec は、作るものがどのように振る舞うのかを記す。読み手は人間のレビュアーと実装エージェントの両方である。**人が通して読める長さであることを、網羅より優先する。** 素直に実装すれば同じになる振る舞いまで書くと、人は読み切れず、本当に決めたことが埋もれる。

文字数の目安: 6000

## セクション

次のセクションを、この順で置く。

| セクション | 書くこと | 書かないこと | 出どころ |
|---|---|---|---|
| 概要 | 何の振る舞いを定める文書か | PRD の背景の繰り返し、上流の要求 ID の一覧 | 導出 |
| ユーザーフロー | ユースケースを、どの画面と操作の順に達成するか。対応するユースケース | 画面の見た目の細部 | 意思決定、導出 |
| Functional Specification | 実装によって答えが割れる、外から観測できる振る舞い。対応する機能要求 | 内部の実現方式（Design Doc）、素直に実装すれば同じになる振る舞い | 導出、意思決定（振る舞いの選択） |
| 確認シナリオ | 人が通しで試して、できあがりを確かめる手順 | Functional Specification の言い直し、実装方法、テストの層 | 導出（採否はユーザー） |
| 未決定事項 | 答えのない意思決定と事実。関わるセクションと、次に聞く先 | 決まったこと | 聞き取りで答えがなかったもの |

次のセクションは**任意**で、書くことがあるときだけ置く（`conventions.md` の「見出し」）。

| セクション | 書くこと | 書かないこと | 出どころ |
|---|---|---|---|
| 画面 | 新しく作る画面や変える画面の一覧と、デザインファイルなど参照先 | 振る舞いの規定（Functional Specification） | 意思決定、ユーザーの知る事実、環境の事実 |
| エッジケース | 実装で判断が分かれるところと、そのときの振る舞い | 上流や Functional Specification から一意に決まるもの、自明なもの | 導出 |

画面はユーザーフローの後に、エッジケースは Functional Specification の後に置く。

## セクションごとの注意

### 概要

- 何の振る舞いを定める文書かを、2〜3 文で書く。
- 上流文書の一覧や、扱う要求 ID、扱わない要求 ID を並べない。上流との対応は、ユーザーフローと Functional Specification の各項目の参照で表す（`conventions.md` の「上流の項目への参照」）。

### ユーザーフロー

- `UF-<番号>` を振り、実現するユースケースを添える（`` `docs/prd/data-export.md#UC-1` ``）。上流文書がなければ、フローの目的を 1 行で書く。
- 画面と操作の順に書く。分岐が多ければ、Mermaid のフローチャートを使ってよい。
- 各画面の見た目の細部は書かない。

### 画面（置くときだけ）

- 新しく作る画面と変える画面を、1 行ずつ並べる。関わる Functional Specification を添える。
- デザインファイル、既存画面、参考にする他製品があれば、リンクと、そこから何を読み取るべきかを添える（「色とレイアウトはこのファイルに従う。文言は Functional Specification を正とする」など）。
- リンク先はユーザーの知る事実か、環境の事実である。推測でリンクや画面名を作らない。

### Functional Specification

**書くのは、実装によって答えが割れる振る舞いだけである。** 全部の振る舞いを列挙しない。AI は抽象的な指示からでも筋のよい実装をするので、文書に要るのは、人間と違う判断をしそうなところである。

- `FS-<番号>` を振り、対応する機能要求を添える（`` `docs/prd/data-export.md#FR-2` ``）。
- 「<状態>で、<入力や操作>を受けると、<観測できる結果>になる」の形で書く。観測できる結果とは、画面の表示、通知、保存されて後から確かめられる結果、API の応答などである。テストはこの項目から導くので、合否を判定できる書き方にする。
- 次のものは書かない。
  - 機能要求をそのまま実装すれば同じになる振る舞い（「名前を押すと、そのメモが開く」「作成した直後は 0 件である」）
  - 同じ種類の製品なら同じになる振る舞い（一覧への即時の反映、保存後に再起動しても残ること）
  - 言語、フレームワーク、HTTP の既定で決まること
- 順に評価して結果を返す判定（どの条件でどの結果を返すか）は、「判定」と「返す理由」の表にする（`conventions.md` の「表、箇条書き、文章を使い分ける」）。
- 内部の実現方式（どのテーブルに書くか、どのジョブで処理するか）に触れない。それは Design Doc に書く。
- 振る舞いに複数の妥当な選択があるとき（失敗時に再試行するか、ユーザーに知らせるかなど）は、意思決定として聞き取る。

### エッジケース（置くときだけ）

**目的は、実装で判断が分かれるところを先に決めておくことである。** 分かれないものは書かない。網羅することが目的ではない。

- `EC-<番号>` を振り、採ったものごとに、そのときの振る舞いを書く。
- **書くのは、同じ入力に対して妥当な振る舞いが 2 通り以上あり、どちらかに決めないと実装できないものだけ。**
  重複して登録されたとき、同時に操作されたとき、上限にちょうど達したとき、外部サービスが失敗したときに再試行するか、
  権限のない人に「無い」と見せるか「見られない」と見せるか、などである。
- 次のものは書かない。
  - Functional Specification から一意に導けるもの
  - 言語、フレームワーク、HTTP の既定で決まるもの（必須の項目が空ならエラー、など）
  - 「不正な入力はエラーにする」のように、どの製品でも同じになるもの
  - 起こりえない組み合わせ
- **目安は Functional Specification 1 件につき多くて 2〜3 件。** これを大きく超えるなら、エッジケースが多いのではなく
  **Functional Specification の書き方が曖昧**な可能性が高い。先にそちらを直すほうが早い。
- 候補を聞くときは、**迷うものだけを候補に出す**（`sources-and-questions.md` の「導出した候補の採否を聞くとき」）。
  自明なものを候補に並べると、選ぶ側の負担だけが増える。

### 確認シナリオ

人が通しで試して、できあがりを確かめるための手順である。**Functional Specification ごとに書かない。** 項目ごとの受け入れ条件は分量の大半を占めるのに、言い直しが多く、人は網羅的に読めない。項目ごとのテストは、実装エージェントが Functional Specification から導く。

- `CS-<番号>` を振り、**全体で 3〜5 本**にする。主なユーザーフローごとに 1 本を基本にし、壊れると困る組み合わせがあれば足す。
- 前提、操作、確かめることの 3 つに分けて書く。
- 確かめることには、外から観測できる事実だけを書く。「正しく処理される」「問題なく表示される」のように、合否を判定できない書き方をしない。
- 実装方法やテストの層（ユニット、E2E など）には触れない。

```markdown
- **CS-1**（UF-1）
  - 前提：投稿が 1 件以上あるユーザーがログインしている
  - 操作：設定画面の「データ管理」で「エクスポート」を押し、届いたメールのリンクを開く
  - 確かめること：10 分以内にメールが届き、ダウンロードしたファイルに全投稿が入っている
```

## 骨組み

```markdown
# <機能名> Product Spec

## 概要

## ユーザーフロー

## Functional Specification

## 確認シナリオ

## 未決定事項
```
