# Product Spec のセクション規範

Product Spec は、作るものがどのように振る舞うのかを記す。読み手は人間のレビュアーと実装エージェントの両方である。受け入れ条件は、テストケースを導く元（契約）として使われるので、判定できることを読みやすさより優先する。

## セクション

次のセクションを、この順ですべて置く。

| セクション | 書くこと | 書かないこと | 出どころ |
|---|---|---|---|
| 概要 | 何の振る舞いを定める文書か | PRD の背景の繰り返し、上流の要求 ID の一覧 | 導出 |
| ユーザーフロー | ユースケースを、どの画面と操作の順に達成するか。対応するユースケース | 画面の見た目の細部（UI / UX References） | 意思決定、導出 |
| Functional Specification | 入力や状態に応じた、外から観測できる振る舞い。対応する機能要求 | 内部の実現方式（Design Doc） | 導出、意思決定（振る舞いの選択） |
| UI / UX References | デザインファイル、既存画面、参考にする他製品へのリンクと、そこから何を読み取るべきかの注記 | 振る舞いの規定（Functional Specification） | ユーザーの知る事実、環境の事実 |
| エッジケース | 実装やテストで判断が分かれるところと、そのときの振る舞い | 上流や Functional Specification から一意に決まるもの、自明なもの | 導出 |
| 受け入れ条件 | 振る舞いが満たされたかを、実装を見ずに判定できる条件 | 実装方法、テストの層 | 導出（採否はユーザー） |
| 未決定事項 | 答えのない意思決定と事実。関わるセクションと、次に聞く先 | 決まったこと | 聞き取りで答えがなかったもの |

## セクションごとの注意

### 概要

- 何の振る舞いを定める文書かを、2〜3 文で書く。
- 上流文書の一覧や、扱う要求 ID、扱わない要求 ID を並べない。上流との対応は、ユーザーフローと Functional Specification の各項目の参照で表す（`conventions.md` の「上流の項目への参照」）。

### ユーザーフロー

- `UF-<番号>` を振り、実現するユースケースを添える（`` `docs/prd/data-export.md#UC-1` ``）。上流文書がなければ、フローの目的を 1 行で書く。
- 画面と操作の順に書く。分岐が多ければ、Mermaid のフローチャートを使ってよい。
- 各画面の見た目の細部は書かず、UI / UX References を参照する。

### Functional Specification

- `FS-<番号>` を振り、対応する機能要求を添える（`` `docs/prd/data-export.md#FR-2` ``）。
- 「<状態>で、<入力や操作>を受けると、<観測できる結果>になる」の形で書く。観測できる結果とは、画面の表示、通知、保存されて後から確かめられる結果、API の応答などである。
- 順に評価して結果を返す判定（どの条件でどの結果を返すか）は、「判定」と「返す理由」の表にする（`conventions.md` の「表、箇条書き、文章を使い分ける」）。
- 内部の実現方式（どのテーブルに書くか、どのジョブで処理するか）に触れない。それは Design Doc に書く。
- 振る舞いに複数の妥当な選択があるとき（失敗時に再試行するか、ユーザーに知らせるかなど）は、意思決定として聞き取る。

### UI / UX References

- デザインファイル、既存画面、参考にする他製品へのリンクを並べ、それぞれから何を読み取るべきかを注記する（「色とレイアウトはこのファイルに従う。文言は Functional Specification を正とする」など）。
- リンク先はユーザーの知る事実か、環境の事実（リポジトリ内の既存画面など）である。推測でリンクや画面名を作らない。
- 参照するものがなければ「該当なし」と理由を書く。

### エッジケース

**目的は、実装とテストで判断が分かれるところを先に決めておくことである。** 分かれないものは書かない。
網羅することが目的ではない。

- `EC-<番号>` を振り、採ったものごとに、そのときの振る舞いを書く。
- **書くのは、同じ入力に対して妥当な振る舞いが 2 通り以上あり、どちらかに決めないと実装できないものだけ。**
  重複して登録されたとき、同時に操作されたとき、上限にちょうど達したとき、外部サービスが失敗したときに再試行するか、
  権限のない人に「無い」と見せるか「見られない」と見せるか、などである。
- 次のものは書かない。
  - Functional Specification から一意に導けるもの
  - 言語、フレームワーク、HTTP の既定で決まるもの（必須の項目が空ならエラー、など）
  - 「不正な入力はエラーにする」のように、どの製品でも同じになるもの
  - 起こりえない組み合わせ
- **目安は Functional Specification 1 件につき多くて 2〜3 件。** これを大きく超えるなら、エッジケースが多いのではなく
  **Functional Specification の書き方が曖昧**な可能性が高い。先にそちらを直すほうが早い。
- 候補を聞くときは、**迷うものだけを候補に出す**（`sources-and-questions.md` の「導出した候補の採否を聞くとき」）。
  自明なものを候補に並べると、選ぶ側の負担だけが増える。

### 受け入れ条件

- `AC-<番号>` を振り、確かめる対象の `FS-<番号>` や `EC-<番号>` を添える。
- 前提、操作、期待結果の 3 つに分けて書く。前提の欄があると、前提を書き忘れた条件が目に見える。前提の抜けは、そのままテストの穴になる。
- 期待結果には、外から観測できる事実だけを書く。「正しく処理される」「問題なく表示される」のように、合否を判定できない書き方をしない。
- 実装方法やテストの層（ユニット、E2E など）には触れない。

```markdown
- **AC-2**（FS-1）
  - 前提：投稿が 1 件以上あるユーザーがログインしている
  - 操作：設定画面の「データ管理」で「エクスポート」を押す
  - 期待結果：10 分以内に、ダウンロードリンクを含むメールが登録アドレスに届く
```

## 骨組み

```markdown
# <機能名> Product Spec

## 概要

## ユーザーフロー

## Functional Specification

## UI / UX References

## エッジケース

## 受け入れ条件

## 未決定事項
```
