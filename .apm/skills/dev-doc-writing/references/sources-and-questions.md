# 出どころと、聞き取りの設問の組み立て方

## 出どころ

開発文書のセクションの中身は、次の 5 つの出どころのどれかから持ってくる。各セクションの出どころは、セクション規範の表に書いてある。

### 意思決定

ユーザーだけが決められる中身。背景、製品原則、スコープ、目標値、スケジュールなど。

- 聞き取りで聞く。選択肢と推奨を示してよいが、決めるのはユーザー。
- 答えがなければ、推測で埋めずに未決定事項に入れる。

### ユーザーの知る事実

ユーザーは知っているが、リポジトリを調べても Web で探しても出てこない事実。今の解約率、デザインファイルの場所、法務から求められている制約など。

- 聞き取りで聞く。候補や例の値を示さない。AI が「5% くらいですか」と候補を出すと、それに引きずられた答えと本当の事実を区別できなくなり、それ自体が捏造への誘導になる。
- 答えがなければ、未決定事項に入れる。

### 環境の事実

作業対象のリポジトリなど、手元の環境を調べれば確かめられる中身。既存実装の構造、今のデータモデル、既存画面の有無など。

- 自分で調べる。調べればわかることをユーザーに聞かない。
- 調べた結果は、聞き取りの前提としてユーザーに示す。

### 外部の事実

Web など外部を調べて確かめる中身。市場の規模、競合製品の機能など。

- 調べて、出典（URL と参照日）を付ける。出典のない外部の事実は書かない。
- 調べる手段がなければ、聞き取りでユーザーに資料や URL を求める。得られなければ未決定事項に入れる。AI の知識だけで書かない。「該当なし」にもしない（「書くことがない」と「調べられなかった」は違う）。

### 導出

確定した前提から AI が洗い出せる中身。エッジケース、エラーの種類、代替案、段階的な公開の手順など。

- 候補を洗い出し、採否をユーザーに委ねる。ただし、**いま書いている文書のセクションにある中身だけ**を洗い出す（「この段で決めることだけを聞く」）。
- 前提から一意に決まるなら、聞かずに書いてチェックに回す。候補が 1 つしかない設問は作らない。
- 洗い出すときの前提（上流文書、聞き取りの答え、調べた事実）が変わったら、洗い出し直す。

### 判定に迷ったとき

- **意思決定か、導出か**：別の妥当な答えがあり、どれを選ぶかで文書の中身が変わるなら、意思決定として聞く。前提から一意に決まるなら、導出として書き、チェックに回す。
- **ユーザーの知る事実か、環境の事実か**：まず調べる。調べて出てこなければ、ユーザーの知る事実として聞く。調べずに聞くと、ユーザーの時間を無駄にする。聞かずに諦めると、事実が抜ける。
- **1 つのセクションに複数の出どころが混ざる**：記述ごとに出どころを判定する。たとえば背景の「今の状況」はユーザーの知る事実、「なぜ今やるのか」は意思決定である。

## この段で決めることだけを聞く

**設問にしてよいのは、いま書いている文書のセクションに書くことだけである。** セクション規範の表の「書くこと」に
当たらないものは、答えが要るとわかっていても聞かない。下流の文書で決まるからである。

| いま書いている文書 | この段で決めること | 下流に送ること |
| --- | --- | --- |
| PRD | 何を、なぜ、誰のために作るか。どこまで扱うか。外から課される制約 | 振る舞いの細部、画面と操作、エッジケース、異常系、境界値、測れる目標値、技術の選択 |
| Product Spec | 入力と状態に応じた振る舞い、エッジケースの採否、受け入れ条件 | 実現方式、データモデル、API の形、性能の目標値 |
| Design Doc | 実現方式、データモデル、契約、非機能要件の目標値、段階的な公開 | （下流はない。決められないものは未決定事項に入れる） |

PRD を書いていて「エラーのときどうするか」「上限を超えたらどうするか」「何件まで許すか」を聞きたくなったら、
それは Product Spec の段である。**聞かずに進み、必要なら Product Spec を書くときに聞く。**

**下流に送るものは、未決定事項にも入れない。** 未決定事項は「この段で決めるべきなのに答えがない」ものを置く場所であり、
「この段では決めない」ものを置く場所ではない。後者を入れると、未決定事項が下流の作業一覧になる。

## 聞き取りの前にすること

1. 上流文書から、すでに決まっていることを拾う。決まっていることは聞き直さない。
2. 環境の事実と外部の事実を調べる。
3. 残った意思決定、ユーザーの知る事実、導出した候補の採否を、設問にする。

## 設問の組み立て方

設問の中身はこのスキルが組み立て、`ask-via-form` のフォーム定義にして渡す。フォームの出し方、回答の待ち方、セッションの扱いは `ask-via-form` に従う。`ask-via-form` の判断でチャットで聞くことになった場合（リモート環境など）も、設問の中身は同じ規則で組み立てる。

フォーム定義は、リポジトリの中にファイルとして書かず、標準入力から渡す（`post -`）。利用する側のリポジトリに、開発文書以外のファイルを増やさないためである。

### 意思決定を聞くとき

- 互いに排他的な選択肢を 2〜4 個、`options` に書く。選択肢ごとの意味やトレードオフは `description` に書く。
- 推奨を 1 つ選んで `recommended` に、理由を `reason` に書く。理由には、上流文書、調べた事実、ほかの答えなど、根拠を書く。
- 選択肢にない答えは補足欄で書けるので、`"text": "none"` にしない。

### ユーザーの知る事実を聞くとき

- `options` も `recommended` も書かず、自由記述だけにする。`body` に例の値も書かない。
- `body` に、何を知りたいのかと、どこに使うのかを書く（例: 「背景の『今の状況』に書く、直近 3 か月の月次解約率」）。

### 導出した候補の採否を聞くとき

- 洗い出した候補を `options` に並べ、`"multiple": true` にして、採るものを選んでもらう。
- 候補ごとに、なぜ候補に挙げたのかを `description` に 1 行書く。
- 候補にないものは、補足欄に書いてもらう。
- **候補は、迷うものだけを出す。** 前提から一意に決まるもの、その分野で既定が決まっているもの、どの製品でも同じになるものは
  候補に入れない。自明な候補を並べると、選ぶ側の負担だけが増える（Product Spec のエッジケースで起きやすい。`product-spec.md` の「エッジケース」）。
- **候補を 1 件ずつ設問にせず、領域ごとに 1 問にまとめる**（「セキュリティの振る舞いのうち、今回入れるもの」「切り替え時に確かめること」など）。Design Doc は導出が多く、1 件ずつ聞くと設問が爆発する。10 個を超える候補でも、複数選択の 1 問なら 1 往復で決まる。
- **採否を聞く対象は、その文書のセクションにあるものだけ。** PRD ならユースケースと機能要求の候補までで、エッジケースや異常系の候補は出さない（「この段で決めることだけを聞く」）。

### すべての設問に共通すること

**フォームは、会話の文脈を持たない人が読む。** その設問だけを見て答えられる形にする。
`body` を次の 3 つで書く。どれも 1〜3 行にとどめる。

1. **前提** — いま分かっていること。上流文書で決まっていることは、パスと要求 ID を添えて引用する。調べた事実なら、どこで調べたかを添える
2. **問い** — 何を決めてほしいか、何を教えてほしいか
3. **効き先** — この答えが、文書のどこをどう変えるか

**その設問に効く前提を `intro` にまとめない。** `intro` は最初に 1 回しか読まれず、設問を読むときには視界から外れている。
`intro` に置くのは全体に効くことだけ（場面、書く文書、調べた結果の一覧）で、設問ごとの前提は `body` に書く。

```json
{
  "id": "scope-corp",
  "title": "スコープ：法人向けプランを今回扱うか",
  "body": "背景では、解約の主因を『エクスポートできないこと』としています。法人向けプランには、管理者が全メンバーの投稿をまとめて持ち出す要求があり、個人向けとは権限の扱いが変わります。\n\n今回のスコープに法人向けプランを含めますか。\n\nこの答えで、スコープの『扱わないもの』と、ユースケースの数が変わります。",
  "options": [
    {"label": "個人向けだけを扱う", "description": "権限の設計が要らず、今回の範囲が小さくなる。法人向けは次の PRD に送る"},
    {"label": "法人向けも含める", "description": "管理者の権限と、他人の投稿をどこまで含めるかを決める必要がある"}
  ],
  "recommended": "個人向けだけを扱う",
  "reason": "背景の課題（個人ユーザーの解約）には個人向けで足りるため。"
}
```

- 設問の `title` の頭に、使うセクションを書く（例: `スコープ：法人向けプランを今回扱うか`）。回答は設問のタイトル付きで返ってくるので、あとで読み直すときも、どのセクションの答えかがわかる。
- 社内の略語や、この文書で初めて出す語は、設問の中で定義する。知っている前提で書かない。
- 調べた事実の一覧は `intro` に置き、誤りがあれば全体メモに書いてもらうよう頼む。
- **`intro` に「ここでは聞かないこと」を書く。** 下流に送った論点（PRD なら画面、エッジケース、目標値、技術の選択）を挙げ、
  どの段で決めるかを添える。細部を聞かれないことが不安に見えるのを防ぎ、答える側が「今は答えなくてよい」と判断できる。
- 答えがわからないとき、まだ決まっていないときは保留にし、誰が決めるか（誰が知っているか）を理由に書いてもらうよう、`intro` で頼む。

### 1 フォームの設問数

**1 フォームは 7 問までにする。** 超えるなら、**それが無いと文書を書けないもの**から出す。残りは書いてから、
本当に要るものだけを草稿を見せて聞く。書けるのに聞くと、答える側の負担だけが増える。

1. それが決まらないと、ほかの設問が作れないもの（場面、スコープ、対象ユーザ）
2. それが決まらないと、セクションが書けないもの（製品原則、スコープの線引き）
3. 導出した候補の採否（領域ごとに 1 問にまとめる）
4. 細部の数値や言い回し — **聞かない。** 書いて、チェックに回す

**上限に収めるために、1 つの設問へ複数の問いを詰め込まない。** 「どのシステムにあり、誰が、どの頻度で、何に困っているか」を
1 問にすると、答えのどれがどの問いに対応するのか分からなくなる。詰め込むくらいなら、草稿を見ながら聞く。

**同じことを 2 度聞かない。** 保留や未回答のまま聞き取りを終えるものは、未決定事項に送る。

## 回答状態の扱い

`ask-via-form` は、設問ごとに回答状態を返す。開発文書では次のように扱う。

| 回答状態 | 扱い |
|---|---|
| 回答、回答（推奨どおり） | 意思決定やユーザーの知る事実として、文書に書く。ただし、答えの中身が「わからない」「未定」なら、保留と同じに扱う |
| 保留 | 理由がほかの設問の答え待ちなら、その前提が決まってから聞き直す。聞ける設問がなくなった時点で保留のままなら、未決定事項に入れ、理由に書かれた「誰が決めるか」を、次に聞く先として添える |
| 差し戻し | 回答ではない。チャットで返事をして前提を解消する。同じフォームに残った設問は、そのまま出し直さず、前提が変わったものを作り直して聞く。聞き取りを終える時点で解消していなければ、未決定事項に入れる |
| 未回答 | 要るなら聞き直す。聞き取りを終える時点で未回答のままなら、未決定事項に入れる |

全体メモやチャットで「ここまでで十分」のように打ち切りを示されたら、残りは聞かない。まだ答えのない中身は未決定事項に入れて書く。

## 答えが上流文書と食い違ったとき

聞き取りの答えが、上流文書に書かれていることと食い違うことがある（上流の Product Spec が「所属組織で判定する」と書いているのに、答えが「Google の `hd` クレームだけを見る」だった、など）。上流を正として答えを捻じ曲げても、答えを正として上流を黙って置き去りにしても、どちらかの文書が実態と食い違ったまま残る。

草稿を見ながら詰めるときに、1 つの論点にして聞く。

- 上流文書の記述（パスと要求 ID、本文の引用）と、今回の答えを並べる。
- 案は「上流文書を改訂して、今回の答えに合わせる」「今回の答えを、上流文書に合わせる」の 2 つにする。
- 上流を改訂すると決まったら、書いている文書を書き終えてから、上流文書を `SKILL.md` の「改訂」の手順で直す。上流の改訂は、ほかの下流文書への反映まで辿ることになるので、書きかけの文書と混ぜない。

これは、答えどうしの矛盾（`check.md` の「指摘の扱い」）と同じく、聞き直してよい場面である。決まったことの是非を問い直すことにはあたらない。

## 聞き取りの組み方

聞き取りは、最初のフォームと、草稿を見ながらのチャットの 2 段に分ける。

1. 答えがほかの設問に左右されない設問を集め、1 つのフォームにまとめて出す。7 問を超えるなら、優先順位の上から 7 問だけを出す（「1 フォームの設問数」）。
2. 回答を受けたら、草稿を書く。答えのない項目は未決定事項に入れる。
3. 新たに聞けるようになった論点と、聞き直す設問（保留、差し戻し、未回答）を、草稿を見ながら詰める。答えによって不要になった設問は捨てる。

答えがまだ出ていない設問を先回りして聞かない。前提が決まる前の答えは、決まった後に覆りやすい。

外部の事実の調査に時間がかかるときは、調査の結果を待たずに聞き取りを始めてよい。調査に左右されない設問を先に出し、結果が届いた時点で、**同じフォームに設問を足す**（`ask-via-form` の「送信前のフォームに設問を足す」。同じ id で `post` し直すと、入力途中の回答は引き継がれる）。足す設問には `id` を明示し、末尾に足す。すでに送信されていたら、草稿を見ながら聞く。

文書ごとの典型的な依存は次のとおり。実際の依存は、上流文書と場面によって変わる。

- **PRD**：場面、対象ユーザ、背景 → スコープ、製品原則 → ユースケース → 機能要求、そのほか技術的要求 → リリーススケジュール、マーケティング計画
- **Product Spec**：上流の要求のうち扱う範囲 → ユーザーフロー → Functional Specification → エッジケースの採否 → 受け入れ条件の採否
- **Design Doc**：Goals / Non-goals → 技術設計の方式 → データモデル、API / Interface → 非機能要件の目標値 → Rollout / Migration

## 草稿を見ながら詰める

**前提の修正が 1 往復で進むように、チャットで 1 回に論点を 1 つだけ聞く。** ユーザーは聞き返しても、前提を直してもよい。前提が変わったら、後に続く論点を作り直す。

1 つの論点は、次の順で書く。

1. **場所** — 草稿のパスとセクションまたは要求 ID。該当箇所を短く引用する
2. **論点** — 何を決めてほしいか、何を教えてほしいか
3. **案と推奨** — 意思決定なら、案と推奨、その根拠を書く。ユーザーの知る事実なら、候補を示さない
4. **効き先** — 答えが、草稿のどこをどう変えるか

**前提の点検は、聞く前に書き手が行う。** フォームの設問も同じである。

- 前提に使えるのは、草稿、上流文書、調べた事実（出典つき）、ユーザーの発言だけである。
- それ以外の前提は、先に草稿へ書くか、「AI の解釈」と明記して聞く。人の目に入らない前提は、人が否定できない。
- 指し示せないことを「決まっています」と書かない。依頼文やチャットで聞いた事実を使うときは、草稿に書いてから聞く。
- 「ラウンド 1 で」「Q3 で」のように過去のやり取りを指さない。人はそこへ確認しに行かない。

## 答えの控え

**人が見る控えは草稿である。** 決まったことは草稿に反映し、人に `forms` や `history` を読ませない。

チェック役に渡す控えは、次の 3 つである。リポジトリに控えのファイルを作らない。会話の記憶から書き起こさず、書くときも、チェック役に渡すときも、これらを読み直す。

- `ask-via-form` の `forms`（出したフォーム定義）
- `ask-via-form` の `history`（送信された回答）
- チャットで示した論点と、ユーザーの返事の原文

使うセクションは、設問のタイトルからわかる。出どころの区分は、回答形式から見分けられる（選択肢と推奨がある設問は意思決定、自由記述だけの設問はユーザーの知る事実、複数選択の候補は導出の採否）。チャットの論点も同じように見分ける（案と推奨があれば意思決定、なければユーザーの知る事実）。
