# dev-doc-writing

開発文書（PRD、Product Spec、Design Doc）を書く、改訂する、レビューするときは、この手順に従う。

## 中心原理

**開発文書のすべての記述について、その中身をどこから持ってきたか（出どころ）を言えるようにする。**

AI に開発文書を書かせるときの一番のリスクは、もっともらしい捏造である。製品原則、スコープ、市場規模、目標値、スケジュールは、材料がなくても流暢に埋められてしまい、読み手はどこまでがユーザーの判断でどこからが推測かを区別できない。そこで、各セクションの中身を次の 5 つの出どころのどれかに割り当て、出どころごとに持ってき方を決める。

| 出どころ | 例 | 持ってき方 |
|---|---|---|
| 意思決定 | 背景、製品原則、スコープ、目標値 | ユーザーに聞く。選択肢と推奨は示してよいが、決めるのはユーザー |
| ユーザーの知る事実 | 今の数値、デザインファイルの場所、社内の制約 | ユーザーに聞く。候補を示さない |
| 環境の事実 | 既存実装、今のデータモデル | リポジトリを調べる |
| 外部の事実 | 市場分析、競合分析 | Web などで調べ、出典を付ける |
| 導出 | エッジケース、代替案、エラーの種類 | 確定した前提から洗い出し、採否をユーザーに委ねる |

意思決定とユーザーの知る事実に答えが得られなければ、推測で埋めずに未決定事項として残す。

出どころの判定と、聞き取りの設問の組み立て方: [references/sources-and-questions.md](references/sources-and-questions.md)

## 開発文書どうしの関係

PRD（何を、なぜ作るか）、Product Spec（どう振る舞うか）、Design Doc（技術的にどう実現するか）の順に、上流から下流へ並ぶ。

- 上流文書があれば必ず読み、下流の各項目から、応える上流の項目を要求 ID（`FR-1` など）で参照する。上流文書がなければ、下流を書くのに要る上流側の決定だけを聞き取って進める。PRD のない小さな機能の Spec や、改修のための Design Doc だけを書く場面はよくある。
- 下流文書は複数の上流文書を参照してよい。複数の Spec にまたがる共通基盤の Design Doc などがこれにあたる。

置き場所、要求 ID、参照の書き方、未決定事項、文書どうしの境界など、3 文書に共通の規約: [references/conventions.md](references/conventions.md) — **どの作業でも、始める前に読む。**

## 作業の判定

- 開発文書を書くよう頼まれた → [作成](#作成)
- 既存の開発文書を直すよう、または上流の変更を下流に反映するよう頼まれた → [改訂](#改訂)
- 開発文書のレビューを頼まれた → [レビュー](#レビュー)

「PRD から Design Doc まで書いて」のように複数の開発文書を頼まれたら、上流から 1 つずつ、聞き取りからチェックまでを終えてから次の文書に進む。下流の設問は上流で決まったことに左右されるので、まとめて聞くと答えようのない設問が混ざる。上流をチェックまで済ませてから進めば、下流が未確定の上流に引きずられない。

## 作成

### 1. 文書の種類と場面を確かめる

書く文書の種類と、場面を確かめる。場面は次のいずれか。

- 新規プロダクトの立ち上げ
- 既存プロダクトへの機能追加
- 社内ツールや個人開発
- 技術的な改修（リファクタリングや移行）

場面によって、書くことのないセクションが変わる（社内ツールの PRD のマーケティング計画、改修の Design Doc のデータモデルなど）。依頼と上流文書から判断できなければ、聞き取りの最初のラウンドで聞く。

種類に応じて、セクション規範を読む。

- PRD: [references/prd.md](references/prd.md)
- Product Spec: [references/product-spec.md](references/product-spec.md)
- Design Doc: [references/design-doc.md](references/design-doc.md)

### 2. 上流文書を探して読む

ユーザーが上流文書を指定していればそれを使う。指定がなければ、置き場所の規約（conventions.md）に沿って探す。候補が複数あって、どれが上流かを判断できなければ、聞き取りで確かめる。上流文書で決まっていることは、聞き直さずに前提として使う。

### 3. 環境の事実と外部の事実を調べる

聞き取りの前に、調べればわかることを調べる。調べた結果は設問にせず、聞き取りのフォームの前置き（`intro`）に前提として書く。ユーザーの時間を、調べればわかることに使わせないためである。

外部の事実を調べる手段（Web 検索など）がなければ、聞き取りでユーザーに資料や URL を求める。AI の知識だけで市場や競合を書くことはしない。それは中心原理が防ごうとしている捏造そのものである。

### 4. 聞き取る

意思決定、ユーザーの知る事実、導出した候補の採否を、`ask-via-form` スキルでフォームに出してユーザーに聞く。このスキルの手順が `ask-via-form` を使う明示的な指示にあたるので、ユーザーに「フォームで聞いて」と言われていなくても使う。

フォームの出し方、回答の待ち方、セッションの扱いは `ask-via-form` に従う。このスキルが決めるのは、何をどう問うかと、返ってきた回答状態（保留、差し戻しなど）を開発文書でどう扱うかである。どちらも [references/sources-and-questions.md](references/sources-and-questions.md) に従う。

- 聞き取りのセッションは、手順 7 の報告を終えるまで閉じない。答えどうしの矛盾が見つかったときに、聞き直すためである。複数の開発文書を続けて書くときは、同じセッションを使い続けてよい。
- フォーム定義や答えを、リポジトリの中にファイルとして残さない。利用する側のリポジトリに、開発文書以外のファイルを増やさないためである。フォーム定義は標準入力から渡し、設問と答えは `ask-via-form` の `forms` と `history` で読み直す。

### 5. 書く

セクション規範に沿って書く。

- 見出しは、セクション規範の表にあるものをすべて、その順に置く。書くことがないセクションは、見出しを残して「該当なし」と理由を 1 行書く。見出しがないと、読み手もチェック役も「検討して不要と判断した」のか「書き忘れた」のかを区別できない。
- 出どころが意思決定、ユーザーの知る事実の記述は、聞き取りの答えにあるものだけを、答えと同じ強さで書く。「ケースがある」という答えを「含まれている」と言い切らない。
- 答えにない理由や補足を書き足さない。推奨の理由や、採られなかった選択肢の説明を、決まったことの理由として流用しない。理由を書く必要があるのに答えにないなら、未決定事項に入れるか、理由を書かずに済ませる。
- 答えがなかった項目は、未決定事項に入れる。
- 規約（conventions.md）の「書き方」に従い、判定できる書き方をする。

書き終えたら、聞き取りで決まったことと、調べた事実が、漏れなく文書に書かれているかを自分で確かめる。設問と答えは、記憶に頼らず `forms` と `history` を読み直す。何を調べ、何を聞いたかを知っているのは書き手だけなので、この確認はチェック役に任せられない。

### 6. チェックする

会話の経緯を持たないサブエージェントに、文書が聞き取りの答え、共通の規約、セクション規範から外れていないかをチェックさせる。指摘は、経緯を知る自分が選別し、本文を直す。直すべき指摘がなくなるまで繰り返す（上限 3 回）。渡す材料、チェック項目、出さない指摘、指摘の扱い: [references/check.md](references/check.md)

書いた本人は、答えより強く言い切ったことや、答えにない理由を書き足したことに気づきにくい。答えと文書だけを突き合わせる読み手なら、それを見つけられる。一方で、経緯を知らない読み手は、決まったことの是非や前提の正しさを判断できない。そこで次のように扱う。

- 指摘を、ユーザーへの設問にしない。答えに合わない記述は、答えに合わせて弱めるか消す。
- 決定が要る指摘は、未決定事項に入れる。
- 聞き直してよいのは、聞き取りの答えどうしが矛盾していて、どちらかに決めないと書けないときだけである。

### 7. 報告する

ユーザーに次を報告する。

- 書いた文書のパス
- 未決定事項の一覧（要求 ID と、誰が決めるか）
- 上流文書があるときは、上流の要求 ID のうち、まだどの下流文書からも参照されていないもの（conventions.md の「上流の漏れの確かめ方」）。文書には書かない
- チェックで直したことの要約と、退けた指摘の件数（主な理由を添える）
- 3 回のチェックで解消しなかった指摘（あれば）
- サブエージェントを使えずに自分でチェックした場合は、その旨と、答えとの食い違いを見逃しうること

## 改訂

1. 変更の内容を確かめ、対象の文書と、その上流文書を読む。
2. 変更に新しい意思決定やユーザーの知る事実が要るなら、作成の手順 4 と同じく聞き取る。
3. 書き換える。要求 ID は振り直さない（conventions.md）。書き換えたら、作成の手順 6 と同じくチェックする。
4. 対象の文書のパスでリポジトリ全体を検索し、それを参照している下流文書と、参照されている要求 ID を洗い出す。下流文書ごとに改訂案を `ask-via-form` の設問として示し、ユーザーの了承を得てから書き換え、チェックする。下流の改訂に新しい意思決定が要るなら、聞き取りから始める。下流文書がさらに下流を持つ場合も、同じように辿る。
5. 作成の手順 7 と同じく報告する。反映した下流文書と、反映しなかった下流文書（とその理由）も含める。

## レビュー

1. 対象の文書と、その上流文書を集める。
2. サブエージェントにチェックさせる。聞き取りの答えがないので、チェック項目の一部を置き換える（check.md の「レビューのとき」）。
3. 指摘の一覧をユーザーに返す。文書は書き換えない。直すよう頼まれたら、改訂として扱う。
