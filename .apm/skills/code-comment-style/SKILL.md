# コードコメントの規範

## 規範の所在

コメントを書く前・評価する前に必ず読む。

```
references/norms.md(この SKILL.md と同じディレクトリ配下)
```

原則、書くべきコメントの類型（A〜K）、書くべきでないコメントの表、対象別の要約、評価に使う規約名がすべてそこにある。この SKILL.md には規範そのものは書かれていない。

読む主体とタイミングは次のとおり。

| 作業 | norms.md を読むか |
| --- | --- |
| 評価そのもの（良し悪しの判定） | **サブエージェントが読む。** 自分は読んでも判定しない |
| 指摘を受けてコメントを書く・直す | **読む。** 修正が規範のどの類型に当たるかを自分で判断するため |
| 起動の要否だけを判断する | 読まなくてよい。判断材料はこの SKILL.md に閉じている |

## 評価は必ずサブエージェントに任せる

**自分でコメントの良し悪しを判定しない。必ず Agent ツールでサブエージェントを起動し、判定を任せる。**

規範は「そのコードを初めて読む人」を基準に組み立てられている。「消したら誰が何を再発明するか」「初めて読む人に意図が伝わるか」は、実装の意図をすでに知っている側には原理的に判定できない。直前までそのコードを書いていたエージェントは、意図を思い出して補完してしまうため、不要なコメントを必要と判断し、不足しているコメントを足りていると判断する。**冷えた読み手として判定できるのは、そのコードを初めて読むサブエージェントだけ。**

自分で判定した結果は、規範を適用したことにならない。

### 二つのモード

入口によって、評価範囲と、指摘を反映するかどうかが変わる。評価をサブエージェントへ委譲する点は共通。

| | **変更完了モード** | **レビュー依頼モード** |
| --- | --- | --- |
| 入口 | 自分がコードを書き終えた | ユーザーがコメントのレビュー・整理を依頼した |
| 起動 | 下の条件に当てはまるときだけ | 常に起動する |
| 評価範囲 | 今回の変更箇所とその周辺（`git diff` / `git diff --staged`） | 依頼で名指しされた範囲（ファイル、ディレクトリ、PR）。diff は使わない |
| 修正 | 指摘を反映する | 依頼に修正の意図（「直して」「整理して」）が含まれるときだけ反映する。「見て」「レビューして」なら**指摘の提示で止める** |

依頼の文面から修正の要否が読み取れないときは、指摘を提示したうえで反映してよいか確認する。勝手に直さない。

### 変更完了モードの起動条件

コードの追加・変更を一通り書き終えた時点で、次のいずれかに当てはまれば起動する。

- コメントを追加・変更した
- 公開要素（型、関数、メソッド、フィールド、定数）を追加した
- 設定値・マイグレーション・CI 定義を追加・変更した
- テストを追加した

次だけの変更では起動しない。

- フォーマット、リネーム、import 整理
- コメントに触れていない既存ロジックの微修正

**起動の要否はどちらに転んでも報告する。** 起動しないなら、どの条件にも該当しなかったことを簡潔に述べる。黙って省略すると、規範を適用したのか忘れたのかがユーザーから区別できない。

判定は `git diff` の追加・削除行を見る。ハンクのコンテキスト行に現れる既存コメントは「変更した」に当たらない。

### 起動の仕方

`Agent` ツールを `subagent_type: "general-purpose"`、`run_in_background: false` で起動する。評価結果を受け取ってから作業を続けるため、同期実行にする。

プロンプトは次の型を使う。`<>` の箇所だけ埋める。

```
あなたはこのコードを初めて読む人です。実装の経緯や意図は一切知らない前提で評価してください。

1. `<このスキルの references/norms.md への絶対パス>` を読み、評価基準を把握する。
2. 評価対象を特定する。
   <対象の指定。例: リポジトリ /path/to/repo で `git diff` と `git diff --staged` を実行し、
   追加・変更された行とその周辺を対象とする>
3. 対象範囲の各コメントを norms.md の規約名で判定する。コメントが無いことによる不足
   （missing-* の規約名）も同じように指摘する。
4. 判定に迷ったら「このコメントを消したら、次に読む人は何を再発明するか」で決める。
   答えられないなら不要。

出力形式:
- 1 件につき `ファイル:行` / 規約名 / 一文の指摘 / 修正案（コメント本文、または「削除」）
- 行番号の昇順に並べる
- 規約に反していない書き方の好みは指摘しない
- 指摘が無ければ「指摘なし」とだけ返す

制約:
- ファイルを編集しない。指摘だけを返す。
- 実装の意図を推測で補わない。コードから読み取れなかったなら、
  読み取れなかったこと自体が unclear の指摘になる。
```

**プロンプトに実装の意図・背景・設計の経緯を書かない。** 「ここは〜のつもりで書いた」を渡した時点でサブエージェントは冷えた読み手ではなくなり、起動した意味が消える。渡してよいのは、評価対象の範囲の指定と規範のパスだけ。

範囲は上のモード表で決まる。差分に無関係な指摘が混ざるとレビューが散漫になるので、モードが定める範囲を自分の判断で広げない。

### 評価結果の扱い

指摘の種類によって既定の扱いが違う。

| 指摘 | 既定の扱い |
| --- | --- |
| 過剰（restate / episodic / out-of-scope / dead / over-doc） | **そのまま採用して消す。** 意図を知っている側は不要性を過小評価するため、ここで反論しない |
| 公開要素の doc が過剰 | 消さずに**契約か意図へ書き換える**。Go の revive など、公開要素に doc を要求する lint を壊さないため。書くべき契約も意図も見つからないなら、その要素が公開である必要を疑う |
| unclear | **反論しない。** 初めて読む人に伝わらなかったという事実がすべて。コメントを書き直す |
| nameable / typeable | コメントではなく**名前・型を直す**。コメントの修正で済ませない |
| stale / no-premise | コメントを実装に合わせる、または前提を書き足す |
| 不足（missing-*） | 内容を確認して採用する。冷えた読み手には見えない事情があるときだけ却下し、却下の理由をユーザーへ伝える |

採用しなかった指摘は、その理由とともにユーザーへ報告する。黙って落とさない。

### 再評価は 1 回まで

修正を反映したあと、コメントを大きく書き直した場合は、新規のサブエージェントをもう一度だけ起動して確認する（前のエージェントを継続しない。冷えた読み手でなくなるため）。**再評価は 1 回で打ち切る。**

2 回目の指摘は、次のように扱う。

- 1 回目で触っていない箇所への新規指摘 → 反映する
- **1 回目の指摘に従って書いた文への再指摘** → 書き換えを繰り返さない。両ラウンドの判定を並べてユーザーに提示し、判断を委ねる

同じ箇所を評価のたびに書き換えると、規範に収束せず往復するだけになる。ラウンドを重ねても消えない指摘は、規範の適用の問題ではなく、その箇所に書くべき情報が決まっていないという signal として扱う。

### 根拠が分からない指摘を推測で埋めない

根拠の記述を求める指摘（`missing-rationale` / `missing-intent` / `missing-whynot` / `missing-test-why`、および前提の追記を求める `no-premise`）には、**根拠がコードにもリポジトリ内の資料にも存在しない**ものが混じる。定数の由来、nil が「ルート」か「未取得」か、なぜその選択肢を捨てたか。サブエージェントの修正案も `<ルート / 未取得>` のような空欄で返ってくる。

ここでもっともらしい根拠を創作して書いてはいけない。**推測で書かれた根拠は、実装と食い違っても誰にも検知されない。** 規範がコメントの意図を重視するのは、意図が実装とズレたときに「実装が意図から外れた」という signal になるからで、その意図が最初から作り話ならこの仕組みは逆に働く。コメントが無い状態より確実に悪くなる。

根拠を確認できない項目は次のように扱う。

1. そのコメントは書かずに残す（空欄のまま埋めない）
2. 「根拠が確認できなかった項目」として箇条書きでユーザーに提示し、答えを聞く
3. 答えが得られてから書く

却下ではなく保留であることを明示する。git log、issue、関連コード、テストを当たって根拠が見つかるならそれを書いてよい。**見つけた根拠と、自分が妥当だと考えた推測とを混ぜないこと。**

`norms.md` の H は定数・設定値に値の根拠を書けと定めるが、根拠が確認できないときはこの節が優先する。空欄や当たり障りのない文言でコメントの形だけ整えるより、書かずに聞く。

**一般に確立した意味は推測ではない。** HTTP 429 がレート制限を表す、`context.Canceled` がキャンセルを表す、といった外部仕様で定まった意味は書いてよい。書けないのは**このプロジェクトがなぜそれを選んだか**。

- 書ける: 「429 はレート制限を表し、時間を置けば解消しうる」（HTTP の仕様）
- 書けない: 「4xx のうち 429 だけを再試行対象にしたのは〜のため」（このコードの判断）

## 完了手続き(スタンプ)

評価と指摘対応を終えたとき、または変更完了モードの起動条件に該当せず非該当を報告したとき — いずれの場合も `scripts/stamp-review.sh` を**対象リポジトリで**実行してスタンプを記録する(Stop hook がこれを確認する)。`CLAUDE_PROJECT_DIR` が別のリポジトリを指す環境では、対象リポジトリを指すよう上書きして実行する。レビュー依頼モードで評価を実施した場合も同様に記録する。

## Stop hook に block されたとき

「コメント評価が未実施」と block されたら、変更完了モードの起動条件を判定し、該当するなら評価を実施、非該当ならその旨を報告したうえで、スタンプを記録してから終了する。

## セットアップ(消費側プロジェクトへの導入)

このスキルの enforcement を有効化するよう依頼されたら:

1. `assets/hooks-settings.json` の内容を消費側の `.claude/settings.json` にマージする(Stop hook)。`command` のパスは、このスキルの実際の配置先に合わせて調整する。
2. `assets/claude-md-snippet.md` の一行を消費側の CLAUDE.md に追記する。

## 自分で書くとき

`references/norms.md` の「書く前の判断順序」に従う。要約すると、コメントを書きたくなったら次の順で疑う。

1. 名前・関数分割・型で言えないか
2. コミットログや ADR に属する情報ではないか
3. 読み手はこの下のコードを読むか（読むなら動作説明は不要）

書いたコメントの妥当性は自分で判定せず、上の手順でサブエージェントに評価させる。
