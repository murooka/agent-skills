## 原則

### 1. コメントは唯一の push チャネル

コミットログ、テスト、ADR、Wiki はすべて「読み手が取りに行く」もの。コメントだけは、そのコードを読む人全員に強制的に配達される。配達枠は希少資源なので、**読むたびに毎回必要になる情報**だけを載せる。一度きりで足りる情報はコミットログへ。

### 2. 重複とは「原理的に食い違えない関係」のこと

動作の説明はコードと食い違えない（食い違えばコメントが単に誤り）ので、情報量はゼロ。**意図の説明はコードと食い違いうる**——実装が意図を達成し損ねることがあるため。だから同じ語彙を使っていても重複ではない。

さらに、意図コメントが実装とズレたときは「コメントが古い」ではなく「実装が意図から外れた」という検知になる。前者はノイズだが、後者は価値のある signal。

### 3. 腐りにくい情報ほどコメントに向く

腐敗速度は 実装詳細 > 契約 > 外部制約 > 過去の意思決定 の順。速く腐るものはコードとテストに担わせ、遅く腐るものをコメントに置く。

### 4. 意思決定のある場所にだけコメントがある

線を引いた場所には境界の意図、値を決めた場所には根拠、手を選んだ場所には Why not。**意思決定のない場所にコメントは要らない。**

## 書く前の判断順序

1. **コードで表現できないか。** 名前・関数分割・型で言えるならそちらへ。コメントが必要に思えた時点で、まず設計の signal を疑う。
2. **他に正しい置き場がないか。** 一度きりの変更理由はコミットログ、複数ファイルにまたがる設計判断は ADR / docs。その場合コメントの役割は**ポインタを置くこと**に変わる。
3. **読み手はこの下のコードを読むか。** 読まない（利用者）なら契約が要る。読む（実装変更者）なら動作説明は不要。
4. 残ったものを書く。

## 書くべきコメント

### A. 境界の設計意図

なぜこの抽象化が存在するのか、なぜここに線を引いたのか。実装は何度でも書き換わるが、線を引いた理由は線がある限り生きる。リファクタリングで「この境界を動かしてよいか」を判断できる唯一の材料。生成コードでは、設計の議論を定着させる唯一の手段でもある。

```go
// Bad — 動作の再掲。コードと食い違えないので情報量がゼロ
// TaskQueue はタスクを保持し、順番に取り出す。

// Good — 意図。実装がこれを達成し損ねることがありうる
// TaskQueue は「取り出し順の決定」だけを担う。並び順の計算をここへ集約することで、
// 呼び出し側が独自のソートを持ち込んで順序が二重管理になるのを防ぐ。
```

### B. 契約（公開 API・関数シグネチャ）

型で表現できない条件。副作用（引数の破壊、DB 書き込み、ネットワーク）、失敗の仕方（どの error がリトライ可能か）、呼び出し順序、呼び出し側の判断を変える計算量。

### C. 「何をしないか」

自分の責務の外側を宣言する。ただし**「ではどこが担当するか」は書かない**（[依存範囲の規則](#依存範囲の規則)）。

### D. Why not

捨てた選択肢とその理由。**結論ではなく前提を書く。**

```go
// Bad — 前提が書かれておらず、将来この判断が生きているか検証できない
// sqlc は使わない。

// Good — 前提が検証可能な形になっている
// sqlc は使わない。動的な WHERE 句の組み立てに対応しておらず、
// フィルタ条件の追加のたびに手書きクエリへ落ちるため。
```

### E. 触るなの警告

未来の特定の編集を名指しで止めるもの。費用対効果が最も高い類型。

```go
// この 2 行の順序を入れ替えないこと。ロック取得より先に ctx を差し替えると
// キャンセル時に mu が解放されない。
```

### F. 外部由来の制約とその参照

仕様書の節番号、他社 API のバグ、障害チケット、issue 番号。コードの外に原因があるものは、コードからは絶対に辿れない。

### G. 型で表せない不変条件

型に上げられるならまず型にする（`NormalizedPath` のような value class、branded type、専用型）。型に上げにくい残余は以下。

- 時制・ライフサイクル（Close 後に Write 不可、Init 前は使用不可）
- 並行性の制約（このフィールドは mu 保持中のみ触ってよい）
- 外部世界との対応（この ID は Stripe の customer ID と一致する）
- 数量的な前提（高々数百件想定、ゆえに線形探索）

型で担保しないと決めた場合、その判断自体が D になる。

```go
// 正規化済みであることは型では担保しない。JSON 境界での変換が全体に波及する
// コストに見合わないため。New 系関数で正規化する。
```

### H. 値の根拠（定数・設定ファイル・マイグレーション・CI 定義）

コードが薄い場所ほどコメントの比重が上がる。`timeout: 30s` には「読めば分かる How」が存在しないので、30 の由来はコメントでしか伝わらない。コードでは過剰になる密度が、ここでは適正。

### I. フィールドの意味

宣言には本体がないため、名前と型以外の情報はすべて外から与えるしかない。ドメイン型の定義箇所は、プロジェクト内でコメント密度を最も上げてよい場所。

- **ゼロ値・nil・空の意味**（`Parent *Task` の nil は「ルート」か「未取得」か。型では区別できない）
- 単位と尺度（`time.Duration` 等で潰せるなら型が先）
- 誰がいつ書き込むか（「Store が採番する。呼び出し側は空のまま渡す」）
- 他フィールドとの整合条件（「Status が Done のときのみ非 nil」）

### J. 要約見出し

分割できない長い手続きや非自明なアルゴリズムに、再構成コストを下げる一行。**関数抽出が第一選択**で、抽出すると壊れるとき（局所状態の共有、手続きの不可分性）のみコメントにする。

### K. テストの Why

テストの What はテスト名とアサーション自体が担う。コメントに落とすと二重管理になる。コメントが担うのは Why。

- なぜこのケースが存在するか（`// #482 の回帰テスト。BOM 付き UTF-8 で先頭キーが読めなくなった`）。テスト関数先頭の契約条項コメント（test-writing 規範が要求する「どの約束を検証するか」の 1 行）もここに当たり、restate ではない
- なぜこの期待値か（`// 仕様書 §3.2 より`）
- なぜ検証しないか（`// TZ は検証しない。CI と開発環境で異なるため`）

由来が書かれていない回帰テストは、後任者に「意味不明なケース」として削除される。

## 書くべきでないコメント

| 書くべきでないもの | 対処 |
| --- | --- |
| コードの動作の再掲 | 消す |
| 名前で言えること | 名前を直す |
| 型で担保できること | 型にする（value class / branded type / 専用型） |
| 説明が要るほど複雑な関数の説明 | 関数が 2 つのことをしていないか疑う |
| 一度きりの変更理由 | コミットログへ |
| 変更履歴、コメントアウトされたコード | 消す（git にある） |
| 自分の依存範囲外への言及 | 消すか、上位（パッケージコメント）へ移す |
| 前提のない結論（「X は使わない」だけ） | 前提を書き足す |
| 文脈のない TODO | 理由と参照を足すか、issue にする |
| 非公開ヘルパーへの過剰なドキュメント | 薄くする（呼び出し元も本体もすぐ近くにある） |
| 装飾的な区切りヘッダ | 消す |

### 依存範囲の規則

コメントが言及してよい範囲は、そのコード要素の依存範囲を超えない。**ドキュメントの結合も結合**であり、コンパイラが検知しないぶん質が悪い。方向も DIP と同じで、上位が下位を語るのは正しい（パッケージが構成要素を語る）が、下位が兄弟や上位を語るのはまずい。

- 「永続化は扱わない」 → そのクラスに書く（自己完結している）
- 「永続化は Store が担当する」 → 両方を含むパッケージのコメントに書く

検査しやすい形にすると、**そのファイルが参照していない識別子をコメントが名指ししていたら疑う**。

## 対象別の要約

| 対象 | 主に書くもの |
| --- | --- |
| パッケージ | 構成要素の地図、責務の配分、利用の入口 |
| クラス・モジュール | 責務、抽象化の意図、何をしないか、全メソッドが保つ不変条件 |
| 公開関数 | 契約（副作用・失敗・順序・計算量）、名前で言い切れない What、抽象化の意図 |
| 非公開関数 | 上記を薄く。多くの場合は不要 |
| 関数内 | Why、Why not、触るな警告、外部制約への参照 |
| フィールド | ゼロ値の意味、単位、書き込み主体、他フィールドとの整合 |
| 定数・設定値 | 値の根拠 |
| テスト | なぜこのケース、なぜこの期待値、なぜ検証しないか |

## 迷ったときの検査

- **このコメントは実装と食い違いうるか。** 食い違えないなら動作の再掲であり、消してよい。
- **名指ししている識別子を、このファイルは参照しているか。** していないなら依存範囲を超えている。
- **書かれた前提は、将来の読み手が検証できる形か。**
- **消したら、誰が何を再発明するか。** 答えられないなら不要。

## 言語依存であること

「型で担保できる範囲」は言語の表現力の関数なので、コメント規範は言語ごとに異なる。Kotlin の value class や Rust の所有権で表現できることは、Go や TypeScript ではコメントに残る。**Go では特に、ゼロ値の意味・並行性の制約・ライフサイクルの残余が大きい。**

型で潰せるものをコメントで代替している箇所を見つけたら、指摘はコメントではなく型に向ける。

## 規約名

評価結果はこの名前で分類する。

### 過剰（書かれているが書くべきでない）

| 規約名 | 内容 |
| --- | --- |
| `restate` | コードの動作の再掲。実装と食い違えないので情報量がない |
| `nameable` | 名前・関数分割で言えること |
| `typeable` | 型で担保できること |
| `episodic` | 一度きりの変更理由。コミットログに属する |
| `out-of-scope` | 自分の依存範囲外への言及 |
| `dead` | 変更履歴、コメントアウトされたコード、装飾的な区切り |
| `over-doc` | 非公開要素への過剰なドキュメント |

### 誤り・不十分（書かれているが機能していない）

| 規約名 | 内容 |
| --- | --- |
| `stale` | 実装と食い違っている |
| `no-premise` | 結論だけで前提がなく、将来この判断の生死を検証できない |
| `unclear` | 書いてあるが、初めて読む人に意図が伝わらない |

### 不足（書かれていないが書くべき）

| 規約名 | 内容 |
| --- | --- |
| `missing-intent` | 境界・抽象化の意図がない |
| `missing-contract` | 副作用・失敗の仕方・呼び出し順序・計算量がない |
| `missing-whynot` | 非自明な選択に、捨てた選択肢の説明がない |
| `missing-rationale` | 定数・設定値・フィールドの意味や根拠がない |
| `missing-ref` | 外部制約（仕様書・issue・障害）への参照がない |
| `missing-test-why` | テストケースの由来・期待値の根拠がない |
