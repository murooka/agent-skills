# organize-memory

Claude Code の auto-memory を整理するときは、この手順に従う。

## 対象と前提

auto-memory はプロジェクト(cwd)ごとに `~/.claude/projects/<cwd のスラグ>/memory/` に保存される。
`MEMORY.md` がインデックスで、セッション開始時に**先頭 200 行または 25KB**(早く達した方)だけがロードされる。
個別メモリファイルはロードされず、必要時に Read されるオンデマンド方式。したがって整理の価値は
「インデックス予算の節約」と「将来のセッションを誤誘導する記述の除去」の 2 つにある。

- **フォーマットの正は、実行中セッションの system prompt にある Memory 節**(frontmatter の契約、
  1ファイル1事実、インデックスの書式)。ハーネスの更新に追従するため、書式をこの文書に固定しない。
  補助資料として `references/memory-spec.md` に公式仕様の詳細と旧世代フォーマットのカタログがある。
  scan 結果を解釈する前に一読する。矛盾したら system prompt が勝つ。
- **対象ルートは既定で `~/.claude/projects`**。ユーザーが別のルートを指定した場合(検証・テスト用途)は
  そのルートだけを対象にし、既定ルートには一切触れない。

## モード

| モード | 対象 | 使いどき |
|---|---|---|
| 単一プロジェクト(既定) | 現在の cwd に対応するスラグの memory/ のみ | 通常の起動時 |
| 横断 | 対象ルート配下の全 memory/ | 「全プロジェクト」「横断で」と言われたとき |

プロジェクト間の重複検出・昇格・消滅プロジェクトの掃除は横断モードでのみ完全に機能する。
単一プロジェクトモードで昇格候補やプロジェクト外の問題を見つけたら、計画に「横断モードで扱う候補」として
記録するに留め、他プロジェクトのメモリには触らない。

## Workflow

### 1. Scan

機械検出できる問題は同梱スクリプトに任せる:

```bash
python3 scripts/scan.py                      # 既定ルート、全プロジェクト
python3 scripts/scan.py --project <スラグ>    # 単一プロジェクト
python3 scripts/scan.py --root <path> --json out.json   # ルート差し替え + 機械可読出力
```

スクリプトが検出するもの: フォーマット世代(旧 frontmatter / frontmatter なし)、非 kebab-case ファイル名、
`type` 欠落、行数超過(1ファイル1事実違反の疑い)、インデックス不整合(索引にないファイル・実体のない索引行)、
インデックス予算(200 行 / 25KB)の消費率、プロジェクト間の同名ファイル、更新が 90 日以上前のファイル。

スクリプトでは判定できず、エージェントが中身を読んで判断するもの: 名前が違うだけで同じ事実を指す重複、
記述の陳腐化(Step 3)、ユーザースコープかプロジェクトスコープか(昇格判定)、スラグに対応する
作業ディレクトリが実在するか(消滅プロジェクト。スラグは `/` と `.` を `-` に潰した非可逆変換なので、
候補パスを組み立てて実在確認し、確信が持てなければ Step 4 の裁定に回す)。

### 2. 分類

検出した問題を処置別に分類する:

| 問題 | 処置 |
|---|---|
| 旧世代フォーマット・非 kebab 名 | 現行契約へ正規化(リネーム + frontmatter 書き換え) |
| 複数の事実・時系列ログが 1 ファイル | 事実単位に分割。ログ形式は「今も真である結論」だけを抽出し、経緯は捨てる |
| 同じ事実の重複(プロジェクト内・間) | 最新かつ正確な 1 つに統合 |
| インデックス不整合・予算超過 | Step 6 でファイル実体から再生成 |
| 陳腐化の疑い | Step 3 の検証へ |
| ユーザースコープの事実 | 昇格候補(後述「昇格先の選び方」) |
| 消滅プロジェクトのメモリ | 後継プロジェクトへの移送、または削除(裁定へ) |

### 3. 陳腐化の検証 — 受動的に残さない

各候補について、記述内容を現実と能動的に突き合わせる: 参照先ファイルの実在、git の状態(push 済みか、
タグの有無、ブランチ)、「未実施」「残作業」と書かれた作業の完了状況、記述されたツール・パスの現存。

検証結果で 3 つに分ける:

- **陳腐化確定**(現実と矛盾する根拠あり) → 削除または更新を計画に載せる。根拠を必ず添える
- **現役**(現実と一致する根拠あり) → 残す
- **曖昧**(裏取りの手段がない) → **黙って残すことを禁止する**。Step 4 の裁定に回す

この禁止が本スキルの中核。判断がつかないとき AI は防御的に「残す」を選びがちで、それを繰り返すと
メモリは古い記述で埋まり、インデックス予算を食い潰し、将来のセッションを誤誘導する。
曖昧さは「残す理由」ではなく「人間に聞く理由」である。

### 4. 人間裁定

曖昧なもの(陳腐化・消滅プロジェクト・消してよいか判断の割れる削除候補)は、まとめて人間に問う。
AskUserQuestion があれば 1 回 4 件までのバッチで、なければ同じ内容を番号付きリストで提示して回答を待つ。

各質問に必ず含めるもの — 人間が**元ファイルを開かずに**判断できる粒度で:

1. 内容の要約(1〜2 文。何が書いてあるメモリか)
2. 疑う根拠(最終更新がいつか、何が確認できなかったか)
3. 消した場合に失うもの

選択肢は「削除 / このまま残す / 更新して残す(直す内容を提示)」。推奨があれば付けてよいが、
回答を推測して代行しない。回答は裁定として計画に反映する。

### 5. 計画提示と承認

適用前に変更計画を提示し、承認を得る:

```
## メモリ整理計画 (<対象スコープ>)

### 正規化 (n 件)
- <file> — <何をどう直すか>
### 分割・統合 (n 件)
### 削除 (n 件)
- <file> — 根拠: <検証結果 or 裁定>
### 昇格 (n 件)
- <file> → <移設先> — <理由>
### 消滅プロジェクト (n 件)
### インデックス
- <slug>/MEMORY.md 再生成: <n> 行 → <n> 行 (予算 200 行 / 25KB)
```

### 6. 適用

1. **最初にバックアップ**: 変更対象の memory/ ディレクトリ全体を
   `~/.claude/backups/memory-organize-<YYYYMMDD-HHMMSS>/<スラグ>/` にコピーする
   (対象ルートを差し替えている場合は `<ルート>/../backups/` 配下)
2. 計画どおりに変更を適用する
3. 昇格は「移設先に書く → メモリから削除」の順。二重管理は残さない
   (公式指針: 恒久ルールは CLAUDE.md、メモリは学習パターン。両方にあるなら CLAUDE.md に一本化)
4. MEMORY.md は編集ではなく**ファイル実体から再生成**する(1 行 1 メモリ、
   `- [タイトル](file.md) — 想起の手がかり`)
5. 結果を報告: 削除 / 更新 / 昇格 / 分割の件数、インデックス予算のビフォーアフター、バックアップの場所

## 昇格先の選び方

| 内容 | 移設先 |
|---|---|
| ユーザー自身の事実、全プロジェクト共通の好み(パッケージマネージャ、言語、確認の取り方) | `~/.claude/CLAUDE.md`。`~/.claude/rules/` の運用があればそちらでもよい(既存構成に合わせる) |
| プロジェクト固有のコード規約・アーキテクチャ・ディレクトリ構成 | プロジェクトの `CLAUDE.md`(肥大化するなら organize-claude-md スキルで整理) |
| 進行中の作業状態・一時的な決定 | メモリに残す(昇格しない) |

判断基準: 「次のセッションで**常に**効いてほしい規範」は CLAUDE.md/rules、「関連する話題が出たときに
思い出せればよい事実」はメモリ。同じユーザー事実が 2 プロジェクト以上のメモリに複製されていたら、
それはグローバル設定に置くべきだったもののほぼ確実な兆候。

## 制約

- **削除は「検証の根拠」か「人間の裁定」のどちらかを必ず伴う**。どちらもない削除はしない
- 適用前バックアップを飛ばさない
- 対象スコープ外(単一プロジェクトモードでの他プロジェクト、既定ルート外)に書き込まない
- 削除以外の操作(正規化・分割・統合・昇格)では情報を落とさない。要約で縮めるのはよいが、
  規範の意図と適用条件(Why / How to apply)は保存する
