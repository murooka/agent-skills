# knowledge-ownership

「この情報を所有するのは誰か」という問いで設計判断を検査するスキル。

## 解決する課題

機能的に正しいコードでも、ファイル分割・コメント・テストの依存先の判断を誤ると、内部知識が境界を越えて漏れ(knowledge leakage)、過剰結合が生まれる。この失敗は怠慢ではなく「分離を増やす・説明を増やす・検証を増やす」という一見勤勉な過剰から生まれるため、個別のバッドパターン列挙では防げない。

## アプローチ

境界や依存を「足す」判断(ファイル分割・新 export・コメント・テスト assertion)の直前にだけ所有権の問いを課す抑制規範と、実装完了後に diff を新鮮なコンテキストのサブエージェントへ渡す change simulation レビューの二段構え。
