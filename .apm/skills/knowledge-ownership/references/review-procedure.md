# Change Simulation レビュー手続き

サブエージェント向けの検査手続き。diff を対象に、境界新設編集が生む不適切な依存と knowledge leakage を検出する。

## 入力

- 検査対象の diff（または変更ファイル一覧）
- 必要に応じて周辺ファイルを読んでよい（依存先の定義、既存の類似実装、テスト対象の公開 API）

## 境界の単位

境界の単位はモジュールとする（Python ならファイル、公開 API を持つパッケージならパッケージ）。同一ファイル内の private 分割・行コメント・docstring は境界を越えない。

## Step 1: 境界新設編集の抽出

diff から次の編集だけを抽出する。それ以外（既存依存の内側に閉じた修正）は検査しない。

- 新ファイル / 新モジュールの作成
- 新しい export（公開関数・公開型・公開定数の追加）
- 新しい import（依存の新設）
- 新しいテスト assertion（既存テストへの追加を含む）
- 新しいコメント（docstring を含む）
- 新しい関数・クラス定義（private を含む。境界内で完結するかは Step 2 で判定する）

抽出は機械的に行う。境界を越えるかどうかの判定は抽出段階ではなく Step 2 で行う（同一ファイル内に閉じる編集も抽出してよく、simulation で非 finding とすればよい）。編集の数え方（新規ファイル一式を1編集とするか要素ごとに分けるか）は判定に影響しないため任意。

## Step 2: 各編集に対する change simulation

抽出した編集ごとに実行する。

1. **依存の特定** — この編集は何の情報に依存したか、または何の情報を新しい場所へ持ち込んだかを一文で書く。
2. **変更シナリオ** — その情報が将来変更される自然なシナリオを1つ以上立てる。次は例であり網羅ではない。対象に自然なシナリオを自由に立ててよい。
   - human-facing 文字列の文言変更
   - 内部データ構造・payload の変更
   - 実装の置き換え（アルゴリズム・ライブラリ）
   - 表示・出力形式の変更
   - 新しい caller の追加
   - private な内部のリファクタリング
3. **波及の判定** — シナリオを実行したとき、いま検査中の編集箇所も変更が必要になるかを問う。必要になる場合、その変更はこの箇所と本来関係があるかを問う。「本来関係がある」とは、その変更が依存先の公開契約・文書化された契約の変更そのものである場合を指す。契約化されていない情報の変更で波及が生じるなら、その依存は本来無関係な情報への依存である。
4. **finding の条件** — 「本来無関係であるはずの箇所に変更が波及する」ことを具体的に示せた場合のみ finding とする。
5. **要件の根拠確認** — 「その情報は明示的な要件・契約か」の確認は、リポジトリ内の情報を根拠とする（docs、仕様、テスト、設定、型定義、実装コードなど。例示であり網羅ではない）。タスクやチケットなどリポジトリ外の明示的な要件も根拠にしてよい。確認は依存を正当化する方向・否定する方向のどちらにも使う。根拠が見つからなければ、要件ではないとみなして判定してよい。

## Step 3: 分類語彙による説明

finding の報告では、依存先の情報を次の語彙で分類して説明する。分類は説明のための語彙であり、検査の入口ではない（先に Step 2 の simulation で波及を示し、その説明にこの語彙を使う）。

- **Stable contract** — 意図的に依存してよい情報。public API、明示的な error code、公開型、外部仕様として保証される behavior。
- **Internal representation** — 特定モジュール内部だけが知るべき情報。内部 payload、private helper 間のデータ構造、内部状態表現。
- **Human-facing information** — 人間向けの情報で、machine-readable contract ではないもの。error message、log message、UI 上の説明文。
- **Incidental implementation detail** — 現在の実装にたまたま存在するが、依存されることを意図しないもの。private helper、内部関数名、処理順序、中間表現。

コメント・docstring に関する finding（caller 固有知識の混入など）は4分類に無理に当てはめず、「その情報をどの抽象化が所有するか」という所有権の言葉で説明してよい。

## Step 4: 報告

finding ごとに次の形式で報告する。

- **場所**: file:line（diff 適用後のファイルの行番号。diff が適用不能な場合は復元後の内容に基づく。複数行は範囲表記、複数箇所は列挙でよい）
- **新設された依存**: 何が何に依存したか（分類語彙を使う）
- **シナリオ**: 立てた変更シナリオ
- **波及**: 無関係であるべき箇所がどう壊れるか
- **修正方向**: 依存を断つ / 知識を所有者側へ移す / 境界を閉じる（分割を戻す）のいずれか。複数の選択肢がある場合は主たる1つを選び、代替を併記してよい

同一の依存が複数の編集（import・コメント・docstring など）に現れる場合は 1 finding に統合し、場所欄に証跡として列挙する。依存先が異なるなら別 finding とする。1つの編集が複数の依存先を持つ場合は、依存先ごとに分けても、密接に絡むなら統合してもよい（数え方は判定に影響しない）。

## 報告バー

- 変更シナリオと波及を具体的に示せない懸念は報告しない。
- 設計の好み（命名、分割の趣味、スタイル）は報告しない。
- 型・lint・architecture test が検出できる違反（現行のプロジェクト設定で実際に検出されるもの）は報告しない。
- 知識所有権・境界と無関係な一般的品質問題（flakiness、バグの疑い、性能）は finding にしない。レビューの価値を大きく損なうほど重大な場合のみ、別枠で簡潔に触れてよい。
- finding が0件なら「境界新設編集に問題なし」と報告する。検査過程の記録（抽出した編集の列挙と判定理由の要約）を付けてよいが、そこに finding 未満の懸念やヘッジを紛れ込ませない。
- 手続きの対象外でも、diff 自体の破損・適用不能など、レビューの前提を壊す問題を見つけた場合は、findings とは別枠で簡潔に報告する（finding には数えない。事実と帰結を数行以内で）。diff が適用不能でも復元できる範囲でレビューは続行し、場所欄の行番号は復元後の内容に基づく。復元の手段は問わない（+ 行の採用、意図の推定など合理的な方法でよい。採った方法は別枠報告に明記する）。

## Calibration: 判定例

### 例1: 内部表現の境界越え（finding になる）

Logger の Formatter を別ファイルに分離し、Formatter が Logger 内部の payload 構造を import している。

- シナリオ: Logger 内部の payload 構造を変更する
- 波及: Logger の外にある Formatter ファイルまで変更が必要になる。payload は internal representation であり、境界を越えて知られるべきでない
- 修正方向: Formatter を Logger と同じ境界内へ戻す

### 例2: caller 固有知識の混入（finding になる）

任意の値を安全に文字列化する汎用 helper に「Logger が安全にログ出力するために使用する」というコメントが書かれている。

- シナリオ: 新しい caller の追加、または Logger 側の用途変更
- 波及: helper 自身の契約と無関係な理由で helper のコメントが陳腐化する。caller の rationale は caller が所有する知識
- 修正方向: コメントを Logger 側の呼び出し箇所へ移す

### 例3: human-facing 文字列への依存（finding になる）

テストが error.code に加えて error.message の完全一致を assert している。

- シナリオ: メッセージ文言の改善（意味は不変）
- 波及: 文言変更という無関係な変更でテストが失敗する。message は human-facing information であり、stable contract は code 側
- 修正方向: message の assert を削除する。ただしメッセージ自体が明示的なプロダクト要件である場合は正当な依存なので、その根拠を確認してから判断する

### 例4: 正当な依存（finding にならない）

テストが公開 API の返り値の型と明示的な error code に依存している。これらは stable contract であり、意図された依存。報告しない。

### 例5: 境界内に閉じた分割（finding にならない）

大きくなった関数を同一ファイル内の private 関数に分割した。知識は境界を越えていない。報告しない。
