# Knowledge Ownership — 情報の所有権による設計判断の検査

コードが機能的に正しくても、情報の境界・所有権・変更可能性の判断を誤ると、knowledge leakage（内部知識の境界越え）と過剰結合が生まれる。個別の bad pattern を記憶する代わりに、それらを生み出す設計判断そのものを検査する。

## 中核の問い

> この情報を所有するのは誰か。所有していないモジュール・抽象化・テストへ漏らしていないか。

## 前提: failure mode は「過剰」である

設計ミスは怠慢からではなく、局所的には美徳に見える過剰から生まれる。分離を増やす・説明を増やす・検証を増やす——いずれも単体では勤勉に見えるが、所有権境界を越えた瞬間に leakage になる。以下の規範はすべて「足す」判断への抑制として働く。

## 生成時の抑制規範

実装・変更の最中、次の3つの「足す」判断の直前にだけ、所有権の問いを課す。それ以外の場面でこのスキルのために立ち止まらない。

### 1. ファイル分割・新モジュール作成の直前

分割先が知る必要のある情報を列挙し、それぞれに「この知識は境界を越えてよいか」を問う。内部表現の知識（内部 payload 構造、private なデータ形式）が境界を越えるなら、分割しない。同じ場所に置くことは美徳である。

### 2. コメント記述の直前

書こうとしている情報を所有するのは、コメントを付ける対象自身かを問う。対象自身の契約（何をするか・何を保証するか）は対象に書く。特定 caller がそれを必要とする理由は caller 側に書く。

### 3. テスト assertion・依存追加の直前

依存しようとしている対象は、意図的に安定化された契約かを問う。error code・public API・公開型・自ら設計し文書化した契約・タスクや仕様が明示的に要求する値や挙動には依存してよい。human-facing な文字列（error message、log 全文、UI 文言）、内部構造、処理順序には依存しない。依存できる安定契約が存在しない場合は、検証を諦めるのでも不安定なものに依存するのでもなく、契約を設計・文書化してから依存する（例: ログの構造化フィールドを出力契約として docstring に明文化し、テストはそこにだけ依存させる）。

## 実装後のレビュー — 必ずサブエージェントへ委譲

コードの追加・変更を一通り書き終えたら、diff をサブエージェントに渡して検査する。

**実装エージェント自身に判定させない。** 自分の設計判断を事後評価すると、判断時の合理化がそのまま残る。診断には diff だけを渡した新鮮なコンテキストが必要である。

サブエージェントの起動手順:

1. このスキルの `references/review-procedure.md` を読むよう指示する
2. 検査対象の diff（または変更ファイル一覧）を渡す
3. 手続きに従った findings の報告を受け取り、修正を実装エージェント側で行う

検査対象は境界新設編集のみ（編集個所ごとに判定する）: 新ファイル/モジュール、新 export、新 import、新テスト assertion、新コメント。既存依存の内側に閉じた修正だけの diff なら、このレビューは不要。

## 対象外・役割分担

- 型エラー・lint 違反・architecture test で決定的に検査できる違反は対象外。deterministic check に任せる。
- コメントの表記規範（書き方・密度・形式）は code-comment-style スキル、テストの記述規約（AAA・assert メッセージ・契約からのケース導出）は test-writing スキルが担当する。本スキルが扱うのは「その情報をどの抽象化が所有するか」という判断層のみ。
